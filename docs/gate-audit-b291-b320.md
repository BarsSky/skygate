- Class (latent, not currently dead): every script's behavioural half is `go test … -run '<block-id pattern>'`, and `go test` prints `ok … [no tests to run]` — which both of the guard greps (`'^ok'` and `! ## B319 regression-detector verdict

B319 is a **genuine regression detector for the query text, and not a behavioural one for PostgreSQL.** Its own structural half *would* have failed before the fix: the lookup is extracted with `awk` from `ruleRows, err := s.dbc().QueryContext` to the closing `, userID, hostname)` line (`check_b319_rules_owner_type.sh:69`), which yields exactly the pre-fix lines that are now `reconciler.go:536-549`; against the pre-fix text `A1` (`:72-76`, "no bare `OR device_id IN (`") and `A2` (`:77-81`, "the explicit `CAST(device_id AS TEXT) IN (` is present"), `B1` (`:89-93`, "the sub-select no longer filters on `user_id`") and `B2` (`:94-98`, "the branch matches the node by hostname") all report `bad` and the script exits 1 — i.e. the contracts are written as absence/presence pairs, not as a snapshot of the post-fix code. The mirror of the same assertions exists in Go (`internal/feature/exit_rules/reconciler_b319_test.go:109-138`), scoped to the same query text for the same reason (`:117-127`).

What it does **not** do is prove the outcome. The SQLite half (`check_b319_rules_owner_type.sh:139`, `go test … -run 'B319'`) runs `collectDevicePrefState` against a migrated SQLite DB and asserts `TotalRules == 2` (`reconciler_b319_test.go:86-104`), but the test file itself records why that is not a detector (`:21-22`, `:29-33`): SQLite compares `9` with `'9'` happily, so the test passes with the broken query too — the breakage is a dialect difference, not a logic difference, which is exactly why «the whole suite stayed green».

The only outcome-shaped contracts are `D1`/`D2` (`check_b319_rules_owner_type.sh:113-135`), and **what they SKIP on is the container name**: the gate is `docker ps --format '{{.Names}}' 2>/dev/null | grep -q 'skygate-pg-local'` (`:114`); when it does not match, the script prints `skip "D1/D2: no skygate-pg-local container — run this on the VM for the live half"` (`:134`) and still exits 0 if the greps and the SQLite tests pass. So on a developer machine (SQLite only, no PG container) both PostgreSQL contracts SKIP, `SKIP` is never a FAIL, and the regression this block exists for is invisible — on the operator's own hosts too, unless PG happens to run as a container with that exact name, user (`admin`), database (`skygate_staging`) and the four-column schema. Worse for detection power: even when they run, `D1`/`D2` execute the check's own SQL literals (`:115`, `:126`), not the product's query, so they prove "this server accepts the CAST shape / refuses the int-vs-text shape" — a capability probe about PostgreSQL — and a Go-side revert would be caught only by `A1`/`A2`/`B1`/`B2`'s text greps, never by `D1`/`D2`. Two secondary fragilities: `A1` and `B1` pass vacuously if the `awk` region ever comes back empty (`:69`), and `D1`/`D2` hard-code their connection details, so a differently-named PG service silently skips instead of failing.

## Notes

- **`mixed` is the honest label for all 30 scripts.** Every script in the slice carries at least one `go test` invocation (B299 is the sole exception — its behavioural half is real shell process control), so a strict reading of the definitions gives 30 × `mixed`, 0 × `structural`, 0 × `behavioural`, 0 × `live-only`. The interesting variance is in *what* the behavioural half touches: real DB/table/server (B291 in-memory migrated SQLite, B305/B316 real stores, B299 the runner), a real subprocess/script (B304's apply-script harness), a real local socket/server (B302's WS probe, B307's STUN server, B315's in-process proxy), or nothing but pure helpers (B297, B308, B309, B310, B312, B320). The stated historical weakness — "checks pin the PRESENCE of code, not the OUTCOME of running it" — is therefore not repealed by this block: the newest checks add the `go test` line, but most of the ones I read still spend 30–60 assertions on source text and then delegate the outcome to a helper-level unit test.
- **The slice is almost entirely offline.** Only **B319** (`check_b319_rules_owner_type.sh:113-135`) has a live-dependency section (docker + PostgreSQL) and it is exactly the section that would have caught the runtime regression — and it is the section that SKIPs. No other script in B291–B320 mentions docker/psql/live hosts at all (verified by grepping the slice for `docker ps|docker exec|docker info|psql |command -v docker|tailscale status|curl -|[ -d /home|sqlite3`); `psql` and `command -v docker` appear in the slice only at `check_b319_rules_owner_type.sh:114-127`. Every other `SKIP` in the range is environmental rather than dependency-shaped: `command -v go` missing (all 30 scripts), no `mktemp` (`check_b304_oidc_panel.sh:283`) and no `timeout`/`setsid` (`check_b299_catalog_cannot_hang.sh:234`, `:238`). So B319's `skip "D1/D2: no skygate-pg-local container"` is the *only* dependency-gated skip in B291–B320 — and it is precisely the one that hides this slice's motivating regression. The right counter-pattern is already in the slice twice: B304 (`:210-284`) and B299 (`:178-239`) build self-contained behavioural harnesses with stubs, so they never need a live dependency to reach a real outcome.
- **FAIL-visibility in the gate log is a second, independent death mode.** `run_check` prints only the first 20 lines of a failing check's combined output (`scripts/verify_pre_deploy.sh:186` for TIMEOUT, `:195` for FAIL — confirmed). Most scripts in this slice print 30–60 `PASS` rows before their late assertions (B315 has ~60 assertions; B317 ~40; B293 ~50), so a failure in e.g. `G7`/`H1`/`I2` of `check_b315_derp_metrics_endpoint.sh` or in the `I2`/`I3` Go-test block of B317 appears in the gate log as the block's essay plus twenty `PASS` rows and nothing else. The contract fires, but the evidence an operator needs is truncated away — worth remembering when a gate run reports an unexplained red block in this range.
- **The two newest blocks are the weakest pair in the slice.** B319's destructive half is a query-text grep whose only outcome probe is container-name-gated, and B320's destructive half is a single-substring assertion (`check_b320_tailscale_self_name.sh:149`) whose pure-function test covers only the *candidate picker*. Both blocks were written in response to live incidents where the code was right and the *data/environment* was wrong (a PG type mismatch; a ghost registration plus an `.env` pin) — precisely the class that a grep cannot see.
- Registration-line housekeeping: B299's `run_check` sits between B303 and B311 (`verify_pre_deploy.sh:5398`), and B311's sits between B299 and B304 (`:5404`), so a reviewer reading the gate top-to-bottom meets the blocks out of order; the numeric order of the slice's registrations is B291–B298, B300–B303, B299, B311, B304–B310, B312–B320.
- All 30 scripts are distinct files (no shared script in this slice), are tracked by git (each asserts `git ls-files --error-unmatch` on itself), and only B304's behavioural harness and B307/B305/B302's socket tests create temporary resources — all of which are cleaned up (`mktemp -d` + `rm -rf` at `check_b304_oidc_panel.sh:281`, `check_b299_catalog_cannot_hang.sh:167`).
