# «Один сервис не работает только на одном устройстве» — префикс ушёл на другой relay (B480)

Правило, вокруг которого построен весь блок, словами оператора: **если правило зарезервировано за
exit node, остальные принимают эту политику**; нужен новый exit node под старые правила — пользователь
выделяет их и делает заявку.

## Симптом

Один сервис (живой случай — Discord) не работает **только на одном устройстве**: остальные
сайты на нём открываются, а тот же сервис работает на других устройствах. В панели всё
выглядит правильно — все правила этого устройства указывают на один и тот же exit node.

## Причина

headscale отдаёт префикс ровно с одного relay, и какой это relay, решает таблица
`prefix_owner`. До B480 движок считал все claim'ы равноправно, поэтому претензия устройства,
у которого exit-node вообще не выбран (`opted_out` / пустая настройка), могла сравняться с
претензией устройства, которое реально маршрутизирует, и тай-брейк по имени relay передвигал
префикс. Дальше ACL пиннил `via=[новый владелец]`, а это **фильтр разрешений**: устройство,
чей exit node — прежний relay, теряло ровно эти адреса. Живой замер 2026-11-16: у `basic`
(exit node karolina, все 164 правила Discord на karolina) и `skyworker` (exit-node не выбран,
правила на emilia) совпали 17 `/32` Discord; голоса разделились 1:1, алфавит выбрал emilia, и
`basic` потерял эти адреса.

## Политика (как договорились)

1. **Резервирование принимают, а не перерешают.** Существующий владелец, который здоров и у
   которого есть хотя бы один голосующий claim, сохраняет префикс; претензия другого relay —
   это принятие.
2. **Инертный claim не голосует.** Устройство без выбора exit-node всё равно получает доступ
   к префиксу (считается покрытием), но не может двигать резервирование. Если у владельца не
   осталось голосующих — префикс пересчитывается, и это возвращает его тому, кому он нужен.
3. **Принятие по объемлющему диапазону.** Префикс, за который никто не голосует (типичный
   CDN-`/32`), обслуживает владелец самого специфичного диапазона, который его содержит, —
   вместо «размазывания» по другому relay.

## Смена exit node — это заявка

Если пользователю нужен **другой** exit node для уже существующих правил, он выделяет эти
правила и отправляет запрос (`exit_relay_requests`, B440): политика `auto` / `require_approval`
/ `refuse`, утверждение = ручной пин оператора. Добавление того же target с другим relay
больше **не** создаёт второе правило: писатель отвечает «already covered by relay "karolina"»
и открывает доступ через резервирование.

## Починка строк, созданных до этого правила

```bash
bash scripts/b480_dup_rule_cleanup.sh            # отчёт: у каких target больше одной строки
bash scripts/b480_dup_rule_cleanup.sh --apply    # оставить строку владельца, лишние удалить
```

Скрипт никогда не удаляет последнюю строку для пары (user, device, target) и перед записью
делает резервную копию базы. Строки, у которых нет владельца ни с одной стороны, он не
трогает — сначала закрепите префикс (`skygate prefix-owner`), потом запускайте `--apply`.

## Как это проверяется в дереве

* `internal/prefixowner/prefixowner_b480_test.go` — шесть тестов: инертный claim не двигает
  резерв; резервирование принимают; резервирование без голосующих пересчитывают;
  вложенный `/32` наследует владельца диапазона; ручной пин сильнее наследования;
  `auto`-размазывание не наследуется (контракт B275).
* `internal/db/device_rules_b480_test.go` — любой поиск правила по target без relay.
* `scripts/check_b480_ownership_policy.sh` — контракт на всё перечисленное, регистрацию в
  гейте, документацию EN+RU и сам скрипт очистки.
