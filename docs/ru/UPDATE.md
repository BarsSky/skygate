# Обновление Skygate

**Все поддерживаемые способы обновления в одном месте** — от обновления одной
кнопкой из интерфейса до полностью ручной замены бинаря на изолированном хосте.

English version: [`docs/UPDATE.md`](../UPDATE.md).
Установка с нуля: [`docs/ru/INSTALL.md`](INSTALL.md).
Эксплуатация (бэкап, восстановление, HA): [`docs/operations.md`](../operations.md).

---

## 1. Какой способ подходит именно вам?

| Вид установки (см. `INSTALL.md`) | В интерфейсе `/admin/update` | Автоматически / по расписанию | Вручную |
|---|---|---|---|
| Docker compose из исходников (A) | **Обновить**, **Протолкнуть обновление** (git pull + пересборка + пересоздание) | ✅ планировщик ([§4.4](#44-обновление-по-расписанию-только-docker)) | [§6.1](#61-docker-compose-из-исходников) |
| Docker compose, готовый образ (B/C/D) | **Pull образа**, **Обновить** | ✅ планировщик | [§6.2](#62-docker-compose-готовый-образ) |
| Нативный systemd (E/F) | **Обновить** → привилегированный помощник ([§5](#5-нативные-установки-systemd--openrc--bare)) | ❌ никогда (планировщик пропускает нативные виды) | [§6.3](#63-нативный-systemd) |
| Нативный OpenRC / Alpine (G) | **Обновить** → помощник | ❌ | [§6.4](#64-нативный-openrc-alpine) |
| Голый бинарь (H/I) | **Обновить** → помощник | ❌ | [§6.5](#65-голый-бинарь) |
| Служба Windows (J) | ❌ (автообновления нет) | ❌ | [§6.6](#66-windows) |

Страница обновления всегда показывает, **какой путь она считает активным**: вид
установки, наличие `systemctl`/`rc-service`/`docker` и установлен ли
привилегированный помощник. Если на нативной установке написано «помощник не
установлен» — перезапустите установщик (идемпотентен, `skygate.env` сохраняется).

## 2. Перед обновлением

1. **Сделайте бэкап БД.** SQLite — копия файла (или встроенный бэкап);
   PostgreSQL — `pg_dump`. См. [`backup-restore-and-migration.md`](../backup-restore-and-migration.md).
2. **Запишите текущую метку сборки** — её показывают `/healthz` и страница
   обновления (например `v1.5.8-39-g2fb8235`). Она нужна для отката.
3. **Прочитайте release notes** целевого тега (миграции, ломающие изменения).
4. **Проверьте совместимость.** Нативный хост на SQLite обязан быть на **v1.5.9
   или новее**: релизы по v1.5.8 включительно на SQLite вообще не запускаются
   (`migration v44 … duplicate column name: user_name`). Помощник откажется от
   такой замены **до** подмены бинаря, так что попытка безопасна, но бесполезна.
5. **Выберите окно обслуживания** для нативного обновления: помощник
   перезапускает сервис, поэтому портал недоступен от нескольких секунд до ~минуты
   плюс время миграции.
6. **Фиксируйте тег, а не `latest`.** `latest` молча следует за новейшим релизом;
   с закреплённым тегом откат — это одна изменённая строка.

## 3. Метки версий и сборок

| Метка | Пример | Что это значит |
|---|---|---|
| Тег релиза | `v1.5.9` | Опубликованный релиз GitHub с ассетами. **Только его умеет ставить нативный помощник.** |
| Метка сборки с коммитом | `v1.5.9+4a6bbbe3` | Тег релиза плюс коммит сборки; суффикс `+…` отбрасывается автоматически. |
| Dev-сборка (git describe) | `v1.5.8-39-g2fb8235` | 39 коммитов после v1.5.8. Для docker-пути это нормальный git-ref, но ассетов релиза для такой метки GitHub не публикует — нативный помощник откажет с понятным сообщением и покажет ручные шаги. |

`SKYGATE_DEV_BUILD=true` помечает сборку как dev, чтобы интерфейс не напоминал об
обновлениях — удобно на машине, которая следит за `main`.

## 4. Установки в Docker

### 4.1 Из исходников

`entrypoint.sh` контейнера выполняет `go build` при каждом старте, поэтому
`git pull` + перезапуск — это полноценное обновление.

```bash
cd /path/to/skygate                 # ВСЕГДА каталог проекта (см. ловушку ниже)
git pull --ff-only
sudo docker compose up -d --force-recreate --no-deps skygate
# рекомендуется: миграции до старта контейнера
sudo docker compose exec skygate /app/skygate migrate-only
until curl -fsS http://127.0.0.1:8080/healthz | grep -q "$(git describe --tags)"; do sleep 3; done
```

`docker compose build` нужен только при изменении **Dockerfile**.

> **Ловушка: интерполяция `docker compose` зависит от CWD.** Если запустить
> `docker compose -f /path/docker-compose.yml …` из другого каталога, `.env`
> проекта **не** подхватится и каждый `${VAR:-default}` молча получит значение по
> умолчанию. На эталонном развёртывании это уже приводило к поломке. Всегда
> переходите в каталог проекта (или передавайте `--env-file /path/.env`).
>
> **Ловушка: `--force-recreate` обязателен** после изменений `extra_hosts`,
> томов или тега образа; обычный `restart` оставит старую сетевую конфигурацию.

### 4.2 Готовый образ

```bash
cd /path/to/skygate
sed -i 's|^SKYGATE_IMAGE=.*|SKYGATE_IMAGE=ghcr.io/barssky/skygate:v1.5.9|' .env
sudo docker compose -f docker-compose.ghcr.yml pull skygate
sudo docker compose -f docker-compose.ghcr.yml up -d --force-recreate --no-deps skygate
curl -fsS http://127.0.0.1:8080/healthz        # убедиться в новой метке сборки
```

* Теги **регистрозависимы и обязаны быть в нижнем регистре** (`ghcr.io/barssky/…`).
* Образ публикуется **только под linux/amd64**. На ARM используйте Go-тарбол
  (способ I в `INSTALL.md`) или соберите локально с `--platform linux/arm64`.
* Аналог в интерфейсе — кнопка **Pull образа** ([§4.3](#43-кнопки-в-интерфейсе)).

### 4.3 Кнопки в интерфейсе

Все они на странице **`/admin/update`** (нужна сессия администратора). Пока идёт
задача, страница сама обновляется, а на нативных установках в неё встраивается
журнал привилегированного помощника.

| Кнопка | Маршрут | Что делает | Где доступна |
|---|---|---|---|
| **Проверить сейчас** | `POST /admin/update/check-now` | Опрашивает GitHub Releases (или заданный канал) и кэширует новейшую версию | везде |
| **Обновить** | `POST /admin/update/apply` | Docker: забирает репозиторий/тег, пересобирает образ, пересоздаёт контейнер, ждёт `/healthz`. Native: кладёт `request.props` для помощника | везде, где вид определён |
| **Протолкнуть обновление** | `POST /admin/update/push` | Тот же оркестратор, но работает всегда и целится в **текущую** версию (или в переданный `target`) — инструмент «пересобрать этот же коммит» и повтора после сбоя | везде |
| **Pull образа** | `POST /admin/update/pull-image` | Забирает образ и тег из реестра (`ghcr.io/barssky/skygate` по умолчанию) и пересоздаёт контейнер — намного быстрее git+сборки (~5–10 с на прогретом кэше) | только Docker |
| **Откатить сейчас** | `POST /admin/update/rollback` | Отменяет идущую задачу; на нативных установках повторно запускает помощник с **предыдущим** тегом из состояния задачи. Если предыдущего тега нет — предлагаются ручные шаги | везде |
| **Скрыть** | `POST /admin/update/dismiss` | Убирает баннер обновления | везде |
| **Расписание автообновления** | `POST /admin/update/schedule` | Планировщик по времени суток (HH:MM) + включение/выключение; хранится в БД и перечитывается на каждом тике | только Docker (нативные виды пропускаются) |

Переменные окружения (значения по умолчанию; расписание страница может
переопределить в БД):

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `SKYGATE_UPDATE_CHECK` | `true` | Опрашивать релизы вообще. `false` для изолированных хостов |
| `SKYGATE_UPDATE_CHECK_INTERVAL` | `24h` | Интервал опроса; `off`/`0` отключает |
| `SKYGATE_UPDATE_CHANNEL` | `stable` | `all` учитывает и пре-релизы |
| `SKYGATE_AUTO_UPDATE_ENABLED` | `false` | Показывает кнопку применения; **сама по себе ничего не применяет** |
| `SKYGATE_UPDATE_SCHEDULE_ENABLED` | `false` | Включает планировщик по времени |
| `SKYGATE_UPDATE_SCHEDULE_TIME` | `03:00` | Локальное время, 24-часовой формат `HH:MM` |
| `SKYGATE_GITHUB_TOKEN` | *(нет)* | Необязательный токен: лимит GitHub API 60/ч → 5000/ч |

### 4.4 Обновление по расписанию (только Docker)

При `SKYGATE_UPDATE_SCHEDULE_ENABLED=true` (или галочке на странице) планировщик
применяет новейший найденный релиз в заданное `HH:MM`, соблюдая обычные
ограничения: идущая задача, неудачная проверка или не-Docker вид установки —
тик просто пропускается, а не ставится в очередь.

**Нативные установки никогда не обновляются автоматически:** systemd/OpenRC/голый
бинарь требуют явного нажатия **Обновить**, потому что помощник перезапускает
сервис.

## 5. Нативные установки (systemd / OpenRC / bare)

Нативное самообновление появилось в **v1.5.9**. До этого кнопки на нативной
установке отвечали «auto-updater for systemd not yet implemented».

### 5.1 Зачем привилегированный помощник (модель безопасности)

Сервис работает непривилегированно под `ProtectSystem=strict`, не может писать в
`/usr/local/bin/skygate` и не может перезапустить свой юнит (перезапуск изнутри
юнита убивает всю cgroup, поэтому потомок через `setsid` тоже умирает). Вместо
запуска skygate от root обновление разделено на две части:

```
непривилегированный skygate ──пишет──> <data_dir>/update/request.props  (только данные: TAG, JOB_ID, …)
                                              │
                                   root-овый skygate-update.path  (следит за файлом)
                                              │
                                   root-овый skygate-update.service (oneshot)
                                              │
                    /usr/local/lib/skygate/skygate-apply-update.sh  (единственный root-актор)
                       backup → download → проверка SHA256 → migrate-only
                       → атомарная замена rename → restart → ждём метку сборки в /healthz
                       → при сбое возвращаем skygate.prev + restart
                                              │
                                  пишет result.status / result.build /
                                  result.error / apply.log
                                              │
                       skygate подхватывает вердикт в состояние обновления при
                       следующем рендере /admin/update (update.ConfirmNativeSwap)
```

Что здесь важно знать:

* `request.props` **не содержит путей** — он парсится как данные и никогда не
  «сорсится». Все пути (бинарь, имя сервиса, env-файл, health-URL, каталог
  обновления, разрешённые owner/repo) берутся из **root-ового**
  `/etc/skygate/update-helper.conf`. Скомпрометированный skygate может попросить
  только «поставь официальный релиз с тегом X». Тег обязан соответствовать
  `^[A-Za-z0-9][A-Za-z0-9._+-]{0,63}$`, поэтому метасимволы shell и `..` до
  помощника не доходят.
* `/etc/skygate/skygate.env` принадлежит **сервисному пользователю** и
  **парсится, а затем передаётся через `env(1)`** — root его не сорсит.
* Бинарь меняется **атомарным `rename`** (запись поверх запущенного исполняемого
  файла падает с `ETXTBSY`), предыдущий бинарь сохраняется в
  `<data_dir>/update/skygate.prev`.
* Успех — это `/healthz`, вернувший `200` **и** метку сборки целевого тега, а не
  просто «кто-то слушает порт».
* Помощник всегда завершается с кодом 0, если вердикт записан; сам вердикт лежит в
  `result.status` (`done` | `rolled_back` | `failed`).

### 5.2 Как запустить и как следить

1. `/admin/update` → **Обновить** (или **Протолкнуть обновление**), цель — **тег
   релиза**. Метка git-describe или «голый» SHA отклоняются заранее: для них
   GitHub не публикует ассетов.
2. skygate пишет `request.props` в `<data_dir>/update/` и показывает «ждём
   привилегированный помощник».
3. systemd (или sudoers drop-in на OpenRC/bare) запускает помощник. Страница
   показывает фазы по мере обновления файла состояния, а по завершении
   подмешивает `apply.log`.
4. Вердикт появляется на странице в **старом** процессе (помощник отвалился до
   перезапуска) или в **новом** (после успешной замены).

Файл состояния — `SKYGATE_UPDATE_STATE_PATH` (в контейнере по умолчанию
`/data/skygate-update-status.json`, на нативной установке
`<data_dir>/skygate-update-status.json`). Если страница говорит «ждём» дольше
5 минут, она добавляет предупреждение — смотрите `journalctl -u skygate-update` и
`<data_dir>/update/apply.log`.

### 5.3 Конфигурация помощника — `/etc/skygate/update-helper.conf`

Создаётся установщиками (`write_update_helper` в `deploy/install-common.sh`),
владелец root, `chmod 0644`. Меняйте только если ваша раскладка отличается от
стандартной.

| Ключ | По умолчанию | Смысл |
|---|---|---|
| `SKYGATE_UPDATE_MODE` | `systemd` | `systemd` \| `openrc` \| `bare` — как помощник перезапускает сервис |
| `SKYGATE_UPDATE_DIR` | `/var/lib/skygate/update` | Каталог запроса/результата/журнала |
| `SKYGATE_UPDATE_SERVICE` | `skygate` | Имя юнита/сервиса |
| `SKYGATE_UPDATE_BINARY` | `/usr/local/bin/skygate` | Заменяемый бинарь |
| `SKYGATE_UPDATE_RUN_USER` | `skygate` | Пользователь для `migrate-only` и сервиса |
| `SKYGATE_UPDATE_ENV_FILE` | `/etc/skygate/skygate.env` | Из него парсится `SKYGATE_DB` (не сорсится) |
| `SKYGATE_UPDATE_HEALTH_URL` | `http://127.0.0.1:8080/healthz` | Точка проверки после замены |
| `SKYGATE_UPDATE_OWNER` / `_REPO` | `BarsSky` / `skygate` | Разрешены релизы только этого репозитория |
| `SKYGATE_UPDATE_ASSET_ARCH` | `linux-amd64` | Архитектура ассета релиза |
| `SKYGATE_UPDATE_BARE_START` | *(пусто)* | Команда запуска процесса в режиме `bare` |
| `SKYGATE_UPDATE_BASE_URL` | *(нет)* | Внутреннее зеркало ([§7](#7-зеркала-и-изолированные-хосты)) |
| `SKYGATE_UPDATE_GITHUB_TOKEN` | *(нет)* | Необязательный токен для fallback через Releases API |

Только на время запуска (удобно для пробного прогона или медленного хоста):

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `SKYGATE_UPDATE_DRY_RUN=1` | `0` | Остановиться после миграции, **до** замены бинаря |
| `SKYGATE_UPDATE_HEALTH_TIMEOUT` | `90` | Сколько секунд ждать метку сборки |
| `SKYGATE_UPDATE_HEALTH_POLL` | `1` | Интервал опроса |

Запуск помощника вручную (от root, например чтобы воспроизвести сбой):

```bash
sudo SKYGATE_UPDATE_DRY_RUN=1 /usr/local/lib/skygate/skygate-apply-update.sh
sudo tail -f /var/lib/skygate/update/apply.log
```

### 5.4 Откуда берётся артефакт и как проверяется

Помощник скачивает `<base>/skygate-<TAG>-linux-amd64.tar.gz` и проверяет его по
источникам в таком порядке:

1. **`SHA256SUMS`** рядом с ассетом (ассет релиза для GitHub, обязателен для
   зеркала). Это штатный путь для v1.5.9+; релизы v1.5.6–v1.5.8 **не прикладывали**
   `SHA256SUMS` (ошибка упаковки, исправлена в v1.5.9).
2. **`digest: sha256:<hex>` из GitHub Releases API** для того же owner/repo/тега —
   тот же корень доверия, что и тарбол; извлекается через `awk` (без зависимости от
   `jq`). Используется автоматически, если ассет `SHA256SUMS` отсутствует или не
   содержит нужный файл.
3. **Если нет ни одного источника — отказ.** Обновление отклоняется **до** замены
   бинаря; помощник никогда не ставит непроверенный бинарь.

Для зеркала (задан `SKYGATE_UPDATE_BASE_URL`) шага 2 не существует: зеркало
**обязано** публиковать `SHA256SUMS`, иначе обновление падает.

### 5.5 Автоматический откат и осознанный откат

* **Автоматический:** любой сбой после замены (сервис не стартует, `/healthz` не
  показывает целевую метку, таймаут) восстанавливает `skygate.prev`,
  перезапускает сервис, проверяет, что он отвечает, и пишет
  `result.status=rolled_back`. Живая проверка на эталонной VM вернула предыдущий
  бинарь **побайтово**.
* **Вручную (в пределах семейства версий):** `/admin/update` → **Откатить
  сейчас**. На нативной установке это повторный запуск помощника с предыдущим
  тегом релиза из состояния задачи.
* **Вручную (по шагам):** страница всегда рендерит списки ручных команд
  обновления/отката для вашего вида установки (`internal/update/manual.go`) —
  копируйте и адаптируйте; имена ассетов сверяйте со страницей релиза (см.
  известный дефект в [§10](#10-известные-пробелы-и-замечания-по-версиям)).

### 5.6 Особенности bare и OpenRC

* **OpenRC (Alpine)** — systemd path-юнита нет, поэтому установщик кладёт узкое
  правило `/etc/sudoers.d/skygate-update`, а сервис запускает помощника командой
  `setsid sudo -n <applier>`; перезапуск — `rc-service skygate restart`
  (`MODE=openrc`, с запасным `start`). `/etc/conf.d/skygate` экспортирует
  `SKYGATE_INSTALL_KIND=openrc`, `SKYGATE_UPDATE_STATE_PATH` и
  `SKYGATE_UPDATE_DIR`, чтобы страница знала платформу без догадок.
* **Bare** — супервизора нет: `MODE=bare` останавливает записанный PID и запускает
  процесс заново командой `SKYGATE_UPDATE_BARE_START`. Если ключ пуст, запустите
  процесс сами и проверьте `/healthz`.
* Во всех трёх режимах `migrate-only` выполняется от имени сервисного пользователя
  **до** замены, поэтому неприменимая миграция отменяет обновление, оставляя
  старый бинарь на месте.

## 6. Ручное обновление

Используйте, когда автоматический путь недоступен (нет сессии администратора,
изолированная сеть, Windows или сломанный бинарь). Всегда делайте бэкап БД.

### 6.1 Docker compose (из исходников)

```bash
cd /path/to/skygate
sudo docker compose stop skygate                      # корректный WAL-flush для SQLite
git remote set-url origin https://github.com/BarsSky/skygate.git
git fetch --tags --prune --force
git checkout v1.5.9
sudo chown -R "$(id -un)":"$(id -gn)" data/ts/        # tailscaled в контейнере пишет от root
sudo docker compose build skygate
sudo docker run --rm --volumes-from skygate skygate-skygate:latest /app/skygate migrate-only
sudo docker compose up -d --force-recreate --no-deps skygate
until curl -fsS http://127.0.0.1:8080/healthz | grep -q '1.5.9'; do sleep 3; done
```

`migrate-only` — это **подкоманда**, а не флаг: `--migrate-only` печатает
`unknown command`.

### 6.2 Docker compose (готовый образ)

То же, что [§4.2](#42-готовый-образ): правим `SKYGATE_IMAGE`, затем `pull` +
`up -d --force-recreate --no-deps skygate`. Откат — вернуть тег назад.

### 6.3 Нативный systemd

```bash
TAG=v1.5.9; ARCH=linux-amd64; BASE=https://github.com/BarsSky/skygate/releases/download/$TAG
cd /tmp
curl -fsSLO $BASE/skygate-$TAG-$ARCH.tar.gz
curl -fsSLO $BASE/SHA256SUMS && sha256sum -c --ignore-missing SHA256SUMS
tar -xzf skygate-$TAG-$ARCH.tar.gz
sudo systemctl stop skygate
sudo cp -p /usr/local/bin/skygate /usr/local/bin/skygate.prev        # цель отката
sudo env $(grep -v '^#' /etc/skygate/skygate.env | xargs) ./skygate migrate-only
sudo install -m 0755 skygate /usr/local/bin/skygate
sudo systemctl start skygate
systemctl is-active skygate && curl -fsS http://127.0.0.1:8080/healthz
```

Если после цикла падений юнит отказывается стартовать:
`sudo systemctl reset-failed skygate` (systemd держит состояние failed и не
перезапускает такой юнит).

### 6.4 Нативный OpenRC (Alpine)

Всё то же, но вместо `systemctl` — `rc-service skygate stop|start`, а env-файл
подключается через `/etc/conf.d/skygate`.

### 6.5 Голый бинарь

```bash
kill -TERM "$(pidof skygate)"                 # или остановка вашим супервизором
cp -p skygate skygate.prev
# скачивание и проверка — как в §6.3, затем:
./skygate.<new> migrate-only
mv skygate.<new> skygate && chmod +x skygate   # атомарный rename
nohup ./skygate >> skygate.log 2>&1 &         # или supervisorctl start skygate
until curl -fsS http://127.0.0.1:8080/healthz | grep -q '1.5.9'; do sleep 2; done
```

### 6.6 Windows

```powershell
.\deploy\Setup-Skygate-Win.ps1 -Version v1.5.9      # скачает, установит, перерегистрирует службу
Get-Service Skygate | Restart-Service
Invoke-RestMethod http://127.0.0.1:8080/healthz
```

Предыдущий `skygate.exe` не сохраняется автоматически — скопируйте его заранее,
если нужен путь отката.

## 7. Зеркала и изолированные хосты

Задайте `SKYGATE_UPDATE_BASE_URL` в **root-овом** конфиге помощника; раскладка —
`<base>/<TAG>/skygate-<TAG>-linux-amd64.tar.gz` **и** `<base>/<TAG>/SHA256SUMS`:

```bash
# /etc/skygate/update-helper.conf
SKYGATE_UPDATE_BASE_URL="https://mirror.example.com/skygate"
```

```bash
/srv/mirror/skygate/v1.5.9/skygate-v1.5.9-linux-amd64.tar.gz
/srv/mirror/skygate/v1.5.9/SHA256SUMS
```

* `https://` для всего удалённого; открытый `http://` допускается **только** для
  loopback-зеркала (`127.0.0.1`, `localhost`, `[::1]`), т.е. на том же хосте.
* `SHA256SUMS` для зеркала обязателен (fallback на digest GitHub недоступен).
  Режим зеркала включается только root-овым конфигом: скомпрометированный skygate
  не может перенаправить загрузку.
* Изолированным хостам стоит также выставить `SKYGATE_UPDATE_CHECK=false`, чтобы
  интерфейс не опрашивал GitHub; при этом можно вручную вписать целевой тег в форму
  обновления.

## 8. После обновления

```bash
curl -fsS http://127.0.0.1:8080/healthz   # ожидаем {"status":"ok","version":"…"}
curl -fsS http://127.0.0.1:8080/readyz    # db + headscale + headplane + tailscale
```

1. `/healthz` должен показывать **целевую** метку сборки, а `readyz` — `ok` по всем
   зависимостям.
2. Откройте `/admin/update`: задача должна быть в состоянии `done`, на нативных
   установках с приложенным `apply.log`.
3. Проверьте страницы, которыми пользуетесь (дашборд, `/admin/devices`, панели
   exit rules/DERP/Tailscale) и вход в систему.
4. Для релиза из этого репозитория прогоните гейт на хосте, где есть зависимости
   проверок: `bash scripts/verify_pre_deploy.sh` — должно закончиться `0 FAIL`
   (проверки, которым нужно живое состояние, рапортуют `SKIP`, а не `FAIL`).
5. Если что-то не так — откатывайтесь: на нативной установке помощник уже сделал
   это автоматически, в интерфейсе есть **Откатить сейчас**, иначе ручные шаги из
   [§6](#6-ручное-обновление).

## 9. Диагностика

| Симптом | Причина | Решение |
|---|---|---|
| Нативная кнопка **Обновить** отвечает «auto-updater for systemd not yet implemented» | бинарь старее v1.5.9 | обновиться до v1.5.9+ (или ручные шаги) |
| Страница пишет «помощник не установлен», запрос никто не забирает | установщик старше v1.5.9, либо `skygate-update.path` не включён | перезапустить `deploy/install.sh` (идемпотентен), затем `systemctl status skygate-update.path` |
| Задача висит «ждём привилегированный помощник» дольше 5 минут | помощник упал, не записав вердикт, или path-юнит не сработал | `journalctl -u skygate-update -n 200`, `tail <data_dir>/update/apply.log` |
| `could not verify … (no SHA256SUMS asset and no GitHub asset digest)` | у релиза нет контрольных сумм или исчерпан лимит GitHub API | использовать ассеты v1.5.9+, задать `SKYGATE_UPDATE_GITHUB_TOKEN` или зеркало с `SHA256SUMS` |
| `SHA256 mismatch` | битая загрузка или зеркало не совпадает с релизом | перекачать; починить зеркало (никогда не отключать проверку) |
| `target "…" is not a release tag` | в форму попала метка git-describe или «голый» SHA | указать настоящий тег (`v1.5.9`); для сборки из коммита — ручные шаги |
| Обновление прервано, сервис на старой версии, `result.status=rolled_back` | новый бинарь запустился, но `/healthz` не показал целевую метку | смотреть `apply.log`; старый бинарь уже возвращён — это штатная защита |
| Обновление прервано **до** замены с ошибкой миграции | БД не мигрируется (например SQLite на релизе до v1.5.9) | перейти на совместимый релиз; старый бинарь не заменялся |
| `systemctl restart` отказывается после цикла падений | юнит в состоянии `failed` | `sudo systemctl reset-failed skygate` |
| `docker compose pull` → `denied` / `no matching manifest for linux/amd64` | реестр заблокирован (нужна локальная сборка) или тег только под ARM | путь со сборкой из исходников либо Go-тарбол на ARM |
| Обновление по расписанию не срабатывает | вид установки нативный (планировщик их пропускает) | обновляться кнопкой **Обновить** вручную или держать Docker |
| Значения `.env` игнорируются при `docker compose -f …` из другого каталога | интерполяция зависит от CWD | перейти в каталог проекта или передать `--env-file` |

## 10. Известные пробелы и замечания по версиям

* **v1.5.8 и старше на SQLite не работают вообще** (`duplicate column name:
  user_name` на миграции v44, на новой и на существующей БД). Нативным хостам на
  SQLite нужен v1.5.9+; шаг миграции до замены бинаря как раз не даёт «окирпичить»
  установку.
* **`SHA256SUMS` прикладывается к релизам только с v1.5.9.** Старые релизы
  проверяются автоматически через digest GitHub; зеркало этим fallback
  воспользоваться не может.
* **Встроенные списки ручных команд** (`internal/update/manual.go`) всё ещё
  ссылаются на исторические имена ассетов `skygate-linux-amd64` / `….sha256`,
  которых текущий релизный конвейер **не публикует** (он публикует
  `skygate-<TAG>-linux-amd64.tar.gz` + `SHA256SUMS`). Берите команды из
  [§6](#6-ручное-обновление) этого документа и сверяйтесь со страницей релиза.
  *(Заведено как дефект документации.)*
* **Docker-образ только linux/amd64** — это осознанное решение; Go-тарболы
  покрывают linux/darwin × amd64/arm64 и windows-amd64.
* **Нативные установки никогда не обновляются сами** — планировщик только для
  Docker, а `SKYGATE_AUTO_UPDATE_ENABLED` управляет лишь показом кнопки применения.
* **Неавторизованные проверки обновлений упираются в лимит GitHub**; задайте
  `SKYGATE_GITHUB_TOKEN` (5000/ч), если проверяете часто.
