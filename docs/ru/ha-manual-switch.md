# Ручное переключение между двумя копиями

Это **запланированный** вариант переключения: оператор решает, что хост B принимает нагрузку,
гасит A, поднимает B и переводит публичные имена на B. Это не путь elector'а (тот срабатывает сам
при пропущенном heartbeat), а отрепетированный перевод — и у каждого шага ниже есть причина.

Полная версия с пояснениями — в [`../ha.md`](../ha.md) §6.4 (EN). Здесь — порядок действий.

## Два правила, без которых остальное бессмысленно

1. **Никогда два headscale с одним noise-ключом и два skygate с одним токеном Telegram
   одновременно.** Они дерутся: `getUpdates` начнёт отвечать `409 Conflict` обоим попеременно, а
   в tailnet окажется два сервера с одной личностью. Поэтому порядок — **сначала остановить A,
   потом запустить B**, и никогда наоборот.
2. **Переключение DNS ограничено TTL, а не вызовом API.** Если A-запись кэшируется на 24 ч
   (`86400`), клиенты, разрешившие имя до переключения, будут ходить на СТАРЫЙ адрес до суток.
   Поэтому TTL опускают до `300` **за сутки до** переключения.

## Шаг 0. За сутки — снизить TTL

```bash
# На хосте, где есть креды регистратора (см. шаг 0.1). Сначала --dry-run: печатает before/after и
# ничего не пишет.
skygate dns-set-a --name=skygate,head,derp --ip=<ТЕКУЩИЙ публичный IP> --ttl=300 --dry-run
skygate dns-set-a --name=skygate,head,derp --ip=<ТЕКУЩИЙ публичный IP> --ttl=300
```

Команда сохраняет адрес и меняет только TTL, после записи перечитывает зону и отказывается
сообщать об успехе, если регистратор отдаёт другой адрес.

## Шаг 0.1. Креды для DNS-половины

**Провайдер — это выбор (B473).** Карточка на `/admin/ha` («Внешний DNS (провайдер)») рисует схему
полей выбранного провайдера, поэтому штатный адаптер reg.ru и будущие Cloudflare (API-токен) или
RFC 2136 (TSIG-ключ) — одна и та же форма: `<select>` перечисляет всех провайдеров из реестра, и выбор
раскрывает поля именно его. Возможности провайдера видны заранее — значками: провайдер без TXT
говорит об этом до попытки, а не падает во время DNS-01.

Креды хранятся **строками, по одной на пару `(провайдер, зона)`**, в таблице `dns_provider_creds`
(v0.84, обе цепочки миграций). Поля конкретного провайдера лежат одним шифртекстом AES-256-GCM
(`fields_enc`, ключ `SKYGATE_SECRET_KEY`), поэтому добавление провайдера не требует миграции — только
адаптер и схема полей в `internal/dns/registry_b473.go`. Прежняя пятёрка ключей `ha.dns.*`
**импортируется один раз** в такую строку (флаг `ha.dns.migrated`), так что обновление сохраняет
креды, которыми инсталляция уже пользуется, и ничего не нужно вводить заново. Активная строка
запоминается в `dns.active_id`; если указателя нет, берётся первая включённая строка.

**Как добавить провайдера** — три файла и никакой конфигурации:

1. адаптер, реализующий `dns.Provider` (`Capabilities`, `SetTTL`, `ListRecords`, `CreateTXT`,
   `DeleteTXT` + get/update/test) — на то, чего он действительно не умеет, возвращается
   `dns.ErrUnsupported`;
2. одна `Spec` в реестре (имя, label, `NeedsZone`, поля с `LabelKey`/`HelpKey`/`Kind`, `Caps`) —
   label'ы это **ключи i18n**, поэтому нужны в обоих каталогах;
3. один `case` в `dns.BuildProvider`, собирающий провайдера из `BuildDeps.Row`.

Ни миграции, ни правки шаблона, ни нового ключа настроек.

Штатный провайдер — API reg.ru (B468): логин, **альтернативный пароль** из раздела API в аккаунте (не
пароль аккаунта) и зона.

**Два входа, одно хранилище.** Форма в панели `/admin/ha` («Внешний DNS (провайдер)») и CLI ниже
пишут одни и те же зашифрованные строки — достаточно любого из них.

*Панель:* `/admin/ha` → «Внешний DNS (провайдер)» → заполнить **Зону** (`example.com`), **Логин**,
**Альтернативный пароль** → **Сохранить**. Кнопка **«Прочитать зону»** (только чтение) печатает
текущую A/AAAA-запись для перечисленных имён, а **«Тест соединения»** отвечает в баннере: `ok` с
задержкой либо причина (авторизация / сеть / креды не заполнены). Обе кнопки работают с тем
провайдером, чья строка **активна**, — сохранение reg.ru делает активным именно его.

**Зона — это домен, которым управляет регистратор, а не сайт регистратора и не имя хоста.** Для
`skygate.example.com` зона — `example.com` (поле нормализуется при сохранении: вставленная ссылка
`https://example.com/` или `EXAMPLE.COM.` станет `example.com`). Если вписать туда домен самого
регистратора (живая ошибка была `reg.ru`), это никуда не указывает: API ответит, что у аккаунта нет
такой зоны, и это покажут и «Тест соединения», и «Прочитать зону».

**«Прочитать зону» хочет поддомены, а не имена хостов**: при зоне `example.com` перечислите
`skygate,derp,head`.

Поле **клиентского сертификата** нужно только провайдерам с mTLS. **reg.ru — нет**: оставьте его
пустым. Сохранённый сертификат заставит клиент предъявлять его при подключении, и API это отвергнет.
Поле принадлежит схеме провайдера, поэтому провайдер, которому mTLS действительно нужен, просто
объявляет его обязательным.

**Сначала подхватите окружение юнита (путь через CLI).** CLI-глаголы читают те же переменные, что
сервис получает из `EnvironmentFile=`; в обычной оболочке их нет, и первый симптом — непонятное
`config: HEADSCALE_API_KEY is required`. Проверьте заодно, что файл — чистый UTF-8/LF: BOM или CRLF
(на одном хосте было и то, и другое) ломают `set -a; . env` сообщениями «syntax error near
unexpected token» / «$'\r': command not found», хотя сам юнит при этом здоров.

```bash
set -a; . /etc/skygate/skygate.env; set +a     # от root
# если точка выше падает: убрать BOM (`tail -c +4`) и CR (`tr -d '\r'`), сохранив бэкап

skygate regapi-credentials set --login=<логин> --password='<альт. пароль>' --zone=<example.com>
skygate regapi-credentials show        # с маскированием
skygate regapi-credentials test        # ТОЛЬКО ЧТЕНИЕ: читает зону, печатает число записей
skygate dns-records --name=skygate     # что DNS отвечает прямо сейчас
```

Без кредов глаголы не гадают, а отвечают
`credentials are incomplete (login=false password=false zone=false) — run skygate regapi-credentials set …`.

Вместо сохранённых строк работают `SKYGATE_DNS_REGAPI_LOGIN` / `_PASSWORD` / `_ZONE` — чтобы
переключение можно было запустить с хоста, где этих строк в БД нет. `SKYGATE_REGAPI_BASE_URL`
переопределяет endpoint (тестовый CA или прокси); штатный — `https://api.reg.ru/api/regru2`.

## Шаг 1. Предполётная проверка на B

```bash
curl -fsS http://127.0.0.1:8080/healthz            # {"build":"vX.Y.Z+<sha>"} — та же версия, что на A
curl -fsS http://127.0.0.1:8080/readyz | grep -o '"healthy":[a-z]*'   # healthy:true
journalctl -u skygate -n 40 --no-pager | grep 'READ-ONLY COPY'
#   ДОЛЖНО быть пусто на B: копия запускается с SKYGATE_READONLY_COPY=1 и не публикует, не
#   алертит и не переключает DNS. Снимите флаг в /etc/skygate/skygate.env ДО переключения (и
#   перезапустите), иначе B будет отдавать только панель.
```

### Шаг 1.1. B должен иметь право SSH до relay'ев — это решает ACL, а не sshd

skygate толкает `--advertise-routes` на каждый relay по Tailscale SSH, поэтому `src` в
SSH-правиле обязан называть тег узла B. Генератор включает все `tag:dev-infra-skygate*` (и
намеренно исключает их из catch-all exit-узлов), то есть резервный хост должен называться
`skygate-*`. Узел с другим именем (например VPS `vps2` с `tag:dev-infra-vps2`) получает отказ:

```
tailscale: tailnet policy does not permit you to SSH to this node
```

Варианты: дать B идентичность `skygate-standby` (переименовать и дать infra-backfill
проставить тег) **или** добавить его тег в SSH-правило руками. Проверить с B до переключения:

```bash
sudo -u skygate ssh -i <ключ> -o BatchMode=yes -o ConnectTimeout=8 root@<tailnet-IP relay> 'echo OK'
# для relay, у которого sshd не на 22 — то же с -p <порт>
```

## Шаг 2. Остановить A (именно первым)

```bash
# native:  systemctl stop skygate ; systemctl stop headscale
# docker:  cd /home/<user>/skygate && docker compose stop skygate headscale
ssh <A> 'systemctl stop skygate headscale'
ssh <A> 'systemctl is-active skygate headscale'     # оба должны ответить "inactive"
```

## Шаг 3. Запустить B

```bash
ssh <B> 'systemctl start skygate headscale'
ssh <B> 'curl -fsS http://127.0.0.1:8080/healthz && curl -fsS http://127.0.0.1:8080/readyz'
```

## Шаг 4. Перевести публичные имена на адрес B

```bash
skygate dns-set-a --name=skygate,head,derp --ip=<публичный IP B> --dry-run   # проверить
skygate dns-set-a --name=skygate,head,derp --ip=<публичный IP B>
#   печатает before ... / after ... / "written and verified by reading the zone back"
#   пишет одну строку аудита: dns.manual_switch (зона, имена, на какой адрес, TTL, когда)
```

## Шаг 5. Проверка снаружи (через терминатор, не с самого хоста)

```bash
dig +short skygate.example.com                        # IP хоста B
curl -fsS https://skygate.example.com/healthz         # сборка, которую отдаёт B
curl -fsS https://head.example.com/health             # headscale отвечает
```

## Шаг 6. Что теперь с A

Держите его **остановленным** — это цель для отката. Запускать A, пока B обслуживает tailnet,
нельзя: два headscale с одним ключом.

## Откат

```bash
# 1) остановить B, 2) запустить A, 3) вернуть DNS, 4) перепроверить (те же команды в обратную сторону)
ssh <B> 'systemctl stop skygate headscale'
ssh <A> 'systemctl start skygate headscale'
skygate dns-set-a --name=skygate,head,derp --ip=<публичный IP A>
dig +short skygate.example.com
```

TTL, снижённый на шаге 0, действует и здесь: откат виден настолько быстро, насколько позволяет
TTL.

## Чего эта процедура СОЗНАТЕЛЬНО не делает

* **Не копирует данные.** A и B должны делить базу (PG-стриминг), либо B — снимок, актуальность
  которого оператор принял. Восстановленная копия отдаёт панель из своего файла, и её данные не
  двигаются; флаг read-only — то, что не даёт ей врать (B465).
* **Не мешает узлам старого headscale переподключиться**: если A вернётся с тем же noise-ключом,
  его узлы подключатся к нему. Поэтому A остаётся остановленным.
* **Не трогает прокси — и у B есть два допустимых вида**, выберите до переключения:
  * **B сам терминирует TLS** (так устроен резервный VPS: у него свой публичный адрес, прокси ему не
    нужен). Тогда DNS-запись переезжает на B, а терминатор локальный — Caddy с автоматическим
    Let's Encrypt, см. [`../https.md`](../https.md) §2.5.
  * **Внешний терминатор остаётся у A** (так устроена текущая agent-VM: NPM на отдельном хосте в
    LAN, «под неё» и организован). Тогда DNS-запись может вообще не меняться — правится только
    `upstream` в прокси на адрес B, см. [`../https.md`](../https.md) §2.2. Это же и способ
    отрепетировать переключение без простоя: сертификат впереди не меняется.

  Смешать два вида нельзя: публичное имя окажется направленным на хост, который ничего не отвечает
  на 443 — поэтому шаг 4 идёт после шага 3, а адрес, который назовёт запись, обязан уже обслуживать.

## База на B: SQLite сейчас, PostgreSQL позже

Резервный хост поднимается на **SQLite**: `SKYGATE_DB=sqlite:/var/lib/skygate/skygate.db` (WAL,
файл в каталоге данных юнита). PostgreSQL подключается позже — он «тяжёлый» для VPS с 1 vCPU и
1.9 ГБ RAM; переезд делается сменой DSN по
[`../backup-restore-and-migration.md`](../backup-restore-and-migration.md), и форма TLS от выбора
базы не зависит. Пока база — SQLite, помните: **свежесть данных на B — ваша ответственность**
(см. первый пункт выше): перед переключением нужен свежий дамп/restore, иначе теряются все
изменения между снимком и переключением.
