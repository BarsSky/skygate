# Префикс, relay и устройство — почему одна площадка не открывается

> English original: [`docs/acl-rules-reference.md`](../acl-rules-reference.md) §7
> («One site stops opening on ONE device»).

Симптом: сайт (чаще всего Discord, Cloudflare-фронт, любой CDN)
перестал открываться **на одном устройстве** и только на нём.
Остальные устройства работают, relay «онлайн», DNS отдаёт адрес,
`ping` до адреса идёт. Это не DNS и не сайт.

## Причина: `via` — это фильтр, а не подсказка

С B276 каждый префикс в ACL идёт с `via=[<тот relay, который
владеет этим префиксом>]`. `via` в headscale — **разрешение**, а не
маршрутизация: устройство, чей трафик выходит через ДРУГОЙ relay, не
имеет права пользоваться этим префиксом вообще. Клиент просто
молча ждёт таймаут, в логах ничего нет.

Решение о владельце принимают две вещи, и они хранятся в разных
местах:

| Вопрос | Где ответ |
|---|---|
| Какой relay обслуживает `104.16.0.0/12`? | таблица `prefix_owner` |
| Через какой relay выходит МОЁ устройство? | exit-node устройства + строки `device_rules` |

Пока эти половины согласованы, всё работает. Когда устройство
переключили на другой relay (или его правила «дрейфовали» на другой
relay), префиксы остались за старым — и устройство потеряло
площадку.

## Диагностика (только чтение)

```bash
# 1. кто владеет префиксом и был ли это ручной пин
skygate prefix-owner --list --prefix 104.16.0.0/12,162.158.0.0/15

# 2. какие префиксы за конкретным relay
skygate prefix-owner --list --relay emilia

# 3. правила самого устройства — в панели
#    /admin/exit-rules?device=<hostname>
```

Полезно посмотреть и `headscale nodes list` вместе с
`/admin/exit-nodes`: у каждой exit-узлы видно, какие маршруты
одобрены (`approved`), и какой relay считается предпочтительным для
каждого устройства.

## Исправление

Пин префиксов **и** пере-применение ACL — одной командой (пин сам по
себе пишет только строку в БД; `prefixowner.Assign` найденный
`manual` не перезаписывает и «изменения» не видит, поэтому без
пере-применения политика останется старой):

```bash
# префиксы — на тот relay, через который устройство реально выходит
skygate prefix-owner --relay=karolina \
        --prefix=104.16.0.0/12,162.158.0.0/15 --apply

# и/или переписать САМИ правила, которые этот префикс заявляют
skygate prefix-owner --rules-to=karolina --device=basic \
        --target=104.16.0.0/12,162.158.0.0/15 --apply
```

Без `--apply` обе команды только печатают план. Каждая запись
пишется в audit с теми же именами действий, что и кнопки панели
(`prefix_owner_pin`, `device_rule_relay_move`). Команда с пином
заканчивается применением политики — причём в **той схеме, которую
headscale реально обслуживает** (`acls[]` или `grants[]`+`via`),
поэтому запуск из «голого» шелла не может незаметно заменить
`grants[]`-политику на legacy.

## Три правила, которые нельзя нарушать

1. **Один префикс — один relay.** headscale отдаёт префикс ровно с
   одного relay; устройство на другом relay этот префикс теряет.
   «Оба сразу» не бывает.
2. **Пин влияет на всех.** Если устройства второго relay тоже ходят
   на эту площадку, после пина им нужен тот же relay. Смотрите
   «preferred» у каждого устройства на `/admin/exit-nodes`.
3. **`manual` переживает пересчёт**, но упавший relay теряет свои
   префиксы — мёртвый узел трафик не носит. Вернуть решение движку:
   `skygate prefix-owner --auto --prefix … --apply`.

## Если ничего не помогло

- `headscale nodes list` — у устройства вообще есть тег
  `tag:dev-<user>-<host>`? Без тега device-правило не сработает
  (B272).
- `/admin/exit-nodes` — префикс есть в `approved` у владельца?
- Политика в headscale совпадает с той, что генерирует skygate?
  Страница `/admin/exit-nodes` показывает это отдельным флагом и
  имеет кнопку resync.
- Старая ошибка схемы (B470): если policy применяется с `500 …
  invalid port range format`, значит собран legacy `acls[]` с голым
  тегом в `dst` — обновите skygate.
