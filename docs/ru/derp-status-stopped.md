# «DERPER SERVICE stopped» на живом релее — и 136 мс у релея на той же машине

## Симптом

`/admin/derp` показывает **DERPER SERVICE: stopped**, при этом плитка `DERP SOCKET :443`
говорит «TCP слушает», клиенты ходят через этот релей (`relay "mow"`), а STUN отвечает за
2 мс. Задержка того же релея показывается как 136 мс (или любой другой «интернетный»
показатель), хотя derper живёт на той же машине, что skygate и headscale.

## Причина (измерено 2026-11-15)

Две независимые вещи, обе в проверке живости:

1. **Неверный токен upgrade'а.** Проба слала `Upgrade: websocket`. Сам derper отвечает
   на такой запрос `101` только когда запрос приходит к нему напрямую; если перед ним
   стоит прокси, ответ даёт прокси:

   ```
   curl --http1.1 -H 'Upgrade: DERP'      https://derp.example.com/derp → 101
   curl --http1.1 -H 'Upgrade: websocket' https://derp.example.com/derp → 200
   curl --http2  -H 'Upgrade: DERP'       https://derp.example.com/derp → 426
   ```

   Проба ждёт ровно `101`, поэтому через Caddy она всегда видела 200 (а при
   согласованном h2 — 426) и рисовала «stopped».

2. **Адрес пробы был старый.** В `global_settings` остался `derp.probe_host` с публичным
   IP **предыдущего** хоста — проба и health-обход ходили туда, отсюда и 136 мс
   «у релея на той же машине».

## Что делать

Обновиться до релиза с B478 (или новее) — проба теперь шлёт `Upgrade: DERP` и
принудительно говорит по HTTP/1.1.

Проверить конфигурацию релея (без релиза это делается руками):

```sql
-- адрес, по которому проба ДОЛЖНА идти (для релея на том же хосте — loopback)
update global_settings set value='127.0.0.1' where key='derp.probe_host';
-- и сам эндпоинт, который объявляется клиентам (порт derper'а, а не прокси)
update derp_relays set url='https://derp.example.com:8443' where hostname='derp.example.com';
```

После смены `derp_relays.url` **перезапустить headscale**: он читает derpmap только на
старте. Проверка:

```bash
curl -s http://127.0.0.1:8080/admin/derp/relays/derpmap.json   # DERPPort должен совпасть
tailscale netcheck | grep -A1 DERP                              # у своего региона должна быть задержка
```

Почему прямой порт релея (8443 в примере) лучше прокси на 443: DERP — это HTTP/1.1
upgrade, а Caddy предлагает ALPN h2, и клиент, согласовавший h2, upgrade выполнить не
может (сервер отвечает `426`). Из-за этого соединение через релей «плавает»: иногда
работает, иногда нет. Прямой порт derper'а говорит только по HTTP/1.1, и этой
неоднозначности нет.

## Как это проверяется в дереве

* `internal/feature/admin/derp_b478_test.go` — проба обязана слать `Upgrade: DERP`,
  говорить по HTTP/1.1, считать живым только `101` и уважать пин адреса
  (`SKYGATE_DERP_PROBE_HOST` / `derp.probe_host`).
* `scripts/check_b478_derp_probe_truth.sh` — контракт на токен, принудительный h1,
  распознавание 101, пин адреса, тесты, дискриминатор пре-B478 формы, регистрация в
  гейте и документация EN+RU.

## B478.1 — пин адреса игнорировался, и «локальный» релей мерился как интернет

После первого исправления на том же хосте: `derp.probe_host = 127.0.0.1`, а строка
health для региона 900 всё ещё показывала **185-221 мс**, при том что локальное
TLS-рукопожатие с `127.0.0.1:8443` занимает 10-40 мс. Причина: подсказка применялась
только когда имя релея резолвится в loopback (правило B296 для контейнера), а релей,
до которого должны доходить клиенты, объявляет имя, резолвящееся в **публичный**
адрес — поэтому пин не срабатывал, и проба уходила в интернет и возвращалась
(Hairpin).

Исправлено: явный адрес пробы (`derp.probe_host` / `SKYGATE_DERP_PROBE_HOST`)
используется **безусловно**, и в health-обходе (`internal/derphealth/probe.go`), и в
пробе самой страницы (`derpReachabilityCandidates` — пин теперь первый в любом
случае). Если адрес не задан, поведение не меняется.
