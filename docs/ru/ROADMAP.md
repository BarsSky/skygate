## 1. Как пользоваться этим файлом

* У элементов есть тег: `TD-n` (технический долг), `BL-n` (заблокировано),
  `RR-n` (элемент дорожной карты). У работ над фичами дополнительно есть
  **идентификатор B-блока** (`B262`, `B-mod-core`, …): однострочное описание
  каждого блока — в индексе блоков внутри `AGENTS.md`, а устойчивые выводы — в
  `LESSONS.md`.
* Ревизия после каждого релиза: перенести выпущенное в раздел «выпущено» тем же
  коммитом, что и релизная бухгалтерия, и перетегировать то, что оператор
  переставил по приоритету.
* Новый элемент добавляется сюда **и** (если это реальная работа) как запись
  B-блока в `AGENTS.md` плюс контракт `scripts/check_bNNN_*.sh`,
  зарегистрированный в `scripts/verify_pre_deploy.sh`.
* Всё, чего нет здесь и нет в индексе, либо выпущено (история git), либо
  осознанно отброшено (см. §8).

## 3. Что выпущено в цикле v1.5.9

По одной строке; обоснования и режимы отказа — в `docs/LESSONS.md`, контракты — в
соответствующих `scripts/check_b*.sh`.

| Блок | Что сделано |
|---|---|
| **B261** | Нативное самообновление (systemd / OpenRC / bare) через root-овый привилегированный помощник: файл запроса только с данными → path/service-юнит → помощник делает backup, скачивание, проверку SHA256, `migrate-only` **до** замены, атомарную замену бинаря, перезапуск, опрос `/healthz` на **метку сборки** цели и откат при сбое. Модель безопасности сохранена (skygate не работает от root). |
| **B261.1** | `SKYGATE_DB=sqlite:/path` вообще не открывался — форма DSN, которую пишет сам установщик, делала любую нативную SQLite-установку нерабочей. Схема `sqlite:` срезается в `openSQLite` + тест с реальным открытием файла. |
| **B261.2** | Резерв проверки целостности: если у релиза нет ассета `SHA256SUMS`, помощник проверяет по `digest: sha256:<hex>` из GitHub Releases API; при отсутствии обоих источников — отказ. |
| **B261.3** | `mktemp -d` (0700) не давал выполнить `migrate-only` от сервисного пользователя → рабочий каталог теперь `0755` (содержимое уже проверено по SHA256). |
| **B261.4** | `--migrate-only` не флаг: подкоманда называется `migrate-only`; исправлено и в помощнике, и в ручных шагах в интерфейсе. |
| **B261.5** | Поддержка зеркала `SKYGATE_UPDATE_BASE_URL` (root-овый конфиг, https или loopback http, `SHA256SUMS` обязателен) для изолированных хостов. |
| **B262** | OpenRC/Alpine как полноценный `InstallKind` (маркер `/run/openrc`, перезапуск `rc-service`, sudoers-триггер, вид установки в `/etc/conf.d/skygate`) **и** отсутствовавший ассет `SHA256SUMS` (workflow качал артефакт в путь, чьё имя совпадало с единственным файлом, поэтому flatten прикладывал каталог → релизы v1.5.6–v1.5.8 вышли без контрольных сумм). |

## 4. Что дальше (кандидаты в v1.6.0, примерный порядок)

1. **Проверка релизного конвейера (RR-1)** — в CI утверждать, что у каждого релиза
   есть **файл** `SHA256SUMS` со всеми загруженными ассетами и что тег ghcr в
   нижнем регистре. Закрывает класс дефектов, породивших B262 и B237.24.
2. **Починить ручные шаги в интерфейсе (RR-2)** — `internal/update/manual.go` всё
   ещё печатает исторические имена ассетов `skygate-linux-amd64` / `.sha256`,
   которых конвейер не публикует; нужно
   `skygate-<TAG>-<arch>.tar.gz` + `SHA256SUMS` (контракт сейчас фиксирует
   устаревшую строку, так что тест меняется вместе с кодом).
3. **Упрочнение помощника (RR-3)** — `systemctl reset-failed <service>` перед
   перезапуском (замечено на живом прогоне отката: упавший юнит отказывается
   стартовать, и помощник рапортует ложный сбой).
4. **Гигиена чеков и скиллов (RR-4)** — каталог B-чеков большой и частично
   дублируется; объединить дубликаты и сохранить правило `SKIP`-вместо-`FAIL` для
   всего, что требует живого состояния (docker, БД, VM).
5. **Паритет SQLite ↔ PostgreSQL (TD-17)** — держать обе цепочки миграций и оба
   диалектных помощника синхронно; добавить проверку паритета, которая падает,
   если изменение схемы попало только в одну цепочку (работа цикла v1.5.9 вокруг
   `execSQLiteDDL` — это фундамент).
6. **Полировка бэкапов (TD-4 + TD-12)** — назначение S3 в `/admin/backup/config`
   и еженедельная авто-проверка (восстановить свежий бэкап во временный каталог,
   прогнать проверку целостности, оповестить при сбое).

### 5.1 Живые контракты, падающие на эталонном хосте (2026-09-18)

Полный прогон гейта на эталонном хосте теперь заканчивается **PASS=307 / 6 строк FAIL =
3 живых чека / 1 SKIP** (`scripts/verify_pre_deploy.sh`, проверочный прогон 2026-09-18 после
исправления контракта B188.2). Ни один из трёх не читает документацию — каждый опрашивает
живую БД, политику headscale или сеть.
Собранные на хосте доказательства:

* **`node_owner_map` (B243).** Живые пользователи headscale: `1 skyadmin`, `8 michail`,
  `11 guest`, `12 daniil`, `85 infra`. Четыре строки указывают не туда:
  `node_id 6/29/31 → headscale_user_id=6 (michail)` — теперь `michail` это **8**, то есть
  строки перелинковываются; и `node_id 45 → 2147455555 (tagged-devices)` — сентинел
  переполнения int, чистый остаток.
  → `UPDATE node_owner_map SET headscale_user_id=8 WHERE headscale_user_id=6;` и
  `DELETE FROM node_owner_map WHERE headscale_user_id=2147455555;`
  **Почему это не самоизлечивается:** часовой реконсилятор (B237.18) здоров — в его
  audit-строке `ok:5, linked:0, relinked:0, orphans:0`, а `portal_users.headscale_user_id`
  верен (`michail=8`) — но он сверяет **только** `portal_users`, поэтому у
  `node_owner_map.headscale_user_id` реконсиляции нет и старые ID остаются.
  → шаг 5A скрипта починки либо (как будущая фича) расширение реконсилятора на
  `node_owner_map`, чтобы класс закрывался сам.
* **Дрейф ACL (B188.2/B188.3/B-mod-tag-owners-coverage).** Две разные причины, обе понятны:
  * **B188.2/B188.3 — дефект чека, исправлен в коде (2026-09-18).** Контракт T требовал
    один «замороженный» CIDR (`h-rule-64-233-164-91-32`, youtube `/32` на момент написания
    B188.2) с `via=[emilia]`. Доменные правила периодически перерезолвятся, поэтому после
    смены DNS алиас исчез, а поведение всегда было корректным: на эталонном хосте 30
    per-CIDR грантов с пином `tag:dev-infra-emilia` и правильно НЕ пинённый catch-all.
    Теперь T проверяет поведение (≥1 пинённый per-CIDR `h-rule-*`), а S и W по-прежнему
    следят за непинёным catch-all. Оба контракта проходят (B188.2 19/0, B188.3 12/0).
  * **B-mod-tag-owners-coverage — устаревшая политика.** В живой политике `tagOwners` всё
    ещё содержит `tag:dev-skyadmin-emilia`, `tag:dev-skyadmin-skygate-host-1` и
    `tag:dev-skyadmin-svyatoslava-1` (легаси-нейминг до B188), и **ни одна** строка БД на
    них не ссылается (`node_owner_map`, `device_exit_node_prefs`, `user_exit_node_prefs`,
    `device_rules` — 0), поэтому перегенерация из БД их убирает. Сама БД для B188.2
    корректна (`device_exit_node_prefs (6, basic, tag:dev-infra-emilia, via_enabled=1)` +
    правило `youtube.com`, id 189985).
    → шаг 5B скрипта починки (`skygate acl-apply`).
* **Telegram-relay (B185).** `[O] expected=ok_relay got=probe_unreachable_B185_not_live`
  — проба не достаёт relay. После исправления секретов 2026-09-18 контракт логинится
  учётными данными из `.env` и доходит до своего реального утверждения, которое
  подтверждает: сам маршрут до relay со стороны контейнера skygate недоступен — то же
  условие, что и **BL-3** (`api.telegram.org` в сети с DPI). `[P]` теперь проходит
  (60 строк discord-CDN).
* **«Дубли» `device_rules` (B183 `[J]`, информационно).** Для `exit_node=emilia`:
  106 строк, 46 различных 5-кортежей и **106 различных 6-кортежей** — лишние строки
  отличаются `parent_domain` (`cdn:cloudflare:discordapp.com` vs `…discord.gg` vs …,
  все резолвятся в `188.114.96.0/20`). Это **текущий** дизайн с 6 колонками
  (B232 + B237.23), поэтому ожидание уникальности по 5-кортежу на этом хосте
  недостижимо; `[J]` уже даёт SKIP и печатает цифры.
* **Плавающие проверки — на этом хосте закрыто.** Четыре контракта раньше падали внутри
  полного прогона и проходили при отдельном запуске через секунды (`check_b183` 11/11,
  `check_b213` 19/19, `check_b235` 22/22, `check_b237_2` 21/21) — во всех есть тяжёлый шаг
  Go (`go build ./...` или `go test` на целом пакете). Ограничение параллелизма компиляции
  (`export GOFLAGS=-p=2` в `verify_pre_deploy.sh`, переопределяется через
  `SKYGATE_GATE_GOFLAGS`) убрало весь плавающий набор в проверочном прогоне. Если
  Go-зависимый контракт снова упадёт на нагруженном хосте — первым делом смотреть этот
  параметр (общее упрочнение SKIP/retry отслеживает RR-11).

**Скрипт починки.** Обе живые проблемы упакованы в одну проверяемую команду:
`bash scripts/operator_repair_live_drift.sh` (по умолчанию — dry run) находит живой ID
headscale для `michail`, печатает точный план перелинковки/удаления, делает бэкап живой
политики (`headscale policy get`) и строк `node_owner_map`, печатает рецепт отката и
ничего не меняет без `--apply`; после применения перегенерирует ACL из БД и повторно
прогоняет четыре контракта. Dry run проверен на эталонном хосте 2026-09-18 (прочитано
13 строк, цели перелинковки `29,31,6`, сентинел `45`, бэкап политики 52 КБ, изменений нет).

## 8. Длинный хвост (осознанно вне области работ)

Отслеживается, чтобы не потерялось, **но не планируется**:

* ~2850 строк хелперов `internal/feature/*/testutil.go`, которые не вызывает ни
  один тест (TD-13) — низкий ROI; растёт естественно вместе с фичами.
* Миграция на отдельную плоскость headscale для compliance-уровня (RR-6).
* Возврат к мультиархитектурным docker-образам — осознанно отброшено в v1.5.4
  (матрица до v1.5.4 пушила один тег дважды, вторая отправка перетирала первую, и
  `:v1.5.2` остался без amd64-манифеста). Возврат требует либо одного
  `build-push-action` с обеими платформами, либо двух buildx-задач, объединяемых
  `docker imagetools create`.
* Исторические планы superpowers B-mod и рефакторингов v0.2x — удалены из дерева;
  устойчивый результат зафиксирован в `docs/internals.md` + `docs/LESSONS.md`,
  тексты — в истории git.
