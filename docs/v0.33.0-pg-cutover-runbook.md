## What "v0.33.0" means

The PG **driver + scaffolding** is already on main as of
v0.31.0 (driver abstraction + 27 PG-compatible migrations +
B11/B12/B18 catalog checks). v0.33.0 is the **actual cutover**:
the live skygate starts running on PG instead of SQLite.

This is a 4-step operator runbook. Estimated total time:
**20 minutes of work + 15 minutes of downtime**.

## Pre-requisites

- [ ] PG-staging VM is up. `SKYGATE_TEST_PG_DSN` env var
      set. `psql $DSN -c '\l'` lists the skygate DB.
- [ ] Current production skygate is on **v0.32.19+** (the
      migration integrity feature that creates the
      `applied_migrations` table).
- [ ] All verify-pre B-checks PASS on the current build.
- [ ] All verify-post R-checks PASS on the current VM.
- [ ] `deploy/backup.sh` ran within the last 1 hour (so we
      have a clean backup to fall back on).
- [ ] A 30-minute low-traffic window (operator's choice).
      The skygate admin UI will be read-only for ~15 min.

## Step 1 — Pre-cutover verification (5 min)

```bash
# On the operator's workstation:

# 1.1 — run the full pre-cutover check
cd /path/to/skygate && git checkout v0.32.19
make verify-pre          # expect 35/35 PASS (B1-B36, B8 SKIP)
make verify-post         # expect ~26 PASS, 1 SKIP (R27)

# 1.2 — confirm PG-staging is reachable
psql "$SKYGATE_TEST_PG_DSN" -c '\l'
psql "$SKYGATE_TEST_PG_DSN" -c '\dt'
# (empty result is OK; we're about to create the schema)

# 1.3 — run the PG test suite against PG-staging
SKYGATE_TEST_PG_DSN="$SKYGATE_TEST_PG_DSN" \
  go test -count=1 -timeout 60s ./internal/db/test_pg_migrations_test.go
# expect 4 PASS (roundtrip, idempotency, lock_timeout, data_mig)

# 1.4 — verify the runtime rewrite compiles under postgres tag
CGO_ENABLED=1 go build -tags postgres -o /tmp/skygate-pg ./cmd/skygate
# (the binary will NOT be deployed; we just want to confirm it builds)
```

**If any of these FAIL**: do not proceed. Fix the failure first.

## Step 2 — Rewrite runtime queries (`?` → `$N`) (5 min, can be done anytime)

This step is **not** in the maintenance window — it can be
done days before, in a separate PR, deployed and observed
on SQLite (SQLite is unaffected by the rewrite because the
`?` and `$N` placeholders are equivalent when there's no
argument:

```python
# On operator's workstation:
cd /path/to/skygate
git checkout -b feat/pg-placeholder-rewrite
python scripts/rewrite_placeholders.py \
  internal/db/queries.go \
  internal/db/audit_log.go \
  internal/db/device_rules.go \
  internal/db/exit_servers.go \
  internal/db/exit_node_health.go \
  internal/db/node_owner_map.go \
  internal/db/integrations.go \
  internal/db/personal_api_tokens.go \
  internal/db/preauth_keys.go \
  internal/db/prefs.go \
  internal/db/portal_users_controlplane.go \
  internal/db/secrets.go \
  internal/db/telegram_rate_limit.go \
  internal/db/acl_snapshots.go

# 2.1 — manual review: every INSERT OR REPLACE / INSERT OR IGNORE
# must be converted to ON CONFLICT (...) DO UPDATE / ON CONFLICT
# DO NOTHING. The script leaves TODO comments for these.
grep -rn 'INSERT OR ' internal/db/ | grep -v _test.go
# (expect zero results after manual review)

# 2.2 — manual review: strftime → EXTRACT
grep -rn "strftime" internal/db/ | grep -v _test.go
# (expect zero results)

# 2.3 — build under postgres tag
CGO_ENABLED=1 go build -tags postgres -o /tmp/skygate-pg ./cmd/skygate
go test -count=1 -short ./...        # SQLite tests still pass

git add -A
git commit -m "feat(db): rewrite placeholders ? → \$N + ON CONFLICT (v0.33.0 PG cutover prep)"
git push -u origin feat/pg-placeholder-rewrite
gh pr create --title "v0.33.0 prep: PG placeholder rewrite"
```

**Then merge the PR** (no rush — it's safe on SQLite).

## Step 3 — Cutover window (15 min downtime)

```bash
# 3.1 — put skygate in read-only mode
ssh admin@192.0.2.1
cd /home/admin/skygate
# Edit docker-compose.yml: set SKYGATE_READ_ONLY=true
# (or pass --env SKYGATE_READ_ONLY=true on the up command)
docker compose up -d --force-recreate skygate
until curl -fsS http://localhost:8080/healthz; do sleep 3; done
# /admin/exit-rules should now show a "Read-only" banner

# 3.2 — snapshot the live SQLite DB
sqlite3 /var/lib/docker/volumes/skygate-data/_data/skygate.db \
  "PRAGMA wal_checkpoint(FULL);"
sudo cp -a /var/lib/docker/volumes/skygate-data/_data/skygate.db \
  /home/admin/backups/skygate-pre-pg-$(date +%Y%m%d-%H%M%S).db
ls -lh /home/admin/backups/skygate-pre-pg-*.db

# 3.3 — dump the SQLite to a SQL file
docker run --rm \
  -v /var/lib/docker/volumes/skygate-data/_data:/from:ro \
  -v $HOME/skygate-pg-dump:/to \
  alpine:3.20 sh -c "
    apk add --no-cache sqlite &&
    sqlite3 /from/skygate.db .dump > /to/dump.sql &&
    wc -l /to/dump.sql
  "
ls -lh $HOME/skygate-pg-dump/dump.sql
# (expect ~10-50 MB depending on audit_log size)

# 3.4 — load the dump into the fresh PG database
# The dump is SQLite-flavored; we need to translate a few
# SQLite-isms to PG equivalents:
#   - AUTOINCREMENT removed (PG uses SERIAL/BIGSERIAL)
#   - "double quote" identifier quoting → standard SQL
#   - 't'/'f' booleans → true/false
#   - x'...' hex blob literals → '\x...' (PG format)
# Use a small Python script to do the translation:
python3 $HOME/skygate-pg-dump/translate_dump.py \
  --in $HOME/skygate-pg-dump/dump.sql \
  --out $HOME/skygate-pg-dump/dump.pg.sql

# Apply to fresh PG
PGPASSWORD=... psql "$SKYGATE_TEST_PG_DSN" -f $HOME/skygate-pg-dump/dump.pg.sql
PGPASSWORD=... psql "$SKYGATE_TEST_PG_DSN" -c '\dt'
# (expect ~20 tables: portal_users, exit_servers, device_rules,
#  acl_snapshots, audit_log, node_owner_map, ...)

# 3.5 — flip the DSN and restart
# Edit /home/admin/skygate/.env:
#   SKYGATE_DB_DSN=$SKYGATE_TEST_PG_DSN
# (remove the file-path line)
docker compose up -d --force-recreate skygate
until curl -fsS http://localhost:8080/healthz; do sleep 3; done
# /admin/exit-rules should now show a "PostgreSQL backend" banner

# 3.6 — turn off read-only mode
# Edit docker-compose.yml: set SKYGATE_READ_ONLY=false
docker compose up -d --force-recreate skygate
until curl -fsS http://localhost:8080/healthz; do sleep 3; done
```

## Step 4 — Post-cutover verification (10 min)

```bash
# 4.1 — verify the data round-tripped
psql "$SKYGATE_TEST_PG_DSN" -c 'SELECT COUNT(*) FROM portal_users;'
sqlite3 /home/admin/backups/skygate-pre-pg-*.db \
  "SELECT COUNT(*) FROM portal_users;"
# (expect same number, modulo any test users added in step 3.5)

# 4.2 — verify all 4 users are present
psql "$SKYGATE_TEST_PG_DSN" -c "SELECT id, username, is_admin FROM portal_users ORDER BY id;"
# (expect admin, user1, user3, user2)

# 4.3 — verify audit_log roundtripped
psql "$SKYGATE_TEST_PG_DSN" -c "SELECT COUNT(*) FROM audit_log;"
# (expect ~4670 rows on the operator's VM)

# 4.4 — verify exit_rules roundtripped
psql "$SKYGATE_TEST_PG_DSN" -c "SELECT COUNT(*) FROM device_rules;"
sqlite3 /home/admin/backups/skygate-pre-pg-*.db \
  "SELECT COUNT(*) FROM device_rules;"
# (expect same number, modulo any test rules from smoke)

# 4.5 — run verify-post (R-checks)
make verify-post
# expect ~26 PASS, R27 now PASS (the lock_timeout + 4 verification tests)

# 4.6 — run smoke
make test
# expect 118/118 smoke (59 RU + 59 EN)

# 4.7 — clean up the dump
rm -rf $HOME/skygate-pg-dump
# Keep the SQLite backup for 7 days, then move to long-term storage
# /home/admin/backups/skygate-pre-pg-*.db
```

## Rollback (if anything goes wrong)

```bash
# 5.1 — flip back to SQLite
# Edit /home/admin/skygate/.env:
#   SKYGATE_DB_DSN=/data/skygate.db
docker compose up -d --force-recreate skygate
until curl -fsS http://localhost:8080/healthz; do sleep 3; done

# 5.2 — restore the SQLite backup (if you suspect the live one
# was modified during the cutover window)
sudo docker run --rm \
  -v skygate-data:/data \
  -v /home/admin/backups:/from:ro \
  alpine:3.20 sh -c "
    apk add --no-cache sqlite &&
    cp -f /from/skygate-pre-pg-*.db /data/skygate.db &&
    sqlite3 /data/skygate.db 'PRAGMA integrity_check;'
  "

# 5.3 — re-apply ACL (the PG-side R-checks may have written
# acl_snapshots rows that aren't on the SQLite side)
curl -fsS -X POST -b /tmp/admin.cookie \
  https://skygate.example.com/admin/exit-rules/reapply
```

## Known issues (read these before starting)

1. **`strftime('%s', 'now')` vs `EXTRACT(EPOCH FROM now())::bigint`**:
   The dump script translates these. If you see "function
   strftime does not exist" during the apply, the translation
   missed a spot — re-run with verbose logging.

2. **`INSERT OR REPLACE` vs `ON CONFLICT`**:
   The rewrite script flags these. **Manual review required**
   because the conflict-target column is table-specific
   (e.g. `node_owner_map` has `(node_id)` as the unique key,
   `device_rules` has `(user_id, device_id, exit_node_id, target_value)`).

3. **`RETURNING id` not in queries**: skygate's Go code uses
   `LastInsertId()` which the `lib/pq` driver maps to PG's
   `lastval()` automatically. No code change needed.

4. **`PRAGMA` calls in queries**: skygate has 2-3 `PRAGMA`
   calls in queries.go (PRAGMA journal_mode, etc.). These
   are SQLite-only; the new code paths skip them under
   the postgres tag.

5. **autoupdate state file**: `/data/skygate-update-status.json`
   is the in-container path. On PG, this file is still
   bind-mounted from the host (`/home/admin/skygate/data/`).
   No change needed.

## Operator's decision points

- **Read-only mode duration**: 15 min is the estimate. If the
  dump.sql is large (>100MB), the translation + apply can
  take 5-10 min. Plan accordingly.

- **Backup retention**: 7 days for the post-cutover SQLite
  backup, then move to long-term storage. The PG-side has
  its own backup strategy (wal-g → S3, configured in the HA
  plan).

- **Rollback tolerance**: the cutover is reversible until
  you `docker compose up -d skygate` with the PG DSN for
  the **second** time. After that, audit_log + acl_snapshots
  diverges and a clean rollback means "restore SQLite from
  backup".
