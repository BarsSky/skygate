## Recurring traps — skim before touching anything

- `docker compose` interpolation is **CWD-relative**: with `-f /abs/path.yml` from elsewhere the project `.env` never loads and `${VAR:-default}` silently wins — always `cd <project dir>` or pass `--env-file`.
- `restart <svc>` keeps the old container definition, so `extra_hosts`, volume and `secrets:` changes need `up -d --force-recreate --no-deps <svc>`; source-only changes need **no** image build.
- **Three operator-managed files must survive every pull/reset:** `docker-compose.yml` (the operator's `extra_hosts` + host hostname), `go.mod`, `go.sum`. Run `git status` on the VM before any `git reset`/`git checkout` and never `git clean -fd` there.
- Never commit a private LAN IP, a real internal hostname, a credential or a key — use `<VM_HOST>`, `<PUBLIC_HOST>`, `example.com` and RFC 5737 addresses. `.githooks/pre-commit` rejects the known leak patterns in the staged diff; `git push` runs the whole gate via `.githooks/pre-push` (10+ min on Windows, `--no-verify` only for prod emergencies); a crashed unit needs `systemctl reset-failed`.
- Distroless images have no shell (`test: wget` healthchecks fail forever); the skygate image has no `sqlite3`, and busybox `wget` has no cookie support. A `0700` `mktemp -d` work dir blocks the service user, and an empty auth-key file makes the daemon read stdin forever.
- `.gitignore` negations are order-sensitive and the **last match wins**: `!scripts/check_*.sh` is overridden by a later `check_*.sh`, so new check scripts stay untracked without `git add -f`.
- Two migration chains (PostgreSQL + SQLite) must be extended together: `ADD COLUMN IF NOT EXISTS` is invalid SQLite, `?` is fatal for pgx, and `length()` counts bytes vs characters.
- Add columns only via `addColumnIfMissingSQLite(d, table, column, ddl)`, where `ddl` is the **full definition including the column name** (it emits `ALTER TABLE <t> ADD COLUMN <ddl>`); never swallow `ALTER` errors as "already applied", and after loading a dump set every sequence to `MAX(id)+1`.
- The PG **primary is not on `localhost`** (that port is a read-only replica), and SQLite `PRAGMA foreign_keys` is **per connection**.
- Scope firewall rules to the traffic, not the source host: a `/32` DROP for a noisy orphan client also killed the legitimate reverse proxy and froze `last_seen` for every device.
- `INSERT OR IGNORE` never re-attributes existing rows — use `UPDATE`; add a new tag **before** removing the old one; headscale 0.29 rejects uppercase tags, which skygate sees only as "pending forever".
- `tailscale up` on an authenticated node is a no-op (re-auth needs `--force-reauth`; a tag change belongs in `headscale nodes tag --force`), and `--advertise-routes` **replaces** the list — never advertise the subnet the host is inside, the bridge CIDRs, or `0.0.0.0/0`.
- Never ship a reconciler with a dry-run default, and never let a status page claim a service is running unless every state has its own branch.
- Never edit Go or templates with line-index shell tricks (`sed -i`, `$lines[618]=…`) — a line-range rewrite already deleted a `return` and a closing brace. Move a handler's tests in the **same commit** as the handler, and never inline a canonical helper (node-name lookup, device delete, session decode, rule annotation, route advertisement, DSN classification).
- Go `html/template` rebinds `.` inside `range`, so `{{if eq $ar.ID .ID}}` in a nested range is always true; annotating a struct **after** copying it into a slice/map loses the annotation; and a missing template key renders `<no value>` with no error.
- A check that needs live state (docker daemon, DB, VM) must report **SKIP, never FAIL**, and a new feature ships its own check script registered centrally.

## 1. Deployment & containment

**L-01 — Container DNS is the host's DNS, and `127.0.0.1` in a container is the container itself (B260).** The host resolver mapped the public relay name to loopback and Docker passed that resolver in, so the probe hit its own empty loopback and the UI showed "DERP socket: closed" while the relay was healthy. Pin the name in `extra_hosts` with a value from `.env` (`SKYGATE_DERP_PROBE_HOST`, gitignored) and a harmless loopback default; the same mapping lets the relay certificate verify inside the container.

**L-02 — A deploy that "succeeded" can run the old network config (B260).** `docker compose config` rendered the right value and the deploy reported success, yet the container kept old `extra_hosts`, because the command ran from the wrong CWD (so `.env` never loaded) and a plain `restart` kept the old definition. Guard: `scripts/rebuild_deploy.sh` step 2.5 warns when the probe host is unset and `CHECK_B260_STRICT=1` makes it fatal.

**L-03 — A host can carry two installations and nothing warns you.** A dead native systemd+SQLite install coexisted with the working docker+PG one (`restart counter is at 98779`, 493 MB / 212,742-line journal), and its earlier `config: HEADSCALE_API_KEY is required` failure **masked** the SQLite open bug (L-09) for weeks. Run `systemctl disable --now skygate` for the unused install kind before diagnosing DB problems.

## 2. Docker & Compose

**L-04 — Graceful shutdown needs an explicit contract, and a one-connection pool deadlocks (B31).** `stop_grace_period: 30s` plus a `/healthz` healthcheck is what lets Go's `db.Close()` flush the SQLite WAL before Docker escalates to SIGKILL, covering the deploy-time-SIGKILL class only. `SetMaxOpenConns(1)` with `synchronous=FULL`, adopted as corruption insurance, caused a CASCADE-LOCK hang under load; use `MaxOpenConns(15)` / `synchronous=NORMAL` / `busy_timeout=2s`, because the durability setting was a red herring that also cost throughput.

**L-05 — Prefer an embed over an image-layout dependency.** Templates were embedded but `static/` was read from disk while the prebuilt Dockerfile copies only the binary and entrypoint, so the panel rendered unstyled — no CSS, system fonts, no icons, dead dark theme — and dev never saw it because the bind mount hid the gap. Fix with `//go:embed static` plus `http.ServeFileFS`, keeping the cache-header policy and traversal guard bit-identical; guard: `scripts/check_b_mod_static_embed.sh`.

## 3. systemd, service lifecycle & native installs

**L-06 — A service cannot restart itself, and its children die with its cgroup (B261).** On a native install the unit runs skygate unprivileged under `ProtectSystem=strict`, so it cannot write the binary or run `systemctl restart skygate` (`sudo -n true` → "a password is required"), and a `setsid` child is killed with the cgroup — privilege, not missing code, blocked the native auto-updater. The fix keeps the model: the service writes **data only** (`<data_dir>/update/request.props`: job id, target tag, previous build, pid; no paths), a root-owned path unit fires a root-owned service, and a root-owned applier does backup → download → SHA256 → migrate → swap → restart → healthz → rollback, never `source`ing the request file and reading every path from a root-owned config.

**L-07 — You cannot `install` over a running binary (B261.3).** A write onto a live executable fails with `ETXTBSY`, so the applier writes a new file and does an **atomic rename**, keeping `skygate.prev` for the rollback path.

**L-08 — "Up" is not "the right build", and the documented fallback used a flag that does not exist (B261, B261.4).** Accepting HTTP 200 on `/healthz` accepts a binary that boots and reports another build, so poll for the **build string of the target tag** and on mismatch restore `skygate.prev`, restart, verify and report `rolled_back` — the live canary rolled back a wrong-build artifact that booted. The manual path was broken too: `--migrate-only` is not a flag but the **subcommand** `migrate-only`, and the wrong form appeared in the applier and in both manual-step lists.

**L-09 — `SKYGATE_DB=sqlite:/path` never opened; every native SQLite install was dead on arrival (B261.1).** The service printed its banner, opened no listener, and gave `dialect open "sqlite:/var/lib/skygate/skygate.db": … unable to open database file: out of memory (14)` because `openSQLite` converted only bare paths to the driver's `file:` form and skipped `sqlite:` DSNs — a scheme that driver does not know — so SQLite tried to create a **relative file literally named `sqlite:/var/…`** and reported `SQLITE_CANTOPEN` (14) as OOM. That is exactly the form the installer writes; it was missed because every SQLite test used `:memory:`, and the fix strips the prefix centrally plus adds real file-open tests for all three accepted shapes.

**L-10 — Detection order, the install-kind enum, installer surfaces and one-time migration scripts are all contracts (B262).** Container markers must be checked **before** `/run/systemd/system`, because skygate runs in a container *on* a systemd host and a permissively bind-mounted `/run` made detection report the systemd kind, so the update page printed `systemctl restart skygate` for a container with no such unit; the install-kind enum is persisted as a string, so new kinds are appended and ordinals must not move, and OpenRC was missing entirely, so every Alpine install detected as unknown and the update page refused. Changing an installer default means changing three surfaces (the env-file heredoc, the per-OS installer flag and the wrapper's exported allow-list), and a clean Debian 12 host showed the dependency lists omit `xxd`, so the env-file writer died and `set -euo pipefail` aborted the install between installing the binary and writing the env file, unit and helper. One-time migrations follow the same discipline: the derper-in-docker script is idempotent and ordered (pre-flight → build image → stop and disable the systemd unit while rendering the compose template → start the container → verify the port, STUN and an HTTPS `GET /`), with the old unit left in place so it remains the rollback.

**L-10.1 — `active` is not `listening`: create the listener first and narrate the boot (B269).** A native install reported `systemctl is-active skygate` = `active` while `ss -ltnp` showed nothing on the port, with the background samplers logging normally: `main()` ran config → DB (5 retries, ~42 s) → migrations → services → the whole route table and only then `ListenAndServe`, so every stall or fatal step in that chain produced an `active` process with **no port**, and neither the journal tail nor the self-updater could name the blocking step (the updater only saw `healthz did not report build '…' within 90s (last build: none)`). Bind the socket at the very top of `main()` (a port conflict then fails immediately and loudly), serve a provisional `/healthz` from it, hand the **same** listener to the real router once routes exist (no second bind, no gap), log `startup: phase=… +Nms` on every transition so the last line is the blocker, and turn a panic into a stack + phase + `503` + exit `3`. The trade-off to keep in mind: a booting process now answers with the **new** build string, so any "is this build deployed?" check needs an explicit boot marker (`"ready":false`) or it will accept a boot that never finishes.

**L-10.2 — A failure message that fits four causes names none of them (B268).** `healthz did not report build 'v1.5.11' within 90s (last build: none)` is equally true for a masked unit, an unrunnable artifact, a port owned by another instance and a service on another port, so the operator could not act. An applier must spend a few lines to be self-explaining: smoke-test the artifact before replacing a working binary, log a pre-swap baseline of what actually answers on the health URL (with the listener on that port), dump unit state + listener + journal tail before any rollback, and split the verdict into "never came up" vs "up but wrong build".

**L-10.3 — An optional feature must never be able to kill the boot, and config defaults must be absolute (B270).** The same native install that produced L-10.1 also died because `NewService` (OIDC) returned an error that `main.go` turned into `log.Fatalf`: the key dir defaulted to the **CWD-relative** `./data/oidc-keys`, the unit's working directory was not the data dir, `MkdirAll` failed with `mkdir ./data: permission denied`, and the process exited before binding its HTTP port — with OIDC *disabled*. Rules: a subsystem the operator has not enabled must degrade (nil/`503` + a log line naming the path and the fix), never abort startup; state paths must default to absolute locations derived from the data directory (never `./…`), because a systemd unit's CWD is whatever `WorkingDirectory=` says, otherwise `/`; and "why does the update always roll back" must compare the health URL's port with the configured listen port, because a mismatch makes verification unwinnable while the service looks perfectly healthy. Corollary worth its own line: `sync/atomic.Value` must be given a single concrete type for its lifetime — mixing `http.HandlerFunc` and `*http.ServeMux` panics at the handover, and no source grep can see it (B269's live probe caught it).

**L-10.4 — A background sampler is a query, so it needs the dialect too (B271).** The same journal showed the `/db/health` sampler running PostgreSQL catalog SQL (`pg_is_in_recovery`, `pg_database_size`, `pg_stat_user_tables`, `pg_current_wal_lsn`) every 30 s against **SQLite**, logging five `SQL logic error: no such function` entries per tick and leaving a permanently degraded DB-health badge on a healthy install — L-16's dialect leak, but in a *reader* rather than a migration, which the existing leak guards did not cover (they scan migrations and shared query files, not feature packages). A dialect-aware reader needs an explicit, defaulted switch (`Dialect: "postgres"` keeps every existing caller unchanged) plus a branch that answers the same operator questions with native SQL (`PRAGMA page_count`/`page_size`, `sqlite_version()`, `quick_check`) and leaves the impossible panels empty rather than inventing values. Guard it with a test that runs BOTH branches against a real SQLite database: the correct branch must succeed and the PostgreSQL branch must fail by name.

**L-10.5 — The database is the source of truth, so reconcile FROM it, not towards it (B272).** The tag autoupdater walked headscale and only considered nodes that already carried a `tag:dev-…` tag. That looks harmless until the first tag apply fails: the node then has no dev-tag, so every later tick skips it — forever — while `node_owner_map` keeps claiming the tag, the UI shows it, and no audit row, metric or alert mentions the divergence (live: `/my/devices` said `tag:dev-daniil-workpc`, headscale had no tags at all, and the per-device ACL rule matched nothing). A reconciliation loop must therefore iterate the DATABASE and make the outside world match it, reporting each repair and each refusal with a reason. The other half of the lesson is about *why* the apply failed: a policy kept in a file (`policy.mode: file`) makes `PUT /api/v1/policy` answer `500 update is disabled for modes other than database` — so a fallback gated on `404`/`405` never fires, and a fallback that shells out to `docker exec` cannot work on a native install at all. Detect the install kind, write the same artifact the service reads, and prefer the REST API over any CLI.

**L-10.6 — One question, one predicate: two "is this an exit node?" tests WILL disagree, and the wrong one will be the one that shouts (B273).** `internal/headscale.hasExitNodeTag` accepts three signals (the `tag:exit-node` tag, an `exit-`/`exitnode` name prefix, an advertised `0.0.0.0/0`|`::/0`), and `/my/exit-nodes` uses it — but the health monitor re-implemented the question as "carries the literal tag" and folded a negative answer into its `offline` bucket (`case !online || !hasTag: state = "offline"`). On the live host `aro` the only relay is `exit-node-vps`, online and advertising both base routes, with no tag: the user page correctly said **online**, the admin page rendered **«Нет рабочих exit-узлов!» + 0/1 здоровых**, and both were reading the same headscale list. Whenever a predicate exists in more than one place, the second copy must be a call, not a paraphrase — `NodeView.IsExitNode` is now the only definition, and the monitor also returns `ok=false` for a node that is not an exit node instead of inventing an `offline` row for every laptop in the tailnet. Corollary about *which* signal drives health: the monitor was checking `AvailableRoutes` (what the relay **advertises**) while the operationally decisive fact is `ApprovedRoutes` (what headscale actually **hands clients**) — so an unapproved relay counted as healthy. Health must be computed from the post-approval state; a missing tag is bookkeeping (surface it as its own `untagged` state and keep it healthy), a missing approval is breakage (`degraded`, and it must alert — the old alert predicate was the literal pair `online↔offline`, so a relay that silently lost its approval produced no notification at all).

**L-10.7 — A prefix can be served by ONE relay, so "each device has its own exit node" needs an owner per prefix, not per rule (B274).** `StaggeredSync` built every relay's `--advertise-routes` from that relay's own rules, so whenever two devices of different users pointed their rules at different relays and both rules resolved to the same CIDR, **both** relays advertised it. headscale assigns one primary per prefix (`node.SubnetRoutes()` is the netmap source), so the second advertisement is invisible — and *which* relay won was not stable: it changed between two `nodes list` dumps on the same day, after a sync pass had rewritten both route sets. That is what broke the operator's own Windows box: `skyworker` accepts routes and has **no exit node selected**, so its path to those destinations is the tailnet's subnet route, and its per-CIDR ACL grant named the relay that happened to hold the primary only half the time. The CDN expansion is what makes the collision routine rather than exotic — one domain rule for a Cloudflare-fronted site yields the CDN's entire published range set, so `discord.*` (device A → relay X) and `auth.docker.io` (device B → relay Y) collide on 28 ranges without the operator ever asking for it. Rules: (1) derive an explicit, deterministic **owner per prefix** (most claims wins, hostname as tie-break so it cannot oscillate) and advertise only the owned set; (2) never let two relays announce the same prefix, because a client can only ever use the primary; (3) a rule that loses its prefix must be **reported**, never silently half-working — the device's rule list stays untouched (that is the operator's model: each device keeps its own list on its own exit node), and the operator decides which relay keeps a contested prefix; (4) derived-row hygiene matters: the CDN expansion also duplicates rows (five identical `104.16.0.0/12` rows for one device, one per parent domain), which inflates the ownership weight and the "expected routes" counters, so collapse them on the natural key and keep the most informative parent.

**L-10.8 — A read-modify-write of a shared artifact must not be issued once per item when the write is asynchronous (B272.7).** `EnsureTagOwner` reads the whole policy, adds one `tagOwners` entry and writes it back, and the reconciler called it once per device. On a `policy.mode: file` host the write is not synchronous at all: skygate drops a request file and the root-owned `skygate-policy.path` unit writes the policy and **restarts headscale**. So call N read the file before the applier had written call N-1's result, and every write after the first was computed from a snapshot that did not contain its predecessor's entry — live on `aro`, immediately after the policy helper was installed on v1.5.31: three devices, three dev-tags, `checked=4 applied=1 failed=2`, `400 requested tags [tag:dev-daniil-laptop] are invalid or not permitted`, and `grep -c 'tag:dev-' /etc/headscale/policy.hujson` = **1**. The trap that costs the most time is the diagnosis: the losing writes each reported SUCCESS (or a downstream 400 that blamed the tag), so it reads like a permission or a tag-validation bug and every retry/backoff change is wasted work — the writes were not lost, they were interleaved. The fix is structural, not a retry: compute the whole pending set first (with the SAME predicates the apply loop uses, or the batch permits tags nothing applies and misses tags it does), write it once, and keep the per-item path only as a fallback so a failed batch still reports each item with its own reason. Corollaries: validate the whole batch before writing, because a single malformed entry must not half-apply it; make the single-item entry point delegate to the batch so the two can never drift; treat an empty batch as "no write", because on a file-mode host every needless write is a headscale restart; and remember that the batch moves the restart into the SAME tick as the applies, so the apply call needs the same bounded transient retry as the permit call (the try that permitted all three tags can otherwise lose all three applies to a daemon that is still starting, and the operator waits five more minutes for tags that were already allowed).

**L-10.9 — When one decision is written by two subsystems on two schedules, the slow one silently wins (B276).** skygate's per-prefix decision lives in two places: the **data plane** (which relay advertises the prefix — headscale serves a subnet prefix from exactly ONE relay, and the assignment table plus the advertised routes are recomputed every few minutes) and the **control plane** (the ACL, whose per-CIDR grant carries `via=[owner]` since B275). The data plane moved; the ACL was only regenerated when a rule, user or device changed. Live: the policy was applied at 18:19, 28 Cloudflare/Google prefixes moved to the other relay after 19:26, the routes followed within five minutes — and every pin kept naming the old relay. Because `via` on a per-CIDR grant is a permission **filter** (not steering), the client does not fall back to the other relay: it receives no route at all, goes out directly, and on a network where that path is blocked the site is simply gone. One user's device lost its entire Cloudflare set while another user's device kept working — the same defect, a different fallback — and nothing in the log, the audit trail, the metrics or the UI said a word (measured: 70 of 177 grants named a non-primary relay, 35 named a prefix nobody advertised). Three transferable rules: (1) if a decision is materialised in two artifacts, every change to the first must regenerate the second **in the same pass** — or the second must be derived at read time and never cached across the change; (2) a comparison is the cheapest alarm — `is the live policy the one I would generate right now?` turns an invisible class of drift into one boolean, and it must compare semantically (a policy arrives as an object, as a stringified blob, or as HuJSON with comments) and treat `cannot parse` as unknown rather than as drift; (3) when a vote decides an owner, count **voters, not rows** — a derived-row generator that rewrites ~145 rows every five minutes will otherwise decide the election, and each silent flip invalidates every pin that depended on the previous result.

## 4. Database: PostgreSQL / SQLite parity & migrations

See also [`db-schema.md`](db-schema.md), [`backup-restore-and-migration.md`](backup-restore-and-migration.md), [`disaster-recovery.md`](disaster-recovery.md).

**L-11 — SQLite drops writes silently when the disk is full; this is the root cause of the recurring corruption incidents (v0.32.5).** `sqlite3_step()` returned `SQLITE_OK` while no bytes reached disk, so the btree went inconsistent and the process kept running — inserts "succeeded" and were lost, with no error log — after the disk hit 100% (containerd's snapshotter held 6.7 GB of un-GC'd layers plus 916 MB of journal). `PRAGMA integrity_check` later reported `Tree 12 page 7838 cell 334: 2nd reference to page 9775` / `database disk image is malformed (11)`; guards are R30 (`integrity_check` on a copy of the live DB) and R31 (hard FAIL at ≥85% disk), and recovery is `sqlite3 .recover` into a SQL dump inside a throwaway container — never `DROP`+`CREATE`, which reuses the corrupted free pages and fails on the same page numbers forever.

**L-12 — All SQLite DDL goes through one chokepoint, and the `ALTER` helper needs the column name twice.** `execSQLiteDDL(d, stmts)` (`internal/db/sqlite_ddl.go`) recognizes `ALTER TABLE … ADD COLUMN …` and rebuilds the statement itself, so `addColumnIfMissingSQLite(d *sql.DB, table, column, ddl string)` emits `ALTER TABLE <table> ADD COLUMN <ddl>`. Pass only a type rather than the **full definition including the column name** (`ssh_port TEXT NOT NULL DEFAULT ''`) and a rerun fails with `duplicate column name`, and because the names are interpolated (`PRAGMA table_info` takes no bound parameters) callers must pass hardcoded literals.

**L-13 — Swallowing DDL errors as "already applied" hid two defects, one of which makes a release unusable.** The old migrations ran ~18 loops shaped `if _, err := d.Exec(q); err != nil { continue }`, and statements used PostgreSQL's `ADD COLUMN IF NOT EXISTS` — a **syntax error in SQLite** — so the error was read as "column exists" and `exit_servers.{ssh_target,ssh_key_path,accept_routes}` plus `device_rules.device_ip` never appeared on a fresh database. Fix by routing adds through `PRAGMA table_info` idempotency and returning every other statement's error; separately ~10 unprotected `ADD COLUMN` statements return `duplicate column name`, and since migrations run on every open that error propagates through the open-ping, so `v44 add user_name: duplicate column name` on a fresh **or** existing database means **v1.5.8 cannot run on SQLite at all** and a native SQLite host needs v1.5.9+, with the applier's pre-swap migrate step preventing a bricked host.

**L-14 — The two chains must stay in lockstep, or one backend silently loses tables.** The PostgreSQL chain ended at V071 while the SQLite chain stopped at V070 and its migration function did not exist, so the cert-sync table was never created on SQLite and certificate auto-renewal was dead there. One migration therefore means one PR containing the PG **and** SQLite function, both registry entries, and a green schema-parity test (version-set equality, per-table column-set equality, chain-run-twice idempotency, PG→SQLite→PG round trip).

**L-15 — The dialects differ structurally, not cosmetically.** `?` → `$1,$2,…` (`$N` is accepted by SQLite, but `?` is fatal for pgx); `INSERT OR IGNORE` → `ON CONFLICT … DO NOTHING`; `INSERT OR REPLACE` → `ON CONFLICT (col) DO UPDATE SET …`; `datetime('now')` → `now()`; `strftime('%s',col)` → `EXTRACT(EPOCH FROM col)::bigint`; `IFNULL` → `COALESCE`; `json_extract(col,'$.f')` → `col->>'f'`; `GROUP_CONCAT` → `string_agg`; `INTEGER PRIMARY KEY AUTOINCREMENT` → `BIGSERIAL`; `BLOB` → `BYTEA`; `DATETIME` → `TIMESTAMP WITH TIME ZONE`; `TEXT[]` → `TEXT`; `VARCHAR(N)` → `TEXT`; `'t'/'f'` → `true/false`. `PRAGMA` statements are SQLite-only, and `ON CONFLICT … DO UPDATE`, `RETURNING id` and `LastInsertId()` work on both.

**L-16 — Portability is one-way, and a stale comment hid it.** PostgreSQL can emulate SQLite (there is even a PG `strftime` shim), never the reverse — yet one file unconditionally returned the PG timestamp expression with the comment "as of v1.3.0 skygate is PG-only; the SQLite variant has been removed" after v1.5.4 restored SQLite, so ~12 call sites emitted `EXTRACT(EPOCH FROM now())::bigint` into SQLite (`SQL logic error: near "FROM": syntax error`). Similar leaks sat in shared query files on both sides with their errors swallowed (one silently disabled exit-node auto-detection, another left release history permanently empty), and a second hard-wired opener left every CLI verb dead on SQLite; fix with one dialect source of truth, a leak-guard grep test, and runtime tests that execute queries on real `:memory:` SQLite.

**L-16.1 — A natural-key change must be mirrored in every `ON CONFLICT` clause (B237.23).** A migration recreated the `device_rules` uniqueness index with six columns while the autoupdater still used a five-column conflict target, so every insert failed with `no unique or exclusion constraint matching the ON CONFLICT specification` and new per-device `/32` rules never reached the database — silently, because the error was only logged. `sync.go` now uses the same six-column target as the shared insert helper; any index-shape change must grep for every `ON CONFLICT` spelling of that table.

**L-17 — PG-specific migration protocol.** Wrap every migration in one transaction, because several auto-committing statements leave PostgreSQL permanently inconsistent and a suspended migration holds locks; `ALTER TABLE … ADD COLUMN` takes **ACCESS EXCLUSIVE**, so use `IF NOT EXISTS` with a constant default or expand-contract for non-constant defaults, and `CREATE INDEX CONCURRENTLY … IF NOT EXISTS` for indexes. Destructive statements are forbidden in the auto path behind an env flag plus an explicit click, because the old binary is still serving and would crash on its next request; `SET LOCAL lock_timeout = '10s'` makes a blocked migration fail fast. Helpers live in `internal/db/pgmigrate/`, with catalog rows B11 (no destructive DDL), B12 (per-driver SQL form), B18 (PG build), R26 (live lock timeout) and R27 (live PG tests).

**L-18 — The schema-conversion tool is a silent data-loss vector, and rollback tolerance is asymmetric.** It rewrites DDL with string replacements and copies with `SELECT *`, so run against an incomplete SQLite schema the missing columns arrive empty and silently destroy exit-node configuration and per-device IP rules; it needs a pre-flight column-parity check that refuses and lists the lost columns, a mandatory source backup, post-checks on row counts and checksums, and a round-trip test in CI. Because a dump load leaves every sequence at 1 (the next insert fails with `duplicate key`), the order is fresh database → migrations → load data → verify row counts → set every sequence to `MAX(id)+1`; the rollback ladder is DNS flip back (bounded by the 5-minute TTL) → `git revert` the migration commits → restore the pre-migration dump (kept 30 days) → rebuild the old host, and tolerance stops being clean once skygate has started twice on the new DSN.

**L-19 — DSN selection, the primary's real address, and WAL hygiene.** `SKYGATE_DB` is the unified selector (`sqlite:/path` or `postgres://…`, classified by `db.DetectDSN`), the older DSN variable is still honoured when it is unset, and unset `SKYGATE_DB` silently falls back to local SQLite unless the require flag is set — a live host carried a stale value on an old bridge address while the new one was correct. The PG primary is reached over the docker bridge, so the `localhost` port is a read-only replica where writes succeed and do nothing; a failing WAL push piles WAL until the disk fills, restore expects Patroni stopped with the data directory recreated and a `recovery.signal` written, the archive command must source one env file because `envdir` wants a directory, and only the bucket-prefix variable gained the `WALG_` prefix (prefixed endpoint or credential names make object stores answer `InvalidAccessKeyId: 403`).

## 5. Networking: headscale, DERP, ACL/tags, tailnet, DNS, firewall

See also [`networking.md`](networking.md), [`derp.md`](derp.md), [`acl-rules-reference.md`](acl-rules-reference.md), [`troubleshooting.md`](troubleshooting.md).

**L-20 — `approve-routes` never worked because the headscale config template omitted `unix_socket`, and a green metric hid it.** `approve-routes: exit status 1: Error: connecting to headscale: connecting to /var/run/headscale/headscale.sock: context deadline exceeded` appeared 144 times in 6 hours, and it reproduces inside the headscale container, so it was never a skygate bug: the config declared a gRPC listen address but no `unix_socket`, so the server never created the socket while the CLI (which has no socket flag, only a config flag) always defaults to that path. Fix by declaring `unix_socket` plus `unix_socket_permission: "0770"` in both the config template and the bootstrap script and restarting headscale. The UI showed `advertised_routes_ok = 1` throughout because automatic route approval approved them instead — always check whether the subsystem you are fixing is the only writer of the state you are reading.

**L-21 — An over-broad firewall rule took the whole tailnet offline, and the 404 noise behind it is not a bug (B179).** All 14 Tailscale clients **and** the skygate VM showed `online=false` with `last_seen` frozen at the minute a previous deploy inserted `iptables -I DOCKER-USER 1 -s <orphan-client-ip> -p tcp --dport 50444 -j DROP`; the rule, added to silence `node not found` 404 noise, also matched the **legitimate reverse proxy** on the same host, which returned 504 to every client fetching `/key` and pushing `/machine/map`. Remove the rules and persist the corrected set to the iptables rules file, with `scripts/check_b179.sh` asserting no rule remains and that headscale answers **401 not 504** on 50444. The noise itself (`ERR user msg: node not found code=404` on `POST /machine/map`, a 15-byte body, 0.2–0.5 ms, from a persistent source port, in bursts of two every 20–40 s, while the same host holds a valid client returning 200 in 200–500 ms) cannot be filtered by source port because both streams are HTTP/2 with multiplexing, so re-auth the client or ignore it — and note that a stale runbook misidentified that host as the operator's router when it is the reverse-proxy host.

**L-22 — "Tailnet split" was policy isolation, not session divergence (B111).** `tailscale status` inside the container listed 4 nodes while headscale reported 10 online, and the earlier theory (control-plane session divergence, fixed by re-authenticating every device) was explicitly retracted: the real cause was an incomplete infra-user migration, where the infra-node predicate matched only a hostname prefix and one tag, the backfill used `INSERT OR IGNORE` so it never re-attributed existing user-owned exit-node rows, the generator emitted no catch-all grants, and per-device grant writing silently skips buckets with fewer than 2 devices. The fix extends the predicate, changes `INSERT OR IGNORE` → `UPDATE` and adds the infra exit-node tag helper, with the remaining operator step being a re-tag that costs minutes of downtime each because Tailscale cannot change tags without re-registration; guards are `scripts/check_b111.sh`, the `tailnet.split_suspected` system test and `scripts/tailnet_probe.sh`, and you must **not** start with re-auth. Related: the generator also could not let skygate SSH into its own exit nodes because it emitted `["tag:private", "<admin>@<domain>"]` while the skygate host carries an infra tag and its traffic arrives as that host — a helper now appends the host's infra tags, and a hand edit to the live policy is only temporary because any ACL apply overwrites it.

**L-23 — Advertising the subnet you are already on creates a routing loop (B236).** Latency to a peer grew from ~500 ms to ~1700 ms because the host advertised its own LAN plus the bridge CIDRs, so route-accepting clients installed a more-specific route via the tunnel and bounced traffic through the relay and back over the same LAN (137 ms peer RTT × 3–4 hops), while LAN clients on that subnet lost direct access to siblings. Clear the advertisement and restart the daemon, verified with `ip route get <LAN_GW>` reporting the Ethernet device — measured after: `ping` 0.6–0.9 ms, TLS `GET /` 4–16 ms; guard: `scripts/check_b236.sh`.

**L-24 — There is no single "preferred exit node": three layers must all be present.** `device_rules` (intent) → `device_exit_node_prefs` (written by the reconciler) → headscale grants carrying `via:`, and a ~24-hour outage for one site came from two causes: the reconciler's live flag defaulted to `false` (dry-run), so the hourly pass correctly computed the change and silently skipped the write, and the ACL flag for `via:` was unset, so regenerated grants had no `via:` and the client picked its default exit. Default the reconciler to live with an explicit opt-out, enable `via:` emission and re-apply the ACL (verified after: 213 grants carrying `via:`), and guard with a unit test requiring an orphan user id to still produce a CREATE change plus decision-matrix tests.

**L-25 — Route delivery has an ordering trap, a tri-state field, and an injection vector.** The SSH step runs first and the approve step runs **unconditionally** afterwards, so a failed SSH still reports `approved=N` in the UI while route acceptance never reached the node — routes were computed correctly (32 of 147) but not applied; `accept_routes` is `-1/0/+1` where **`0` means "don't touch"**, so the flag is omitted entirely, and a relay daemon restart means up to 5 minutes with no exit-node capability. `ssh_target` comes from the database and is appended positionally to the `ssh` argv, so `-oProxyCommand=<cmd>` is parsed as an **option** and executes a command — validate it with a strict regex at the form and again before exec, pass `--` before the host, force `-oProxyCommand=none`, and require an absolute key path.

**L-26 — `/admin/derp` must not require `--debug`, and its status collection had three compounding bugs (B260, B260.1).** Operators run the relay without `--debug` deliberately because the debug endpoints leak client connection info, so `/debug/vars` returns 403, the JSON parse bails and the page claimed `DERPER-SERVICE: stopped`; the fix is a WebSocket upgrade probe against the always-on `/derp` endpoint (`101 Switching Protocols` on any functional relay) that runs **last** so debug-enabled deployments keep the rich panels. The collection itself had a probe URL hardcoded to an RFC 5737 TEST-NET address, plain HTTP against a TLS listener (rejected with `Client sent an HTTP request to an HTTPS server`), and a `LIMIT 1` without `ORDER BY` over duplicate bundled-relay rows inserted by direct SQL that bypassed the guard — fixed with deterministic ordering, hostname resolution mirroring the port resolver, TLS with SNI and verification skipped only for a literal-IP host, and `extra_hosts` for container DNS (L-01).

**L-27 — DERP container, certificate and config-file traps (B235, B260.2.x).** Manual cert mode forces `:443` and the HTTP port must be **80** (the old `8443` default was a leftover); an empty `--verify-clients=` value crashes the daemon; the verify check must match the SNI certificate; port resolution must prefer the database over the env var; and the probe URL must not be conflated with the derpmap URL. Build the image locally from the host's binary when the registry refuses, on a **glibc** base because the host binary is dynamically linked, keeping host networking for the privileged ports and STUN. A derpmap's short region label is not a hostname (using it made all 28 public regions render degraded), a certificate must be the **full chain**, a static cert file never renews itself, the two cert directories must not be confused because the sync writes one path while the daemon reads another, and reload for a cert change is SIGHUP rather than a restart. Editing headscale's config file does **not** change headscale — a duplicate derpmap URL was removed but the process was never restarted — and the ACL file-mode fallback is currently unreachable because the template sets database policy mode.

**L-28 — headscale duplicate node names behave asymmetrically, and that breaks device attribution (0.29.1).** Client-driven registration auto-bumps the name (`resolveGivenName`, `hscontrol/state/node_store.go:365-388`: `base`, `base-1`, `base-2`, …), so a second device silently becomes `<device>-1` while its client still believes it is `<device>`, whereas an **admin** rename collision is rejected with HTTP **409** `given name already in use by another node` (`setName`, `node_store.go:243-271`). Hostname is not the given name — the hostname is client-reported, case-preserved and collidable, while the given name is lowercase, globally unique and is what the dev-tag policy uses — so the ownership map should store the **given name**, because storing the hostname is the root of "pending forever" drift when a manual headscale tag never updates the DB row. Attribution has exactly four strategies (preauth-key id match, temporal window, existing dev-tag, OIDC username match), none of which matches a key minted by the headscale CLI or a node on the synthetic tagged-devices user, and "Sync from headscale" fills **only** the ownership map.

**L-29 — Tag operations are order- and case-sensitive (B176, B177).** headscale 0.29 rejects uppercase tags with `Error: tag should be lowercase`, which skygate saw only as "pending forever", and without the ACL-side lowercase the policy carries a differently-cased tag and headscale ignores the rule — so lowercase every dev-tag construction site. A tag never whitelisted in `tagOwners` is rejected on first sight with `InvalidArgument: requested tags are invalid or not permitted`, and the original untag-then-tag order therefore destroyed the old tag and left the node with **none**; the correct order is add-first, then untag and the DB row update only inside the success branch. Guards: `scripts/check_b176.sh` and `scripts/check_b177.sh` (10 contracts); infra tags belong to the infra owner, the public tag must never be mixed with infra, and the exit-node tag is required for the catch-all grant.

**L-30 — Device deletion is a coordinator, and ACL regeneration overwrites rather than merges (B171).** The earlier delete paths cleaned headscale, the ownership map and the exit-node preferences but left orphan `device_rules` and stale dev-tag ACL references, so the next regeneration either skipped them or made headscale's policy call return **400**; use one shared coordinator for both scopes — ownership cleanup, preference cleanup, all rules for the device in one query, ACL regen, cache invalidation (otherwise the deletion is invisible for the 5 s TTL) and an audit row — and note the UI bug where the Delete button was rendered inside an expiry-guarded block, hiding it for exit-nodes and no-expiry devices. Because the generator builds a brand-new policy and the push replaces headscale's policy wholesale, a first apply with no rules **wipes every existing grant**, so before any first re-apply on an adopted headscale dump the live policy, verify the snapshot captured the live policy, and use the import endpoint to convert it.

**L-31 — The Telegram relay uses subnet routes deliberately, not an exit node.** Replacing the default route would push every non-tailnet packet through the relay, so the relay advertises only the ranges Telegram uses; because that advertisement is static while Telegram adds blocks, a weekly cron resolves the known hostnames, unions the records, re-applies the routes (whose reset semantics prune stale ranges) and refuses an empty list that would wipe the advertisement. Alerts with no bot configured go to a noop sink, so the audit row is the durable proof. See [`TELEGRAM.md`](TELEGRAM.md).

## 6. Auth / OIDC

See also [`oidc.md`](oidc.md), [`https.md`](https.md).

**L-32 — OIDC is four must-match values, the redirect URI is an exact string, and three config traps bite.** The issuer, client id, client secret and redirect URI must match headscale's `oidc:` block value for value, and `redirect_uri` matching is exact per RFC 6749 §3.1.2.3 — a trailing slash, a port difference or http-vs-https is a 400 (`redirect_uri mismatch`), with `Invalid state parameter` or a browser stuck on `/oidc/authorize?` after a successful login as the tell. The block must be at YAML **top level** (nesting gives `FATAL no oidc provider configured`), `strip_email_domain` was removed in headscale 0.23+ and its presence crashes 0.29.x at startup, and `automatic_authorization: true` is what makes provisioning one-click while `auto_update: true` re-applies the ACL on every login. Discovery is the heartbeat — 404 means the path is not routed, 502 means skygate is down, `jwks_uri returned no keys` means the keypair was not initialized — and JWKS must return exactly one RS256 key because a `kid` mismatch breaks token parsing and losing the key directory invalidates every issued token.

**L-33 — A login round-trip that ignores `next` silently kills the handshake, and later fixes did nothing until the real bug was found (B172 → B173.1 → B174).** Logging into headscale through its OIDC redirect landed on skygate's welcome page and the device was never registered, because the login handler always redirected to the dashboard and discarded the `next` parameter the handshake depends on; the fix reads, validates and honours `next` through `safeNextRedirect(next, requestHost)`, an open-redirect defense rejecting protocol-relative, cross-host and non-http(s) targets. Two intermediate fixes then did nothing: a button-only loading state is invisible because `HTMLFormElement.submit()` from password managers bypasses submit listeners, and the real defect was that OIDC session reading parsed the cookie as a colon-separated string the login handler **never wrote**, so it always returned nil and every authorize call bounced back to login — perceived as "the login page keeps resetting my password", and unnoticed only because the hard-coded redirect meant the broken code was never exercised. The fix delegates to the shared JWT parser plus a user-lookup callback, and the e2e test that should have caught it had passed only because it pre-populated an auth code and set a test-only session header — a test-only bypass is worse than no test.

**L-34 — OIDC-registered nodes need their own attribution strategy, and the public issuer is the fragile part (B167, B168, B175).** An OIDC node has no preauth key and no tags, so the other strategies never fire and the device showed a pending dev-tag forever; the OIDC strategy matches "no preauth key id and headscale user name equals the portal username", relying on headscale naming the user from the OIDC `name` claim. Two gaps remain: headscale creates a new user whenever that claim matches no existing user, so duplicates recur on every fresh bootstrap, and nodes already on the synthetic tagged-devices user with no live dev-tag are skipped entirely. The sync page offers six restart modes plus a download-only seventh, and every proxy location must set `X-Forwarded-Proto` (read to render the issuer claim) with long timeouts — a missing header still redirects to login but with an **empty** `next=`, and a stale env file yields HTTP 200 discovery whose issuer has no scheme.

## 7. UI / templates / i18n

See also [`features.md`](features.md).

**L-35 — Go template scope and copy semantics caused two consecutive releases of wrong data (B178, B178.1).** All 103 of one user's rules showed the same preferred exit node while the database lookup returned the right value, because an inner `range` over an annotated slice rebinds `.` to the inner item, so the comparison was always true and the value ended as the last row's. The fix moves the answer into the rule struct, resolved in Go by a helper that batches one lookup per unique (user, device) — 3 queries instead of 324 — and the follow-up bug was that the annotation ran **after** the grouping loop that copies each rule into the per-node map; guards are 8 unit tests plus a contract pinning the call order by line number.

**L-36 — The error surface is architectural, and template, i18n and JSON-response bugs all pass their tests.** No shared error-rendering helper exists while `http.Error(...)` is called **482 times in 68 files**, and `http.Error(w, err.Error(), 500)` both replaces the page with `text/plain` and leaks SQL text, table/column names and sometimes the DSN — the keys page has no flash block at all, so a DB error there can only be a raw page. Never hand `err.Error()` to the user, redirect form POSTs with an i18n key after verifying the page renders a flash block (a redirect without one makes the failure invisible), and never touch `403 forbidden`; a leak-guard test pins a baseline of 101 leaking sites that may only decrease. Template and translation bugs are equally silent — a page used a field no handler set and printed `<no value>`, and the i18n parity test proves there are no missing keys but cannot see typos, wrong-language values or HTML encoding — while a per-row button returning JSON from a plain form replaced the page with raw JSON, and a status page claimed a daemon was running when a third state (configured path, file missing) had been collapsed into "enabled". Enumerate the states before rendering the controls, and remember a killed router stayed "active" for 35 s+ because the watchdog fires only when the node id is gone, never when it is merely offline.

## 8. Release & self-update

See also [`UPDATE.md`](UPDATE.md), [`deploy.md`](deploy.md).

**L-37 — The Docker image is amd64-only, and the missing checksum asset was a path collision (Issue #4, B262).** The pre-v1.5.4 release workflow built amd64 and arm64 in separate jobs pushing the **same** tag, so the second push overwrote the first and an older tag answered "no matching manifest for linux/amd64" on amd64 hosts; the image is now deliberately linux/amd64-only, and re-enabling multi-arch needs one build-push action with both platforms or two jobs merged with `docker buildx imagetools create`, never two pushes to one tag. Releases in that window also attached **no checksums**, because the workflow downloaded the artifact into a directory whose only file has the same name, so the flatten step moved the file into the same-named directory; the applier's hard checksum requirement then made native self-update impossible on every real release while appearing secure, so it falls back to the per-asset digest from the Releases API with an operator-managed base-URL mirror for air-gapped hosts. Verify the artifact rather than the job's exit code, and remember GitHub Actions parses `format()` arguments as literals, so a `| lower` inside `format()` did not apply and produced an invalid mixed-case registry tag with a failed release and no image.

**L-38 — Installer entry points must not silently ignore flags, and first-run bootstrap must be idempotent.** The readme recommends a compose-file flag the installer does not handle at all, and the per-OS installer has no catch-all branch, so unknown flags are ignored and the operator gets a bare-metal install instead of Docker. First-run adoption of an existing tailnet is deliberately explicit: an hourly cron classifies each portal user's headscale id and never auto-deletes a portal user, a banner says users were detected but not adopted, the claim-all endpoint claims rows idempotently and case-insensitively, and the exit-server upsert is idempotent by primary key — but claim matching is case-insensitive, so a case mismatch is a silent no-op, the original root cause of "no device" with no explanation.

## 9. Testing & B-check contracts

See also [`internals.md`](internals.md).

**L-39 — The B-check is the unit of "done", and a missing or mistyped script is a silent no-op.** Every block ships a check script, a row in `scripts/verify_pre_deploy.sh` and an `AGENTS.md` mention plus build/vet/test, so a B-number in prose proves nothing about a script existing; the catalog was invoked as `test -f scripts/check_b*.sh && bash …` under `set -u`, so a typo produced no FAIL and no SKIP and the catalog simply got shorter — seven referenced paths did not exist, one of them a dot-vs-underscore typo that meant a contract never ran at all. Fix the paths and add a gate that every referenced script exists, report SKIP rather than FAIL when a prerequisite is unavailable, and update greps that reference implementation details in the same change that moves the code.

**L-40 — Corrupted counters, a red baseline, and several "bugs" that were correct behaviour.** Duplicate `run_check` entries inflate pass/fail totals, backticks inside a `run_check` description were **executed by bash** (TD-15), a contract that pinned a deliberately removed function kept passing, and `go vet ./...` was **red on HEAD**, blocking every gate; baseline false positives (a `DROP INDEX IF EXISTS` flagged as destructive DDL, stale migration-version assertions, probe-context artifacts where the host namespace was probed instead of the container's) erode trust, so read a gate result as a claim to verify rather than a verdict. Liveness is the process and readiness is dependencies with a 1-second cache, so a 503 from a stopped headscale container or a readiness p99 of ~300 ms under 50 concurrent scrapes is expected rather than a DB problem, and a `SIGSTOP`ped process answering nothing, a `mv` of the open database file being harmless on Linux, and lock contention absorbed by the busy timeout are all normal; since sessions are stateless JWTs, a restart does not log users out.

**L-41 — Test-quality rules that came out of real misses.** Port a handler's tests **in the same commit** as the handler, and write the per-feature test harness first and port one test file as proof of concept, because the refactor dropped 12 test files and ~600 functions then spent a 1–2 day tail re-porting 30+, while re-inventing the harness twice cost 2–3 days on its own. System tests against external systems must restore prior state so they can run on the production VM, `:memory:` SQLite is not coverage for the SQLite code path, and a query's portability is only visible in the other dialect. The v0.26.0 fault-tolerance matrix (twelve cases) is the reference for what "verified" means here, and `/etc/hosts`-based partition simulation does **not** work because DNS is cached in-process.

**L-45 — "Green locally, red in CI" is usually a test that depends on a database somebody migrated by hand (CI test-pg job, 2026-09-19).** The job `go test with SKYGATE_TEST_PG_DSN` runs `go test ./internal/db/...` against a **fresh** `postgres:15`, and it was failing 40 tests that passed on every machine where the test database had been migrated once. Four distinct causes, all test-side except the last:
* **Raw `sql.Open("pgx", dsn)` bypasses the harness.** `OpenTestPG(t)` creates `skygate_pgtest_<test>`, sets `search_path` and runs `MigratePostgres`; tests that opened the DSN directly skipped all of that and hit `relation "global_settings" does not exist (42P01)` on an empty database.
* **`?` placeholders against PostgreSQL.** The runtime is `$N`-first (`queries.go`), but nine read-back queries and `seedExitServer` still used SQLite's `?` → `syntax error at end of input / at or near ")" (42601)`. Symptom to watch for: an assertion helper that ignores the `Scan` error reports a plausible-looking wrong count ("bob keys left = 0, want 1 (cascade over-reached)") when the query never ran.
* **Catalog queries without a schema filter.** `information_schema.columns` and `pg_class` span every schema the role can see, and each sibling test owns a `skygate_pgtest_*` schema: an unfiltered count saw 9 `exit_servers` tables and an unfiltered `pg_index` join returned 53 index columns from ~10 index instances. Always scope with `current_schema()`.
* **Tests that assume the schema is empty (or at V060).** `OpenTestPG` already applied the whole chain, so `applied_migrations` holds one row per migration (the tests wanted 1 and 7), and `CREATE UNIQUE INDEX IF NOT EXISTS` in a migration is a no-op when a later migration (V068) already created that index with 6 columns while the test asserts 5. Reset the bookkeeping / `DROP INDEX` inside the test instead of assuming a pristine schema.
* **And one real product fix**: two concurrent `MigratePostgres` runs raced on the DDL and on the bookkeeping and the loser died with `tuple concurrently updated (XX00)`; `SET lock_timeout` only makes a blocked migrator abort (and does not cover advisory locks), so the chain now takes a session-level `pg_advisory_lock` on a dedicated connection. That matters beyond CI: an HA pair booting together would otherwise fail to start.
* Rules that follow: a test suite that only ever runs with the DSN unset is **not** evidence about PostgreSQL; every new `.Query/.QueryRow/.Exec` in `internal/db` tests uses `$N` + `current_schema()`; and a database-touching test must be runnable against a brand-new empty database — that is the entire point of the CI job.

**L-46 — A release pipeline's own plumbing is unverified until the published asset and body are inspected, and "optional input, empty output" is a silent failure (v1.5.6–v1.5.9, 2026-09-19).** Three failures came from the pipeline rather than from skygate:
* `release.yml` downloaded the `SHA256SUMS` artifact into `dist/SHA256SUMS` — a *directory* whose only file is also named `SHA256SUMS` — and the flatten step then ran `mv <file> .` with that directory already present, which moves the file **inside** it. `mv f dir/` is a silent success, so v1.5.6, v1.5.6.1, v1.5.7 and v1.5.8 published a directory and no checksum file at all. The native applier's GitHub-digest fallback masked it for three releases (and a mirror cannot use that fallback, so the gap would have surfaced as a broken air-gapped update).
* The release body came from `RELEASE-NOTES-v${VERSION}.md` with `body_path` set to the empty string when the file was absent, and `generate_release_notes` was never set — so v1.5.8 published an **empty** release body. The deeper cause was not the file name: the `release` job had **no `actions/checkout` step at all**, so neither that file nor any other named notes file could ever be found there.
* `${{ format('ghcr.io/{0}/skygate', github.repository_owner | lower) }}` never applied the filter, because Actions parses `format()` arguments as literals, so `BarsSky` produced an invalid tag and two releases (v1.5.0, v1.5.2) pushed no image.
* Rules: never let an output path collide with the name of the file inside it — the same mistake appeared twice in one session (the workflow's `dist/SHA256SUMS`, and an acceptance harness that built a binary to a path that was already a directory, then `docker cp`'d a directory and got `Is a directory`); never leave a body/path field empty when an input is missing — fall back to something non-empty; pre-compute values instead of relying on expression filters inside `format()`; give every **consumer** of a release a second, independent source (both the installers and the native applier now fall back to the GitHub per-asset `digest: sha256:<hex>` when a release publishes no `SHA256SUMS` — and their JSON matching is whitespace-tolerant, because the API's pretty-printing is not contractual — instead of telling the operator to set `SKYGATE_SKIP_VERIFY=1`); and treat "verify the published artifacts" (checksum file is a *file* listing every archive, the image tag pulls, the release body is non-empty, the tarball reports the expected build string) as a required post-tag step, not an optional one. The guard is `scripts/check_b261_native_self_update.sh` sections L (flatten simulation), O (extract the newest section with the workflow's own awk against the real file, version-boundary probe, non-empty fallback, no per-version files) and P (the installer's checksum chain rehearsed offline: SHA256SUMS, digest fallback, corrupted tarball refused, neither source refused).

**L-47 — `producer | grep -q` under `pipefail` is a false-FAIL generator, and "one rotating red check per run" means the gate's own plumbing is broken, not the product (2026-09-19).** Five consecutive full gate runs on the reference host each ended with *one* FAIL — B237.24.1, B213, B202.5, B212, then three at once (B237.20, B237.23, B235) with the output cap lifted — and every one of those checks passed standalone, repeatedly (20/20, 6/6, 3/3, also under artificial concurrent Go load and during a container rebuild). The causes were three different bugs in the *checks*, none in the code under test:
* **The dominant one**: `CGO_ENABLED=0 go test … | grep -q '^ok'` in a script that sets `set -uo pipefail`. `grep -q` exits at its first match and closes the pipe; the still-writing `go test` (one line per package, so any multi-package pattern) dies with SIGPIPE (141), and `pipefail` reports the *pipeline* as failed although the tests passed. It is timing-dependent — worse under load, invisible on a warm standalone run — which is exactly why it looked like "load flakiness" and why every attempt to blame memory (no OOM evidence in `journalctl -k`, 5.6 GB free, `go build ./...` fine) or the small VM was wrong. The repo had already documented this exact trap in `scripts/b_mod_reregister_live.sh` ("DROP `set -o pipefail` … `echo "$VAR" | grep -q` returns 141"), so the lesson is: **capture first, then match** — `OUT="$(cmd 2>&1)"; if grep -q '^ok' <<< "$OUT"; then …` — and when you see a `pipefail` + `grep -q` pair anywhere, check it before trusting the FAIL.
* A test-side race: `TestSSHDumpTransport_Dump_FakeSsh` asserted stderr lines that the reader goroutine could still be holding when `cmd.Wait()` closed the pipes (Go's documented "do not call Wait before all reads have completed"); both dump transports now drain to EOF first.
* A live contract that reported its dependency as broken: `check_b237_24`'s `git ls-remote` turned "remote unreachable" into `FAIL`; it must `SKIP`.
* Rules: a FAIL is a claim to verify, not a verdict (L-40) — re-run that check standalone, and if it passes twice, hunt the check, not the code; never "fix" a rotating red by loosening the product's tests; and the diagnostic that settled this was lifting `run_check`'s 20-line output cap (`head -20` → `head -200`) for one run, because the failing contract and its message were being truncated away. Partial fix + the remaining ~25 sites: `docs/ROADMAP.md` RR-11 / TD-19; the four `--help` contracts now also retry the binary link once and print the real error (`scripts/lib/go_build.sh`).

## 10. Documentation & process

See also [`README.md`](README.md), [`internals.md`](internals.md).

**L-42 — Refactor process rules from the v0.30 postmortem.** Wrap-and-migrate beats delete-and-rewrite and the no-behaviour-change rule outranks a clean diff, so introduce the per-feature seam satisfied by thin wrappers and never do a 70-file rename; delete nothing you cannot re-derive, since the 4260-line i18n catalog was split mechanically by a script and the two residual handler tests cover rendering that lives in that package. Move least-dependent first, keep the binary green at every commit, run the catalog plus VM smoke at each phase boundary, and prove a move lost no behaviour with a coverage diff (before/after profiles, diff empty or renames only). Two silent process traps: a legacy method and its wrapper coexisting with different behaviour, and removing a struct field the old tests used — prefer one canonical helper per concern and delete the alternate outright.

**L-43 — Documentation and trackers drift into a second, wrong source of truth, and stale documents must be corrected forward.** Live examples: a project doc claimed Go 1.23 while the module file declared 1.25.0, readmes claimed "66/66 checks" while the catalog had 223 check invocations, readmes described the pre-v1.3.0 architecture long after the driver changed, and one link target had a doubled path segment; the backlog was about a release behind the agent instructions, one workstream was described as blocked, shipped **and** done in three sections, a UI refactor was "deferred" in one file and DONE in two others, and several blocks were stamped SHIPPED while later entries listed them as pre-existing FAILs. Pin counts and versions with a script (trust grep over a human count — the consistency contract found 7 and 11 occurrences where a hand count found 6 and 4), update the tracker in the same commit, never leave two unreconciled statements about one decision, and never edit a historical doc in place — add a correction note pointing at the current doc and the superseding commit, because quoting a stale document as authoritative is exactly how a wrong root cause was published (L-21).

**L-44 — Module boundaries, canonical helpers and the security inventory.** Node-name lookups, device deletion, session decoding, rule annotation, route advertisement and DSN classification each go through exactly one helper — an inline duplicate is the bug class the whole-tree sweeps fixed — and alerts must not create an import cycle, so each package declares a small local notifier interface that `main` wires. All admin writes go through the single audit helper, and where a state change and its audit row must not diverge they share one transaction; modules are opt-in and statically registered with atomic state writes, and cross-feature calls go through the other feature's service rather than its handler or template. Security items worth keeping current: an empty JWT secret silently falls back to a logging-only dev default with an unreachable "required" check below it; the settings page writes the env file mode **0644** with the JWT secret and API keys inside and silently discards several form fields while reporting success; the docker socket is mounted into the skygate container, which is a host breakout on RCE; the per-user key-encryption secret is optional so encryption degrades; the Telegram bot token is logged in cleartext because Go substitutes the full URL into a URL error; the SSH target is an injection vector (L-25); and host-key checking is trust-on-first-use without pinning.

## Rejected / abandoned approaches

- **PG-only (SQLite removed)** — v1.3.0 removed SQLite and v1.5.4 restored it; do not delete a working backend to add a second. Also rejected: build tags for dialect selection, treating SQLite as second-class, and hiding PG-only features in the UI instead of showing an explicit "requires PostgreSQL" message.
- **`lib/pq`**, **one squashed PG schema**, **managed PostgreSQL**, **`pg_auto_failover`** — rejected for the pgx driver, per-version migration diffing, self-hosted Patroni, and the same.
- **Litestream + SQLite as the long-term HA answer** (5–15 min failover versus the < 1 min target, non-zero RPO, a single-file DB that hurts past ~1 GB), **a second replica**, and **headscale on PostgreSQL now** (blocked, 0.29.x has no PG support).
- **Active-active multi-writer HA** — headscale's API is not built for concurrent writers, and last-write-wins lets a slow write clobber a fast one; the operator chose active-passive with a priority chain, auto-reclaim off (manual reclaim only, to prevent flapping), Patroni untouched and Tailscale Funnel skipped. **Auto-promotion without an operator** is deferred, because without an external lock both nodes can promote; force promote/demote does not bypass the elector, which writes an intent key the next tick confirms or overwrites.
- **`DROP`+`CREATE` for DB corruption**; **`synchronous=FULL` plus a single DB connection**; **`envdir` in the archive command** and prefixed object-store env names; **running WAL backups while Patroni manages the data directory**; and **tests that assert only dialect classification for a `sqlite:/…` DSN**, which is exactly why the DSN bug shipped.
- **An in-container reverse proxy on by default in front of an existing terminator** — a rendered config with placeholder hosts made the ACME client refuse it and crash-loop, and when an external terminator owned 80/443 the container intercepted its traffic; it now sits behind a compose profile and is off by default.
- **`tailscale up` as a generic fix** (a no-op on an authenticated node); **subnet routing as a reachability fix**; **advertising your own LAN, the bridge CIDRs, or a default route**; and **an exit node for the Telegram relay**.
- **A dry-run default for a reconciler**; **`INSERT OR IGNORE` for re-attribution**; **blocking a noisy host in the firewall**; filtering the 404 stream by source port (infeasible under HTTP/2 multiplexing); **the "home router" root cause and the re-auth-every-device tailnet-split fix** (both retracted); **keeping the subnet-router on the old host**; and **a manual preference-row insert** (an interim workaround only).
- **A registry image where the registry is blocked, a musl base for a glibc-linked binary, bridge networking for the relay, and a multi-stage build** — all rejected in favour of a local build on a glibc base with host networking. **A restart for cert pickup** is rejected for a reload signal; **pushing certs to each node from the admin page** is rejected because the periodic object-store poll converges both nodes and works when the active node is down; **a certificate's validity dates as the sync trigger** is rejected for an operator-controlled version/hash file.
- **The colon-separated session cookie and the e2e test's mock session header**; **sourcing the update-request or env file as root**, because a compromised service must not be able to hand the root applier a shell; **a `setsid` child to perform the restart**, since systemd kills the whole cgroup; and **capturing a raw database handle instead of the resettable source in long-lived services**, which produced a "database is closed" cascade plus a silent login-audit drop on DSN hot-reload.
- **Disabling the netfilter integration entirely for OS-level tailscale installs** — banned, the directory-less mode is required. **Re-provisioning the same subnet CIDR on a new host** — issue a new preauth key and let the sidecar garbage-collect the old node, and prefer disabling a subnet (which preserves the row and preauth progress) over removing it.
- **Keeping the old handler package as re-export shells**, **cross-feature imports of handlers or templates**, and **a single giant i18n catalog** — all rejected, as were the heavy GitHub client library, a migration framework, OS package distribution, unattended auto-update, in-app release-candidate channels, repack tools at the current schema size, a full rewrite of the 48 KB query file (pilot only), and a big-bang error-rendering refactor across all 482 sites.
- **Deferred by decision, not by accident:** full ACL import/merge (import exists as a shape-validated replace), multi-control-plane, OIDC-driven adoption, bulk first-run adoption beyond the explicit claim flow, a subnet-router discovery wizard, Telegram Bot API rate-limit and message-length handling, MTU guidance, auto-rollback when a promoted node cannot start, backup retention/pruning, and a dependency-free amd64 manifest for pre-release tags.
