## 1. Topology — how the pieces fit

```
   operator's browser
     │ HTTPS 443
     ▼
   ┌──────────────────────────┐
   │ reverse proxy            │  <PROXY_HOST> (Nginx Proxy Manager): terminates TLS
   └───┬──────────────────┬───┘
       │ / , /admin/*     │ /machine/* , /key , /ts2021
       ▼                  ▼
   ┌──────────────┐   ┌────────────────────────┐
   │ skygate      │◀──│ headscale              │
   │ <VM_HOST>    │   │ :50444 (API + gRPC)    │
   │ :8080        │   │ headplane :50445 (UI)  │
   └──┬────────┬──┘   └───────────┬────────────┘
      │        │ SSH (routes)     │ DERP map
      │        └─────────▶ ┌───────────┐
      │                    │ derper    │ <RELAY_HOST>:443/tcp HTTPS
      │                    │           │ :3478/udp STUN, :80/tcp
      │                    └───────────┘
      │ tailscaled (optional in-container sidecar)
      ▼
   tailnet (headscale control plane)
     ├── user devices        tag:dev-<user>-<host>
     ├── subnet routers      tag:subnet-router
     ├── exit nodes          tag:exit-node, tag:dev-infra-<host>
     └── skygate host itself tag:dev-infra-*
```

### Who talks to whom

| From | To | Port / proto | Purpose |
|---|---|---|---|
| browser | reverse proxy | 443/tcp | UI + OIDC |
| reverse proxy | skygate | 8080/tcp | portal UI, `/healthz`, `/readyz` |
| reverse proxy | headscale | 50444/tcp | Tailscale control plane (`/machine/*`, `/key`) |
| skygate | headscale | 50444/tcp | API (`/api/v1/*`) — list nodes, `SetPolicy`, `DeleteNode` |
| skygate | headscale (CLI) | `docker exec headscale /ko-app/headscale …` | `nodes approve-routes` (the API route endpoint is gone in headscale 0.29.1) |
| skygate | exit nodes / relays | 22/tcp (or `ssh_target` port) | `tailscale set --advertise-routes=…` |
| skygate | derper | 443/tcp (HTTPS) | `/debug/*` status probes + `/derp` WebSocket liveness probe |
| tailnet clients | headscale | 50444/tcp | long-poll `/machine/map`, `/machine/ping-response` |
| tailnet clients | derper | 443/tcp + 3478/udp | relayed WireGuard + STUN when direct P2P fails |
| headscale | skygate derpmap endpoint | `http://skygate:8080/admin/derp/relays/derpmap.json` | merges operator's DERP rows into `derp.urls` |

### Three planes, three failure classes

- **Control plane** — every client learns the tailnet map from headscale. If this
  path breaks, clients stop updating `last_seen` and every device looks `offline`.
- **Data plane** — WireGuard direct P2P, or relayed via DERP when NAT/firewall
  prevents a direct path. Skygate cannot speed this up; it can only report it.
- **Policy plane** — the ACL headscale enforces, generated by skygate from
  `portal_rules` + device tags + exit-node preferences and pushed with `SetPolicy`.

Skygate sits **between** the operator and headscale as a policy/self-service layer,
and **beside** headscale as an automation client. It is not in the packet path
except when the optional in-container `tailscaled` sidecar is enabled.

## 2. Subnet routers

A subnet router is one Tailscale node on a LAN that advertises a CIDR to
headscale. Once the route is approved, any tailnet member running
`tailscale up --accept-routes` can reach the LAN through that node.

**Use it when** several LAN devices cannot run Tailscale themselves (NAS, printer,
IoT hub, hypervisor UI, ESP32) — roughly "5+ installs or impossible installs".
**Do not use it** when only one or two devices need tailnet access: install
Tailscale on each directly. Skygate's allocation of `<USER_SUBNET>` is only a
*logical namespace* in the ACL; reachability requires a real router on a real LAN.

### 2.1 Prerequisites

1. A host that runs 24/7 (Raspberry Pi, mini-PC, NAS with SSH, a VM that never sleeps).
2. Tailscale installed on it (`curl -fsSL https://tailscale.com/install.sh | sh` or
   the official installer).
3. A **preauth key** issued by the admin at `/admin/users/{id}/subnet` →
   *Issue preauth key*. Keys are single-use with a 1-hour TTL.
4. The allocated CIDR — shown on the same page as `<USER_SUBNET>`.

### 2.2 headscale route-approval flow

```
admin provisions                user runs setup.sh                skygate sidecar
/admin/users/{id}/subnet   ──▶  tailscale up --advertise-routes ──▶ SyncOnce (30s)
   (preauth + CIDR)                + --authkey=tskey-auth-…           auto-approve
                                                                     by hostname
   user_subnets.status: pending ──────────────────────────────▶ router_active
```

A node can *advertise* routes freely; headscale will not push them to other
clients until an admin **approves** them. Skygate's `sidecar.SyncOnce` goroutine
polls headscale every **30 s**, finds nodes tagged `tag:subnet-router` whose
hostname matches `skygate-subnet-<username>`, approves the advertised routes and
flips `user_subnets.status` to `router_active`.

### 2.3 What skygate automates

| Step | Who | Mechanism |
|---|---|---|
| Issue preauth key | admin UI | `/admin/users/{id}/subnet` → *Issue preauth key* |
| Register the router node | operator | `deploy/subnet-router/setup.sh` (or the pasted `tailscale up` command) |
| Approve advertised routes | skygate | `sidecar.SyncOnce`, every 30 s, hostname match only |
| Flip status `pending → router_active` | skygate | sidecar tick writes `user_subnets.status`; the denormalised `portal_users.subnet_status` is refreshed on the next `/my/devices` load |
| Detect a dead router | skygate | sidecar marks `user_subnets.status='disabled'` when `last_seen > 5 min`; the CIDR is **not** re-allocated |
| Push routes for exit nodes / relays | skygate | `headscale.Client.SetAdvertisedRoutes` over SSH, then `nodes approve-routes` |
| Remove the router | admin UI | `POST /admin/users/{id}/subnet/remove` |

### 2.4 Exact commands

**Operator, on the router host** (the quick-start path):

```bash
curl -fsSL https://raw.githubusercontent.com/BarsSky/skygate/main/deploy/subnet-router/setup.sh -o /tmp/setup.sh
chmod +x /tmp/setup.sh

PREAUTH_KEY=tskey-auth-XXXXXXXX \
SUBNET_ROUTER_HOSTNAME=skygate-subnet-<username> \
SUBNET_CIDR=<USER_SUBNET> \
sudo -E /tmp/setup.sh
```

The equivalent raw command (what the admin page renders, and what `setup.sh`
ends up running):

```bash
sudo tailscale up --accept-routes --netfilter-mode=off \
  --login-server=https://head.example.com \
  --hostname=skygate-subnet-<username> \
  --advertise-routes=<USER_SUBNET> \
  --authkey=tskey-auth-XXXXXXXX
```

Add `--advertise-exit-node` to the same command if the router should also offer
its internet uplink as an exit node (then approve it from `/admin/exit-nodes`).

**Forwarding on the router host** (required — `ping <router>` works without it,
`ping <LAN device>` does not):

```bash
sudo sysctl -w net.ipv4.ip_forward=1
echo 'net.ipv4.ip_forward=1' | sudo tee /etc/sysctl.d/99-router.conf
sysctl -w net.ipv6.conf.all.forwarding=1

ip route show <USER_SUBNET>       # must resolve to the LAN interface, e.g. dev eth0

# Only if the host firewall drops forwarded packets:
sudo iptables -A FORWARD -i tailscale0 -j ACCEPT
sudo iptables -A FORWARD -o tailscale0 -j ACCEPT
```

**Approval / verification on the skygate host:**

```bash
# Watch the sidecar auto-approve:
docker logs -f skygate | grep -E 'sidecar.*approved|<USER_SUBNET>'

# Per-user end-to-end health check (DB + headscale + denorm + UI + audit):
bash scripts/check_subnet_router.sh <username>
bash scripts/check_subnet_router.sh <user_id>

# Manual approval if the sidecar did not fire:
docker exec headscale headscale nodes list
docker exec headscale headscale nodes approve-routes -i <NODE_ID> --routes <USER_SUBNET>

# From another tailnet client (must have --accept-routes):
ping skygate-subnet-<username>     # the router's own tailnet address
ping <LAN_DEVICE_IP>               # a device behind the router
```

The Go regression coverage for the whole flow:

```bash
go test -count=1 -short ./internal/feature/admin/
```

The one-time shell script `e2e_pilot.sh` that was used for the original live

download the bundle from `/admin/users/<id>/subnet/download` → extract the preauth
key from `commands.txt` → start a sidecar node → confirm `tag:subnet-router` and
the advertised routes → wait for `sidecar.SyncOnce` auto-approval → confirm the
`sidecar: approved <CIDR> on node skygate-subnet-<user> (user=<id>)` log line →
load `/my/devices` and confirm `user_subnets.status` becomes `router_active` with
the `portal_users` denormalised columns matching.

**Removing a router** (`POST /admin/users/{id}/subnet/remove`, admin-only,
idempotent). Verify afterwards that (1) `headscale nodes list -o json` no longer
contains the `skygate-subnet-<user>` GivenName, (2) the `user_subnets` row is back
to `pending` with empty `router_node_id`/`router_hostname`, and (3) `audit_log`
has a `subnet_router_removed` row.

Remove is the inverse of provision: it reads `user_subnets.router_node_id`, calls
`headscale.Client.DeleteNode(nodeID)` (failure is logged, not fatal), clears the
`user_subnets` row and the four denormalised `portal_users` columns
(`subnet_status`, `subnet_cidr`, `subnet_router_node_id`,
`subnet_router_hostname`), then writes the audit row. ACL is **not** re-applied —
`h-user-<user>-subnet` is always present in the policy regardless of router
status. To pause without losing progress use
`POST /admin/users/{id}/subnet/disable` instead.

### 2.5 State that must stay consistent

The subnet-router feature has one fact ("this user's CIDR is served by node N")
mirrored in several places. Drift between them is the most common cause of
"the UI says `active` but nothing is reachable".

| Store | Columns | Written by | Notes |
|---|---|---|---|
| `user_subnets` | `status`, `cidr`, `router_node_id`, `router_hostname` | provision, sidecar tick, Remove | the **source of truth** |
| `portal_users` (denorm) | `subnet_status`, `subnet_cidr`, `subnet_router_node_id`, `subnet_router_hostname` | `/my/devices` load | refreshes only when the page is loaded |
| `node_owner_map` | `(hostname, user_id, headscale_id)` | node-ownership backfill | maps the headscale node to the portal user; must key on the headscale **GivenName** |
| `device_exit_node_prefs` | per `(user, device)` preferred exit | reconciler / UI | used for the `via:` clause, not for subnets |
| headscale policy | `tagOwners[tag:subnet-router]`, `h-user-<user>-subnet → <USER_SUBNET>` | `SetPolicy` on ACL regen | must include `tag:subnet-router` in `tagOwners` |
| headscale node | `allowedRoutes` vs `enabledRoutes` | `tailscale up` + `approve-routes` | advertised ≠ enabled |

`router_active` means **only** "skygate approved a route for this user". It does
not prove that a device exists behind the router, or that the router host has
`ip_forward=1`. A route can be approved and still be **phantom**: the router is on
a LAN that does not actually contain `<USER_SUBNET>` devices, so headscale accepts
the route, clients install it, and the kernel at the router drops every packet.
Use Remove, not disable, to clean up a phantom router.

### 2.6 Operational cautions

- **The preauth key is the security boundary.** Anyone holding it can register a
  node tagged `tag:subnet-router`; the auto-approver matches the **hostname only**
  and does not verify the advertised CIDR against `user_subnets.cidr`, so a stolen
  key could advertise `0.0.0.0/0`. Rotate quickly (1-hour TTL) and check the
  advertised CIDR after approval.
- **The router is a single point of failure** for that user's LAN; the sidecar marks
  it `disabled` but never re-allocates the CIDR.
- **The router host sees LAN traffic in cleartext** — it is a router, not a VPN
  concentrator.

## 3. Exit nodes and the exit-rules reconciler

An **exit node** replaces the default route for clients that select it: every
non-tailnet packet from the client goes out through that node. A **subnet router**
re-routes only specific CIDRs. The two are deliberately separate concerns —
`0.0.0.0/0` must come from an exit node, never from a subnet-route advertisement on
a host that needs its own LAN.

### 3.1 Registration

1. The host advertises `--advertise-exit-node` (plus `0.0.0.0/0`,
   `::/0` — see below) when it joins the tailnet.
2. The admin tags/approves it: `/admin/exit-nodes` → *Tag as exit-node* (approves
   only `0.0.0.0/0,::/0`, not the node's entire available-route set), or
   `headscale nodes tag --force <id> tag:exit-node`.
3. Skygate stores a row in `exit_servers` with `enabled`, `ssh_target`,
   `ssh_key_path`, and `accept_routes`. The SSH target supports
   `user@host:port`; skygate splits it into `user@host` + `-p port` because `ssh`
   does not accept the `host:port` shorthand on the command line.
4. Skygate keeps the node's advertised routes in sync over SSH and then approves
   them in headscale.

**Exact command skygate sends over SSH** (`BuildTailscaleSetCommand`):

```
tailscale set --advertise-exit-node --advertise-routes=0.0.0.0/0,::/0,<rule CIDRs…>[ --accept-routes=true|false]
```

`--advertise-routes=` **replaces** the list atomically, so `0.0.0.0/0` and `::/0`
are always prepended and the caller's routes are deduped against them. `ssh` is
invoked as:

```bash
ssh -i <ssh_key_path> -o BatchMode=yes -o StrictHostKeyChecking=accept-new \
    -o ConnectTimeout=10 [-p <port>] <user@host> \
    "tailscale set --advertise-exit-node --advertise-routes=…"
```

**Approval in headscale** (the `/api/v1/routes` endpoint is 404 in headscale
0.29.1, so skygate shells out):

```bash
docker exec headscale /ko-app/headscale nodes approve-routes \
  -i <NODE_ID> -r "0.0.0.0/0,::/0,<CIDRs…>" --force
```

`accept_routes` semantics on `exit_servers`: `-1` →
`--accept-routes=false` (recommended when the node co-hosts another VPN, so peer
subnets don't leak into source-routing table 52), `0` → leave the flag alone,
`1` → `--accept-routes=true`.

### 3.2 Per-device and per-user preference precedence

A client is *pinned* to an exit node only when the headscale grant carries a
`via:` clause. That clause is built from `device_exit_node_prefs`. Precedence:

```
per-device pref (user_id + device_hostname)   ← wins
per-user pref   (user_id + empty/`*` hostname) ← only when no per-device row
no pref → no `via:` clause → the client is free to pick any exit node (or none)
```

Prefer to set the preference through the UI (`/my/devices` → *Preferred
exit-node*, or `/admin/devices` for an admin override); the reconciler exists to
fill in the same rows automatically.

### 3.3 The three layers (and why confusing them hides outages)

- **Layer 1 — `device_rules`.** Per-`(user, device, exit_node)` "allow this traffic
  on this exit node" rules, created at `/my/exit-rules` or `/admin/derp`. They are
  the operator's permanent intent.
- **Layer 2 — `device_exit_node_prefs`.** Per-`(user, device)` "use exit node X for
  everything", created by the auto-reconciler each tick or manually in the UI.
  Derived **only** from Layer 1; updated when the device's dominant exit node
  changes (stale tag → canonical tag).
- **Layer 3 — headscale policy grants.** The rendered HuJSON, where each grant may
  carry `via: [tag:dev-infra-<exit-node>]`. Built by
  `POST /admin/exit-rules/reapply` (or any ACL regen) and overwritten on every
  reapply.

The flow is `Layer 1 ──auto-create──▶ Layer 2 ──reapply──▶ Layer 3`. All three must
be present. A rule that exists in Layer 1 but has no Layer 2 row produces a grant
**without** `via:`, which is allowed but not pinned — the symptom is "the rule
exists but the traffic still goes out the wrong exit node".

### 3.4 What the reconciler does each tick

`exit_rules.ReconcileDeviceExitNodePrefs` runs in the background (boot + every
`SKYGATE_PREFERRED_RECONCILE_INTERVAL`, default `1h`) and is a pure decision over
each `(user, device_hostname)` pair via `PlanDevicePrefChange`:

| # | State | Decision | Reason string |
|---|---|---|---|
| 1 | empty pref, **1** distinct `exit_node`, valid canonical tag | **CREATE** | `missing-pref-unanimous` |
| 2 | empty pref, **2+** distinct `exit_node`s | **SKIP** | `missing-pref-split` (operator must choose) |
| 3 | empty pref, no canonical tag (host absent from `node_owner_map`) | **no-op** | the host may come back; do not clobber |
| 4 | existing pref with a non-canonical tag | **UPDATE** | `stale-tag` (e.g. `tag:dev-<user>-basic` instead of `tag:dev-infra-<exit>`) |
| 5 | existing pref canonical, `via=0` | **UPDATE** | `via-disabled-but-canonical` |
| 6 | existing pref canonical, `via=1` | **no-op** | idempotent — no audit churn |
| 7 | `user_id` with no `portal_users` row | **CREATE** (empty username) | must not crash on a missing username |
| 8 | `SKYGATE_PREFERRED_RECONCILER_LIVE` unset | **live = true** | default-on; opt out with `false/0/no/off` |

**Ordering inside a tick**: read enabled `device_rules` → group by
`(user_id, device_hostname)` → load the existing pref row → resolve the canonical
tag from `node_owner_map` (never from user input) → apply the decision only in live
mode → write one `audit_log` row per change (`action='preferred_exit_reconciled'`)
plus a rate-limited alert (1 per `(hostname, reason)` per hour). The reconciler does
**not** push the ACL — run `POST /admin/exit-rules/reapply` (or let the next
`ApplyACLPipelineForPlane` call) to materialise the `via:` clause in headscale.

**Idempotency**: case 6 is a strict no-op, so repeated ticks do not grow the audit
log; cases 1/4/5 converge to case 6 after one write.

**Failure modes**: live mode off (`… live=false`) logs every change but writes
none — the silent-footgun class; no canonical tag (case 3) leaves the pref stale by
design; split exit nodes (case 2) yields no pref because the reconciler cannot
choose; a missing username (case 7) is handled and must remain non-fatal.

**Scheduling / tuning knobs**:

| Env var | Default | Effect |
|---|---|---|
| `SKYGATE_PREFERRED_RECONCILE_ENABLED` | `true` | master switch for the startup goroutine (per-tick override also readable from `global_settings.preferred_reconcile_enabled`) |
| `SKYGATE_PREFERRED_RECONCILE_INTERVAL` | `1h` | tick cadence; `0` disables the goroutine entirely |
| `SKYGATE_PREFERRED_RECONCILER_LIVE` | unset → **live** | set `false/0/no/off` for dry-run |
| `SKYGATE_ACL_VIA_ENABLED` | unset | must be set to `true` for the reapply to emit `via:` clauses at all |
| `SKYGATE_DNS_AUTO_CHECK` | `5m` | domain-rule → `/32` refresh + `StaggeredSync` |
| `SKYGATE_NODE_DISCOVERY_INTERVAL` | `5m` | dev-tag backfill (new devices only) |
| `SKYGATE_STAGGER_INTERVAL` | `30s` | spacing between per-node SSH route syncs |

These four intervals are the freshness budget for "I set a preferred exit node but
the connection still tries the wrong one": worst case is one
`PREFERRED_RECONCILE_INTERVAL` for a stale pref, one `DNS_AUTO_CHECK` for a
domain-rule IP, one `NODE_DISCOVERY_INTERVAL` for a brand-new device, and
`STAGGER_INTERVAL × <node count>` for a full route sync. Lowering them trades
headscale API + SSH load for freshness.

### 3.5 Health and latency reporting

| Surface | Source | What it reports |
|---|---|---|
| `/admin/exit-nodes` | `internal/monitoring/exit_node_monitor.go` | `online` / `degraded` / `offline` per exit node |
| `/admin/derp/dashboard` | `internal/derphealth/cron.go`, every 5 min | region latency + health for public/bundled DERP |
| `/admin/exit-rules` | `internal/feature/exit_rules` | per-rule preferred host + `Applicable` flag |
| `exit_rule_logs` / `audit_log` | sync + reconciler | every route sync, ACL reapply, pref change |
| system tests | `/admin/system_tests`, `scripts/tailnet_probe.sh` | tailnet peer visibility (`tailnet.split_suspected`) |

**Online detection rule: trust headscale, not `last_seen`.** An idle exit node with
no peer traffic for hours has a stale `last_seen` but headscale still reports
`Online=true`. The monitor takes headscale's `n.Online` as the primary signal and
consults `OfflineAfter` (`SKYGATE_EXIT_NODE_OFFLINE_AFTER`, default `10m`) only when
headscale says offline; `0`/empty disables the fallback entirely.

DERP latency is outside skygate's control: `tailscale netcheck` on the node is the
authoritative measurement. The right relay minimises
`(node → DERP) + (peer → DERP)`, which is not necessarily the geographically nearest
relay for one side. Report and diagnose; do not "fix" a transatlantic leg with a
policy change.

## 4. Advertised-routes troubleshooting and ordering constraints

### 4.1 The hard rule

> **Never advertise a subnet that the advertising host is itself inside of.**

A host that advertises its own LAN creates a routing loop on every client that
accepts routes: the client's kernel prefers the more specific
`<lan> dev tailscale0` over the default route, sends the packet to the relay, the
relay routes it back through the same LAN via the same host, and so on. Typical
multi-hop RTT blow-up: a ~130 ms peer path multiplied by 3–4 hops becomes
500–1700 ms. LAN clients on that subnet lose direct Ethernet access to their own
siblings because Tailscale's route shadows the local route.

| CIDR class | Advertise? | Why |
|---|---|---|
| the LAN the host sits in | **NO** | the host is *inside* it — loop, and every same-LAN peer already has a direct Ethernet route |
| `<DOCKER_BRIDGE_CIDR>` (host-local bridges) | **NO** | only the host needs to reach its own bridges; remote clients have no use for them |
| `<USER_SUBNET>` (a per-user subnet *external* to the advertising host) | **YES** | this is the subnet-router use case — the host sits outside the CIDR it serves |
| `0.0.0.0/0` | **NO** on a subnet router | default-route advertisement is only valid with `--advertise-exit-node` and an approved `tag:exit-node` |

### 4.2 Verify

```bash
# On the advertising host: is the route direct or via Tailscale?
ip route get <LAN_PEER_IP>
# Expected: <LAN_PEER_IP> dev ens18 src <host LAN IP>   (direct, not tailscale0)

# What is this node actually advertising?
tailscale status --json | python3 -c "
import sys, json
d = json.load(sys.stdin)
print('Self.PrimaryRoutes:', d['Self'].get('PrimaryRoutes', []))
print('Self.Prefs.AdvertiseRoutes:', d['Self'].get('Prefs', {}).get('AdvertiseRoutes', []))"
# Expected for a pure exit node: 0.0.0.0/0, ::/0 only.

# On a LAN client: confirm the direct path won
ip route get <LAN_PEER_IP>
# Expected: via <gateway> dev eth0   (direct Ethernet, not Tailscale)
```

The fix for a self-LAN advertisement is one command on the offending host:

```bash
sudo tailscale set --advertise-routes=""
sudo systemctl restart tailscaled
```

### 4.3 Ordering constraints

These orderings are load-bearing; reversing them produces silent partial state.

1. **Advertise → approve → accept.**
   `tailscale set --advertise-routes=…` only makes a route *available*. Headscale
   must run `nodes approve-routes` before any client installs it, and the client
   must run with `--accept-routes`. Skipping the middle step is the classic
   "the relay advertises it but headscale shows it as not enabled".

2. **Exit-node base routes are always present.**
   `--advertise-routes=` replaces the list. Any sync that drops `0.0.0.0/0`/`::/0`
   silently demotes the node from exit node to ordinary node. Skygate prepends
   them, so never hand-edit the advertised list to remove them.

3. **`device_rules` → `device_exit_node_prefs` → ACL reapply.**
   Layer 2 must exist *before* the ACL is regenerated, otherwise the grant is
   emitted without `via:` and the pin is decorative. If you write a rule by hand,
   wait for the reconciler tick **or** insert the pref, then hit
   `POST /admin/exit-rules/reapply`.

4. **Rename: add the new tag before removing the old one.**
   The node-ownership rename path calls `AddTag(new)` first and `UntagNode(old)`
   only on success, and only then updates `node_owner_map`. The reversed order
   leaves a node with **no** dev-tag when headscale rejects the new tag
   (`InvalidArgument: requested tags are invalid or not permitted`) — and the DB
   row is left out of sync with headscale.

5. **Annotate before grouping.**
   In the `/admin/exit-rules` render path, per-rule `PreferredHost` values are
   annotated onto the rule structs **before** they are copied into the page's
   grouping map. Annotating after the copy silently loses the values and the page
   shows "no preferred exit-node set" for every rule.

6. **Subnet-route sync is per node, once.** `SyncAdvertisedRoutes` sends exactly one
   `SetAdvertisedRoutes` per node with the full aggregated route list, then one
   `approve-routes`; `StaggeredSync` spaces nodes by `SKYGATE_STAGGER_INTERVAL`
   (default 30 s) so a 4-node fleet does not open four simultaneous SSH sessions.

7. **DNS rule refresh precedes route push.** A `target_type='domain'` rule resolves
   to concrete `/32` rows only on the `SKYGATE_DNS_AUTO_CHECK` tick (default 5 min),
   and only after that does the staggered sync push them to the exit nodes. A
   freshly-added domain rule therefore has a bounded window where the ACL allows
   the traffic but no exit node knows the IP.

8. **`--force-recreate`, not `restart`, after any `extra_hosts`/volume change.**
   Container DNS/hosts state is rendered at create time, and compose interpolation
   is CWD-relative — `${…:-default}` placeholders silently take their defaults when
   compose runs outside the project directory.

## 5. DERP — ports, certs, host networking, health probing

DERP (Designated Encrypted Relay for Packets) relays encrypted traffic when a
direct peer-to-peer path cannot be established. Headscale is configured with
`derp.urls` — a list of HTTPS URLs serving Tailscale-shaped `derpmap.json`
documents. See [`derp.md`](derp.md) for the feature/config reference; this section
covers the topology and the operational traps.

### 5.1 Deployment modes

| Mode | Config | Behaviour |
|---|---|---|
| Bundled derper | `DERP_ENABLED=true`, `DERP_EXTERNAL_URLS` empty | deploys the `derper` container, writes `derpmap.json`, appends `https://<DERP_HOSTNAME>/derpmap.json` to `derp.urls` |
| External relay(s) | `DERP_EXTERNAL_URLS=https://derp1.example.com,https://derp2.example.com` | no container; each URL is appended to `derp.urls` |
| Bundled + external | both set | both in `derp.urls`; clients try in order, first responder wins |
| No custom DERP | both empty/false | public Tailscale DERP relays only |

Since the web-UI relay management landed, `derp_relays` is the source of truth:
`/admin/derp/relays` does add/edit/delete/toggle + per-row *Test connection*, the
bundled container is the `is_bundled=1` row, and
`GET /admin/derp/relays/derpmap.json` publishes a skygate-managed map that
headscale fetches over the compose network (`http://skygate:8080/…`, no `authMW`).
`POST /admin/derp/relays/apply-headscale` rewrites the headscale config
(`SKYGATE_HEADSCALE_CONFIG_PATH`) and restarts headscale — idempotent and audited
as `derp_apply_headscale`.

### 5.2 Ports

| Port | Proto | Purpose | Notes |
|---|---|---|---|
| `DERP_DERP_PORT` (default **443**) | tcp | HTTPS + `/derp` WebSocket upgrade | `--certmode=manual` **requires** :443 ("Serves HTTPS if the port is 443 and/or `-certmode` is manual, otherwise HTTP") |
| `DERP_HTTP_PORT` (default **80**) | tcp | HTTP → HTTPS redirect / ACME helper | the pre-v1.5.8 default of `8443` was a leftover and is an active trap: a stale `DERP_HTTP_PORT` in `.env` shadows the DB-derived port |
| `DERP_STUN_PORT` (default **3478**) | udp | STUN endpoint | first source is `DERP_STUN_PORT`; there is no STUN column in `derp_relays` |
| `DERP_MAP_PORT` (legacy `8765`) | tcp | legacy derpmap serving | superseded by the skygate derpmap endpoint |
| `--verify-clients=<URL>` | — | client-verification against headscale | must be empty to disable; an empty value used to crash the container |

### 5.3 Certs

- Manual cert mode reads the cert directory bind-mounted into the container (the
  systemd-era path is reused read-only, so a migration need not copy files).
- The cert files are **operator-managed**: certsync writes to its own
  `/var/lib/skygate/certs/`, *not* the derper cert directory — a copy step bridges
  them.
- The derper must serve the hostname clients dial; a CN/SNI mismatch is the usual
  cause of a probe that "connects but reports the wrong thing".

### 5.4 Host networking

The derper container runs with `network_mode: host`: it binds privileged :443, :80
and the STUN :3478/udp, and bridge networking would need explicit port mappings
while losing listen-address parity with the legacy systemd unit. The container's
`--a=:<port>`/`--http-port` must therefore not collide with the host's own
listeners, and the host firewall must allow those ports from clients.

A Docker-image migration path exists (`deploy/docker/derper/Dockerfile`, built
locally to avoid a registry that may be blocked, plus the idempotent
`scripts/migrate_derper_to_docker.sh`, which leaves the systemd unit
stopped-but-present as the rollback). Host networking is deliberately kept, so
`/admin/derp` needs no change after the migration.

### 5.5 How skygate probes relay health

`collectDerpStatus` (`internal/feature/admin/derp.go`) runs on every
`/admin/derp` page load:

1. **Resolve the target.** `resolveDERPHostname` / `resolveDERPPort` take the **DB
   first** (the `is_bundled=1 AND enabled=1` row, `ORDER BY id ASC LIMIT 1` for
   determinism when duplicate bundled rows exist), then the env var
   (`SKYGATE_DERP_HOSTNAME` / `DERP_HTTP_PORT`), then empty.
2. **Probe the rich debug endpoints** (`/debug/vars`, `/debug/…`) over
   `https://<host>:<port>` with a TLS-aware client (SNI from the URL hostname;
   `InsecureSkipVerify` only when the host is a literal IP).
3. **Fall back to a WebSocket liveness probe** when debug parsing fails. Production
   hardening disables `--debug` (the `/active-conn` and `/all-recent` endpoints leak
   client connection info), so the debug endpoint returns 403/plain text. The
   fallback probes `/derp` (always on for a functional derper): `101 Switching
   Protocols` ⇒ `DERPER-SERVICE: running`. Rich metrics still win when `--debug` is on.
4. **Display** service state, port, STUN port, active connections, bytes, regions.

**Public IP display**: the *public IP* is the DNS A record of the configured
hostname, resolved through a public resolver rather than the container's own
resolver chain. The value carries a provenance annotation (`dns:env` /
`dns:derper` / `egress`); the last-resort egress fallback is the container's
docker-bridge source address and is usually **wrong** for this purpose.

**DERP health cron**: `internal/derphealth/cron.go` probes every region every
5 minutes and feeds `/admin/derp/dashboard`. The page-load probe and the cron are
different consumers of the same facts; a "degraded" dashboard row is normally a
missing latency sample rather than a down relay.

### 5.6 Container DNS / `/etc/hosts` interaction (the probe trap)

When skygate runs in a container and the derper runs on the **same host**:

1. The host's `systemd-resolved` (or any resolver honoring `/etc/hosts`) resolves
   the host's own hostname to `127.0.0.1`. Docker's default DNS setup inherits
   this, so the container resolves `derp.example.com` to **its own loopback**,
   where nothing is listening.
2. Symptom: the derper clearly works (valid cert, WebSocket upgrade via curl,
   STUN listening) but `/admin/derp` reports `stopped` / `Unreachable` / `0 active
   connections`.
3. **Fix**: pin the hostname in the skygate service's `extra_hosts`, with the
   address supplied by an operator-managed `.env` variable so the template stays
   generic:

   ```yaml
   services:
     skygate:
       extra_hosts:
         - "derp.example.com:${SKYGATE_DERP_PROBE_HOST:-127.0.0.1}"
   ```

   The `127.0.0.1` default is a safe fallback: with no derper the probe fails
   cleanly and nothing else in skygate breaks.
4. **The change only takes effect on recreate**, and compose interpolation is
   CWD-relative:

   ```bash
   cd <project dir>            # NOT `docker compose -f /path/…` from elsewhere
   sudo docker compose up -d --force-recreate --no-deps skygate
   ```

   A plain `restart` reloads the binary but keeps the old `/etc/hosts`; running
   compose from an unrelated CWD silently uses the placeholder default.

### 6.1 Verification commands


### 6.2 Symptom → cause → fix

| Symptom | Likely cause | Fix |
|---|---|---|
| `ping <router tailnet IP>` works, `ping <LAN device>` doesn't | `ip_forward=0`, host firewall drops forwarded packets, or the advertised CIDR isn't the LAN's CIDR | enable `net.ipv4.ip_forward=1` (+ `net.ipv6.conf.all.forwarding=1`); allow `FORWARD` on `tailscale0`; advertise the real LAN CIDR |
| `/admin/users/{id}/subnet` stuck on `pending` | the denormalised `portal_users.subnet_status` only refreshes on `/my/devices` | load `/my/devices` (or wait one sidecar tick) |
| Status pill flips `router_active` ↔ `active` every 30 s | sidecar writing `status='active'` on a tick and clobbering the router-state | upgrade to a build where the sidecar logs `sidecar: approved …` and never writes `status=active` |
| MagicDNS doesn't resolve `skygate-subnet-<user>` | client has `--accept-dns` off, or `tag:subnet-router` missing from `tagOwners` | `tailscale up --accept-dns`; `POST /admin/exit-rules/reapply` |
| Route approved but nothing behind it | phantom route — the router is on a LAN that does not contain `<USER_SUBNET>` | provision a router on the real LAN, or `POST /admin/users/{id}/subnet/remove` |
| `500–1700 ms` to a LAN peer that should be ~1 ms | the advertising host advertises **its own LAN** → route loop | `tailscale set --advertise-routes="" && systemctl restart tailscaled` |
| `/admin/derp` shows `stopped` while the derper is running | container resolves the hostname to `127.0.0.1`; HTTP probe against an HTTPS derper; debug disabled and no liveness fallback | `extra_hosts` pin + `--force-recreate`; probe `https://`; upgrade for the `/derp` WebSocket liveness probe |
| `/admin/derp` flips between two ports on refresh | duplicate `is_bundled=1` rows and a non-deterministic `LIMIT 1` | upgrade for `ORDER BY id ASC LIMIT 1`; clean duplicate rows |
| `/admin/derp` `Public IP` shows a bridge address | egress fallback used instead of the DNS A record | set `SKYGATE_DERP_HOSTNAME`; upgrade for `resolvePublicDERPIP` with provenance |
| Exit node shows `offline` in `/admin/exit-nodes` despite being reachable | `last_seen`-based override on an idle node | trust headscale `n.Online`; keep `SKYGATE_EXIT_NODE_OFFLINE_AFTER` (default `10m`) as a fallback only |
| Preferred exit node ignored / rule "allowed but not pinned" | `device_exit_node_prefs` row missing, `SKYGATE_ACL_VIA_ENABLED` unset, or the policy was not reapplied | wait a reconciler tick (or set the pref in the UI), set `SKYGATE_ACL_VIA_ENABLED=true`, `POST /admin/exit-rules/reapply` |
| New domain rule has no effect for a few minutes | `/32` rows appear only on the `SKYGATE_DNS_AUTO_CHECK` tick, then route sync | `POST /admin/exit-rules/sync`, or lower `SKYGATE_DNS_AUTO_CHECK` |
| Brand-new device cannot use an exit node | dev-tag not yet applied → the per-device grant doesn't match | wait one `SKYGATE_NODE_DISCOVERY_INTERVAL` tick (5 min) |
| Exit-node sync log shows `ssh=err=…` | `ssh_target` unresolvable, missing `ssh_key_path`, or the relay is down | fix `exit_servers.ssh_target` (`user@host` / `user@host:port`), set `ssh_key_path` or `SKYGATE_EXIT_SSH_KEY` |
| Exit node IS this host (`tailscale status` reports the relay's address as `Self`), yet the sync still wants SSH or reports a missing key | before v1.5.57 the transport was always SSH, and `/admin/exit-nodes` warned about a key the local node does not need | upgrade to v1.5.57+: the relay is marked «локальный узел» and the routes are applied with a local `tailscale set`. If the service user cannot run it, the page shows the rung — see §6.3 |
| Local exit node: `local=err=… permission denied` / `local=err=… no local way to apply tailscale routes` | the skygate user may not run `tailscale set` (daemon socket is root-only, no `--operator`, no `NOPASSWD` rule) | one of: `sudo tailscale set --operator=<skygate user>`; a sudoers rule `skygate ALL=(root) NOPASSWD: /usr/bin/tailscale set`; or `sudo bash deploy/install-routes-helper.sh` (root-owned applier, no sudoers needed) |
| Local exit node: the sync reports `self_subnet_skipped=…` | the relay advertises a subnet this host sits INSIDE → the documented route loop (`500–1700 ms` to a LAN peer) | intended: skygate refuses that route and reports it. Remove the rule/subnet, or move the relay to a host outside the advertised network |
| `/admin/exit-rules` shows "no preferred exit-node set" for every rule | preference computed after the rule structs were grouped | upgrade for the annotate-before-group ordering |

### 6.3 Exit node on the skygate host (the local transport, B293)

When the machine that runs skygate is **also** an exit node — headscale, skygate and
the relay in one place, which is the reference `aro` host — the local tailscaled IS
the relay:

```console
$ tailscale status --json | jq '{Self: {Host: .Self.HostName, IPs: .Self.TailscaleIPs}}'
{"Self": {"Host": "exit-node-vps", "IPs": ["100.64.0.1","fd7a:115c:a1e0::1"]}}
```

skygate detects this from **evidence** — the daemon's own addresses against the
addresses headscale reports for the relay — and then applies
`tailscale set --advertise-exit-node --advertise-routes=…` **locally**, with no SSH
and no key. A shared hostname is deliberately not enough (the reserved name
`skygate-host` once matched every relay); "I could not ask the local daemon" keeps
the SSH path, so a container install (whose own tailscaled is a different node) is
unaffected.

**Privileges.** `tailscale set` needs root, the daemon's `--operator` user, or a
NOPASSWD sudoers rule. skygate walks a ladder and names the rung it used in the sync
result (`local=ok via direct|sudo|helper approved=N`):

| Rung | Needs | Result string |
|---|---|---|
| `direct` | skygate runs as root, **or** `tailscale set --operator=<skygate user>` was applied to the daemon | `local=ok via direct` |
| `sudo` | a sudoers rule: `<skygate user> ALL=(root) NOPASSWD: /usr/bin/tailscale set` | `local=ok via sudo` |
| `helper` | nothing: skygate stages a data-only request and the root-owned applier consumes it | `local=ok via helper` |

The helper is `deploy/skygate-apply-routes.sh`, triggered by
`skygate-routes.path`/`.service` (installed by `install-common.sh`, re-installable
on an existing host with `sudo bash deploy/install-routes-helper.sh`). It re-validates
every value and passes the whole CIDR list as one argv element, then records its
verdict in `<update_dir>/routes-apply.status`. Only a **privilege refusal** falls
through to the next rung — a real `tailscale set` error is reported as-is, and a
staged request nobody consumed is an error, not a success.

**Guard: never advertise a network this host sits inside.** A co-located relay that
advertises its own LAN sends the host's own traffic to LAN peers into the tunnel and
back (`500–1700 ms` for a 1 ms hop). skygate drops such routes, keeps the exit-node
bases (`0.0.0.0/0`, `::/0`), and reports `self_subnet_skipped=…` in the sync result.

**Egress is not a thing here.** If the relay IS this host, its way out to the
internet is skygate's own, so `telegram.egress_node_id` pointing at it cannot route
anything — and the `api.telegram.org` probe on `/admin/telegram` becomes
*representative* (it measures exactly the path the bot will use). If Telegram is
unreachable from this host, the answer is a **different** relay on another machine.
