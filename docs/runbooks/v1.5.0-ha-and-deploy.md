## 1. Prerequisites

You need these **before any v1.5.0 feature works**:

1. **A working skygate v1.4.x deploy** (the v1.5.0 surface is
   additive — it does NOT change v1.4.x behaviour unless you
   enable the new env vars).
2. **`SKYGATE_SECRET_KEY`** in `.env` — the HA chain's external DNS
   credentials (cert + password) are stored encrypted via
   `db.EncryptForColumn` (AES-256-GCM keyed by this env var).
   Without it, the /admin/ha "External DNS" form will return
   `db.ErrSecretKeyUnset` on save.
3. **An S3 deploy bucket** for certsync + binary deploys.
   The default is `s3://skygate-backups/`, reused from the backup
   pipeline. Set `SKYGATE_HA_DEPLOY_S3_BUCKET=skygate-backups` in
   `.env` on every node. The layout under the bucket is:
   - `ha/certs/{cert.pem,key.pem,.version}` — certsync (B147)
   - `deploy/<target-hostname>/{skygate,meta.json}` — binary
     deploy (B150)
4. **Patroni + etcd already running** (the v1.5.0 plan explicitly
   does NOT touch Patroni config — the elector reads Patroni's
   existing REST API on `http://localhost:8008/patroni`).
5. **Tailscale headscale MagicDNS** working — the chain uses
   hostnames (`skygate`, `skygate-standby`), not IPs, so the
   nodes must be resolvable to each other by name.

**Smoke test** before any of this:

```bash
# On the active node
curl -fsS http://localhost:8080/healthz
# Expected: 200, "db_backend": "postgres"
curl -fsS http://localhost:8080/readyz
# Expected: 200, all dependencies green (db/headscale/headplane/tailscale)
```

If `/healthz` or `/readyz` is not green, **fix that first**. v1.5.0
builds on a working v1.4.x; it does not paper over a broken one.

## 2. B145 — HA chain + elector + pluggable DNS provider

### 2.1 What it is

The HA model is **active-passive with priority chain**:

- One node holds the "active" role (responds to the public FQDN,
  owns the DNS A-record, holds the cert + secrets).
- The rest are "standby" nodes, ordered by priority (P1 is the
  preferred active, P2 is the first failover target, etc).
- The "next active to promote" is the lowest-priority ALIVE member
  in the chain. "Alive" = heartbeat seen within
  `MissedThreshold * HeartbeatInterval` (= 15s with defaults).

This is **NOT** active-active. Two writers → split-brain → data
corruption. The 2026-08-18 v1.5.0 plan locks active-passive, and
Patroni is already configured for synchronous replication. The
elector reads Patroni state but does NOT participate in the
election.

### 2.2 Storage

The chain is a single JSON blob under `global_settings.ha_chain`:

```json
{
  "members": [
    {"hostname": "skygate",         "priority": 1, "public_ip": "192.0.2.10", "tailscale_ip": "100.64.0.10", "last_seen_unix": 1724000000, "role": "active"},
    {"hostname": "skygate-standby", "priority": 2, "public_ip": "192.0.2.11", "tailscale_ip": "100.64.0.11", "last_seen_unix": 1724000000, "role": "standby"}
  ],
  "auto_failover_enabled": true,
  "last_transition_unix": 0
}
```

The /admin/ha page is a UI around `internal/ha.LoadChain` /
`internal/ha.SaveChain`. SaveChain is transactional and idempotent
(returns `changed=false` if the new bytes match the old ones, so
re-saving the same form is a no-op).

Other global_settings keys the HA feature uses:

| Key | What | Encrypted? |
|---|---|---|
| `ha_chain` | The chain JSON above | no (operational state) |
| `ha_apply_active_role` | The elector's "force target" | no |
| `ha.dns.cert_pem_enc` | the configured DNS provider SSL cert PEM | **yes** (AES-256-GCM) |
| `ha.dns.password_enc` | the configured DNS provider API password | **yes** (AES-256-GCM) |
| `ha.dns.zone` | e.g. `example.com` | no |
| `ha.dns.login` | e.g. `<your-dns-provider-login>` | no |
| `ha.dns.provider` | always `external` for v1.5.0 | no |

### 2.3 How to bootstrap a chain

**First-time setup** (no chain yet):

1. SSH to the node that should be **P1** (the preferred active).
2. Enable the elector:
   ```bash
   # /opt/skygate/.env on the node
   SKYGATE_HA_ENABLED=true
   SKYGATE_HA_HEARTBEAT_INTERVAL=5s        # default
   SKYGATE_HA_MISSED_THRESHOLD=3           # default; 3 missed * 5s = 15s
   SKYGATE_HA_ROLE=auto                    # default; "active" or "standby" also valid
   ```
3. Open `https://<your-fqdn>/admin/ha` (you'll need an
   `SKYGATE_ADMIN_USER` / `SKYGATE_ADMIN_PASSWORD` set — see
   `docs/deploy.md`).
4. Section 3 (HA nodes / CRUD) — add each node. For each:
   - `hostname` = the headscale MagicDNS name (e.g. `skygate`,
     `skygate-standby`)
   - `priority` = 1, 2, 3, ... (lower = higher priority)
   - `public_ip` = the public IP the external DNS A-record
     should resolve to when this node is active
   - `tailscale_ip` = optional, used by the elector for
     reachability checks
5. Section 2 (Failover policy) — set `auto_failover_enabled` to
   `true` if you want the elector to auto-promote; `false` for
   fully manual (force promote only).
6. Click **Save chain**. The chain is now in
   `global_settings.ha_chain`. The elector on every node (once
   they have `SKYGATE_HA_ENABLED=true`) reads it on the next
   5-second tick and starts heartbeating.
7. Section 6 (Audit log) — confirm `ha.bootstrap` row is present.

**Adding a node later**: Section 3 → "Add node" form → fill in
the new node → Save. The elector on the new node picks up the
chain on its next tick and starts participating.

**Removing a node**: Section 3 → "Remove" button on the row.
**WARNING**: if you remove the active node, the elector will
auto-promote the next-priority ALIVE member on the next tick
(if auto-failover is enabled). If you want a clean "remove the
active without promoting", disable auto-failover first
(Section 2), then remove, then re-enable.

### 2.4 How the elector works (5s tick)

Every `SKYGATE_HA_HEARTBEAT_INTERVAL` (default 5s), the elector
on each node:

1. Asks local Patroni REST API
   (`http://localhost:8008/patroni`) whether THIS node is the PG
   primary. Patroni is the source of truth for "am I primary
   right now" — we don't replicate Patroni's election logic.
2. Asks each remote member (via Tailscale IP) whether it has
   seen a recent heartbeat from THIS node. The remote members
   reciprocate, so the chain converges.
3. Decides the new global role assignment:
   - If THIS node is Patroni primary AND the chain's current
     "active" slot is empty OR points at a higher-priority
     member that's now unreachable: THIS node self-promotes
     and writes the new chain.
   - If THIS node is NOT primary but the chain still has THIS
     node as active: demote self (write the new chain with the
     lowest-priority ALIVE member as active).
4. Writes the updated chain via `SaveChain` so the /admin/ha
   page sees the new state on its next render. An audit log
   entry (`ha.role_change from=X to=Y reason=...`) is appended
   via `db.AppendExitRuleLog` (we reuse the existing table —
   adding a new audit table is more migration cost than the
   feature needs at v1.5.0).

### 2.5 Failover behavior

| Scenario | What happens (auto-failover on) | What happens (auto-failover off) |
|---|---|---|
| Active node dies, standby alive | Standby misses 3 heartbeats (15s), promotes itself, writes chain, sends Telegram | Nothing; operator must click "Force promote" or run `skygate ha promote skygate-standby` |
| Active node comes back | Standby stays active (auto-reclaim is OFF by default). Operator must click "Reclaim primary" or run `skygate ha reclaim` | Same |
| Standby dies | Active logs `ha.member_unreachable`, keeps serving | Same |
| Both nodes die (etcd down) | Patroni is frozen at last known state; reads + writes may stall if you happened to fail over mid-write. Restart etcd, the cluster resumes within 30s (Patroni's `loop_wait`) | Same |
| Network partition (split-brain) | Risk: both nodes think they're active. **Mitigation**: Patroni's leader lock + the elector's read of Patroni primary state + DNS TTL means writes to the "wrong" node are isolated. Recovery: resolve the network, run `skygate ha reclaim` on the higher-priority node | Same |

**Anti-flap rule (locked 2026-08-18)**: when a previously-dead P1
node comes back, the system does NOT auto-flip back. This avoids
the classic "P1 dies, P2 takes over, P1 returns, P1 takes over,
P1 dies again, P2 takes over" flap. The operator explicitly
reclaims with `skygate ha reclaim` (CLI) or the "Reclaim primary"
button on /admin/ha.

### 2.6 Force actions

Force actions do **NOT** bypass the elector. They write the
desired state to `global_settings.ha_apply_active_role`; the
elector's next tick (5s) sees the new state and either confirms
(if Patroni agrees) or overwrites (if Patroni disagrees). This
keeps the operator's intent visible in the audit log without
racing the elector.

| Action | Effect | Reversible? |
|---|---|---|
| `skygate ha promote <host>` | Sets `ha_apply_active_role=<host>`; elector promotes within 5s | Yes — set to empty / run `skygate ha reclaim` |
| `skygate ha demote <host>` | Sets `ha_apply_active_role=<host>`, then immediately clears. Net effect: revokes any "auto-promote to <host>" intent | Yes |
| `skygate ha reclaim` | Sets `ha_apply_active_role=""`, lets the elector re-pick (P1 wins if alive) | Yes — promote someone else |

The /admin/ha page Section 5 (Force actions) and the /admin/deploy
page Section 3 (HA actions) call into the same primitives — the
CLI and the UI share the path.

### 2.7 Pluggable DNS provider

The DNS failover (B145) supports **multiple providers** through a
common interface (`internal/dns/provider.go`):

```go
type Provider interface {
    Name() string                                         // "external", "cloudflare", "route53", "rfc2136"
    GetRecord(ctx, zone, name) (ip string, err error)
    UpdateRecord(ctx, zone, name, ip) error
    TestConnection(ctx) error
}
```

`BuildProvider` reads `SKYGATE_DNS_PROVIDER` and returns the
matching client. At v1.5.0 the only fully-shipped provider is
`external` (B146 live test is blocked (deferred to manual mode); the code path exists and is
covered by unit tests, but the live external DNS provider API is not yet
reachable from this VM). Cloudflare / Route53 / RFC2136 are
interface-only — the code paths exist but the per-provider
implementations are deferred to v1.5.x.

**Adding a new provider** (v1.5.x future work):

1. Create `internal/dns/<your-provider>/<your-provider>.go`
2. Implement the 4 `Provider` interface methods
3. Add a `case "<your-provider>":` in `BuildProvider`
4. Add a test (`<your-provider>_test.go`) with a unit test using
   a local httptest.Server — DO NOT hit the live provider API
   from a unit test
5. Add a section to /admin/ha §4 with the provider-specific
   fields (API token, zone, etc.)
6. Add a B-check to verify the wiring

For now, the operator configures the external DNS via /admin/ha §4
(External DNS). The /admin/ha "Test" button calls
`extcreds.Store.TestConnection`, which uses the external DNS provider API's
`/api/<provider-v2-path>/zone/get_zone` endpoint as a ping — the response
payload is irrelevant; only the HTTP status and `error_code`
matter.

### 2.8 Troubleshooting

| Symptom | Likely cause | Fix |
|---|---|---|
| Both nodes show "active" in the chain | Split-brain (network partition healed) | `skygate ha reclaim` on the higher-priority node |
| Chain not loading on a node | `SKYGATE_HA_ENABLED=false` on that node | Set to `true` in `.env`, restart skygate |
| Elector writes the chain but no one sees it | `SKYGATE_HA_HEARTBEAT_INTERVAL` is high (e.g. 60s) | Lower it; the B145 default of 5s is the recommended setting |
| "Test connection" on /admin/ha returns `db.ErrSecretKeyUnset` | `SKYGATE_SECRET_KEY` not in `.env` on the node rendering the page | Add it; restart skygate |
| `ha.role_change` audit row keeps firing for the same pair | Network blip causing 15s heartbeat miss; check Tailscale between nodes | Tailscale-side; check `tailscale status` on both nodes |
| Operator pushed the wrong chain via psql | Chain fails `Validate()` on next load | Revert the `global_settings.ha_chain` row to the last known-good JSON |

## 3. B147 — In-app certsync scheduler

### 3.1 What it does

Before B147, the cert pipeline (scripts/cert-renew.sh + system
cron) ran certbot / DNS-01 via the configured provider on the **active** node only,
wrote the new PEM + key to `/var/lib/skygate/certs/`, and reloaded
Caddy via `docker exec skygate-caddy caddy reload`. On a HA
cluster, the standby had no cert of its own — when the active
died and the standby was promoted, the cert on the standby was
either stale (last sync was 60+ days ago) or missing. Promotion
would then 502 until the operator manually ran the cert-renew
script on the new active.

B147 fixes this by running a per-node scheduler that polls the
S3 deploy bucket for a `.version` file, pulls the newer certs if
the local SHA doesn't match, and reloads Caddy. Same upload
triggers the new certs on BOTH nodes simultaneously, so failover
is always cert-fresh.

### 3.2 S3 layout

```
s3://<SKYGATE_HA_DEPLOY_S3_BUCKET>/
  ha/
    certs/
      cert.pem       # the current cert
      key.pem        # the matching private key
      .version       # JSON: {"version": 5, "sha256": "...", "uploaded_at": "..."}
```

The `.version` file is a tiny JSON manifest with a monotonically
increasing version number + the SHA-256 of the current
`cert.pem` + `key.pem` pair. The active node uploads the cert
+ bumps `.version` after every renewal; every other node polls
`.version` + downloads the new certs when its hash changes. This
pattern works identically to a CDN (write-once, read-many) and
is resilient to the active node being down (the standby still
has a working poll target).

### 3.3 Tick behavior

Tick interval: 30s by default (env override
`SKYGATE_CERTSYNC_INTERVAL=30s`). Coarse enough to be cheap, fine
enough that an active cert upload propagates to all nodes within
30s (the operator's mental model: "I clicked Apply, and within a
minute both nodes have the new cert").

On each tick:

1. **HEAD** `.version` in S3 (no body — just metadata).
2. If the remote version > local version OR the remote cert
   SHA-256 != local cert SHA-256:
   a. Download `cert.pem` + `key.pem` to a temp file.
   b. Verify the pair is a valid x509 cert + RSA/EC key
      (`crypto/x509.ParseCertificate` + ParsePKCS1/8).
   c. Atomic rename into the live path
      (`SKYGATE_CERTSYNC_LOCAL_DIR/cert.pem` + `key.pem`,
      default `/var/lib/skygate/certs/`).
   d. Trigger the Caddy reload callback (operator-supplied;
      usually `docker exec skygate-caddy caddy reload`).
   e. Update local `.version` cache + write an `audit_log` row
      `certsync.pull` with the new SHA-256 + version.
3. **Self-check** (runs every tick, regardless of cert change):
   if the local cert expires within 7 days, log a WARNING + send
   Telegram alert (so the operator has time to renew before the
   cert actually dies and breaks the HTTPS listener).

### 3.4 Why a hash-based version + not the cert's NotBefore/NotAfter

A cert can be renewed EARLY (operator manually triggers a renewal
30 days before expiry). The NotAfter changes on every renewal,
but the operator's intent is "pull whenever I upload a new one"
— not "pull when the cert age changes". A version file the
operator controls is simpler and more explicit. The `.version`
file format is just a JSON object:
`{ "version": 5, "sha256": "...", "uploaded_at": "..." }`.

### 3.5 Configuration (env vars)

```
SKYGATE_CERTSYNC_ENABLED=true                              # default true
SKYGATE_CERTSYNC_S3_BUCKET=skygate-backups                 # default
SKYGATE_CERTSYNC_LOCAL_DIR=/var/lib/skygate/certs          # default
SKYGATE_CERTSYNC_INTERVAL=30s                              # default
```

### 3.6 Failure modes

| Symptom | Likely cause | Fix |
|---|---|---|
| Tick is a no-op, no error in logs | S3 unreachable (network blip) | Same as B130/B142: tick is a no-op, next tick is fresh |
| Tick is a no-op, ".version 404" in logs | No certs uploaded yet | Expected on a fresh deploy; upload via /admin/certificates |
| Downloaded cert is invalid (parse fails) | Cert + key don't match (operator uploaded a cert without re-uploading the key, or vice versa) | Log error + Telegram alert, do NOT replace the live cert. The operator can investigate via the audit log |
| Caddy reload callback fails | `docker exec skygate-caddy caddy reload` errors | Log error + alert, but the cert is still on disk. The next manual Caddy reload will pick it up (same "best-effort reload" pattern B130 uses) |
| Telegram not configured | `Notifier == nil` | Silent; operator sees the failure in /admin/audit and the certsync log lines |
| Two parallel pulls race | `inFlightPull` mutex prevents this | The pull is fast (S3 + atomic rename + 1 Caddy reload) so a 30s tick never overlaps with itself in practice; the mutex is a safety net |

### 3.7 How certsync interacts with /admin/certificates (B148)

The /admin/certificates "Upload" handler writes to the SAME S3
layout the certsync scheduler reads. After a successful upload,
the certsync scheduler picks up the new cert on its next 30s
tick — the /admin/certificates page does NOT need to "push to
nodes" or "reload Caddy", the B147 surface handles that
automatically. So the operator flow is:

1. Open `/admin/certificates` on any node
2. Upload the new cert (paste PEM + key, or browse)
3. Wait 30s
4. Both nodes now have the new cert; Caddy reloaded; audit row
   `certsync.pull` on both nodes

## 4. B148 — /admin/certificates page

### 4.1 Page surface (4 sections)

1. **Current cert info** — Subject + NotAfter + days_left +
   SHA-256 (read from the local file the certsync writes)
2. **Upload form** — paste PEM cert + matching key (or browse
   to upload); the handler validates the pair
   (`x509` + `matchedAny`), writes to S3, bumps `.version`
3. **DNS-01 toggle** — "Enable Let's Encrypt auto via the configured provider
   DNS-01" (the actual cert-acquisition flow is v1.5.x; this
   v1.5.0 surface stores the operator's intent in
   `global_settings` + writes an audit row)
4. **Recent cert events** — last 10 `certsync.*` audit rows
   (filtered at query time)

### 4.2 Upload flow

```
1. Operator pastes PEM (cert + key) or browses to upload
2. Handler reads the pair
3. certsync.validateCertKeyPair is called:
     - x509.ParseCertificate on the cert
     - x509.ParsePKCS1PrivateKey / x509.ParsePKCS8PrivateKey /
       x509.ParseECPrivateKey on the key
     - matchedAny checks the cert's public key matches
       the key's public key
4. If valid:
     - Writes cert.pem + key.pem to s3://<bucket>/ha/certs/
     - Bumps .version (increments + updates SHA-256 + uploaded_at)
     - Writes audit row certsync.upload
5. The certsync scheduler (B147) on every node picks up the
   new cert on its next 30s tick
```

The validation re-uses `certsync.validateCertKeyPair` so the
rules stay in one place. If B147's check ever loosens (e.g.
adds Ed25519 support), B148 picks it up automatically.

### 4.3 DNS-01 toggle (intentional minimal v1.5.0)

The DNS-01 toggle is intentionally minimal for v1.5.0: it just
stores `dns01_enabled=true` in `global_settings`. The actual
cert-acquisition flow (LE certbot + DNS-01 via the configured provider challenge) is
a separate v1.5.x surface (Phase 4.5 in the plan) that depends
on B146 being unblocked. The v1.5.0 toggle is the "intent" — the
operator sees the toggle, sets it on, and a future v1.5.x release
reads the toggle + runs the LE flow.

If the operator toggles it on, the page shows a clear message:
"LE auto-renewal via DNS-01 (provider) is queued for the v1.5.x
release. This toggle stores your intent." (B148 also writes
an `audit_log` row so the operator's intent is visible.)

### 4.4 Common pitfalls

| Pitfall | What happens | Fix |
|---|---|---|
| Cert uploaded without matching key | `validateCertKeyPair` fails | Re-upload both as a pair; the page shows the mismatched-key error inline |
| Cert is for the wrong domain | Upload succeeds, but the live HTTPS breaks (Caddy serves a cert for the wrong FQDN) | Upload the correct cert; the next 30s tick will replace it |
| Caddy reload callback not configured | Cert on disk, but Caddy serves the old one until the next manual reload | The Caddy reload callback is a build-time wire-up in `cmd/skygate/main.go`; verify the callback is set during initial deploy |
| `.version` write fails (S3 transient) | Audit row says "upload FAILED", but the cert is on disk; certsync picks it up on the next tick anyway | Just wait; the next 30s tick will reconcile |

## 5. B149 — /admin/ha page

### 5.1 Page surface (6 sections)

1. **Cluster topology** — read-only chain table (hostname,
   priority, public_ip, tailscale_ip, last_seen_unix, role)
2. **Failover policy** — auto / manual radio + auto-reclaim toggle
3. **HA nodes (CRUD)** — add / remove buttons
4. **External DNS (provider)** — credentials form + "test" button
5. **Force actions** — promote / demote / reclaim
6. **Audit log (read-only)** — last 20 HA-related events

### 5.2 CRUD operations

| Action | What it does | Reversible? |
|---|---|---|
| Add node | Appends a member to the chain; validates hostname + public_ip | Yes — Remove |
| Remove node | Removes the member; if it was active, the next tick elects the new active (if auto-failover on) | Yes — Re-add |
| Edit priority | Re-sorts the chain by priority; the lowest-priority member becomes "active" on the next tick | Yes — Edit again |
| Edit raw JSON (debug form) | Parses the operator's text + calls `SaveChain` | Yes — but the page re-loads the chain from DB on next render |

**WARNING** on Remove: if you remove the active node with
auto-failover on, the elector auto-promotes the next-priority
ALIVE member within 5s. If you want a clean "remove without
promoting", disable auto-failover first (Section 2), then remove,
then re-enable.

### 5.3 Force actions

Force actions (Section 5) and the /admin/deploy Section 3 share
the same code path as the CLI (`skygate ha promote|demote|reclaim`).
See §2.6 for the full semantics.

| Button | What it does | When to use |
|---|---|---|
| Force promote | Sets `ha_apply_active_role=<selected-host>`, elector promotes within 5s | The active is degraded and you want to move traffic NOW (don't wait for auto-failover) |
| Force demote | Sets + clears `ha_apply_active_role=<selected-host>`, revokes any auto-promote intent to that host | Take a node out of active rotation temporarily (e.g. for maintenance) without auto-reclaim bringing it back |
| Reclaim primary | Sets `ha_apply_active_role=""`, elector re-picks (P1 wins if alive) | A higher-priority node came back; you want to move traffic back to it manually |

### 5.4 External DNS (provider) form

The Section 4 form is the operator-managed way to set the external DNS
credentials. The credentials live in 5 `global_settings` rows
(encrypted cert + password + plaintext zone / login / provider).
The form:

- **Provider** dropdown — `external` only at v1.5.0; other values
  are reserved for v1.5.x
- **Login** (text) — e.g. `<your-dns-provider-login>` or
  `user@example.com`
- **Password** (password) — the "Альтернативный пароль" from
  the provider's "Настройки API" (or equivalent) page
- **Zone** (text) — the zone you own, e.g. `example.com`
- **Cert PEM** (textarea) — paste the SSL cert PEM (BEGIN
  CERTIFICATE … END CERTIFICATE)
- **Key PEM** (textarea) — paste the matching key PEM (BEGIN
  RSA/EC PRIVATE KEY … END …)

Clicking **Test** calls `extcreds.Store.TestConnection`, which uses
the external DNS provider API's `/api/<provider-v2-path>/zone/get_zone` endpoint as a
ping. The response payload is irrelevant; only the HTTP status
and `error_code` matter. On success, the page shows
"external: ok (latency=NNNms)".

### 5.5 Anonymization reminder

NEVER commit real certs, keys, passwords, or your real
`<your-dns-provider-login>` into a file in this repo. The
`/admin/ha` form writes them to `global_settings` (encrypted);
they are NEVER logged in the audit_log plaintext; the audit_log
only records the `ha.test` event, not the creds. (The
`scripts/verify_pre_deploy.sh` B18 anonymization sweep catches
accidental commits — see `docs/BACKLOG.md` §v1.5.0 §18 for the
locked policy.)

### 5.6 Common pitfalls

| Pitfall | What happens | Fix |
|---|---|---|
| Save chain fails with "duplicate priority" | Two members have the same priority | Edit one of them to a unique priority |
| Save chain fails with "empty hostname" | Operator cleared the hostname field | Re-fill; the chain must have at least one member with a non-empty hostname |
| Test returns `auth_error` | wrong login, wrong password, or cert is for a different provider account | Re-paste the correct creds; provider creds are account-scoped (the cert is per-account, not per-user) |
| Test returns `ACCESS_DENIED_FROM_IP` | VM's public IP not in the the provider's "Диапазоны IP-адресов" (or equivalent) whitelist | Add `<your-vm-public-ip>/32` in the provider's "Настройки API" (or equivalent) → "Диапазоны IP-адресов" |
| Test returns `IP_EXCEEDED_ALLOWED_CONNECTION_RATE` | Hit the provider's 1200/hour rate limit (per user AND per IP) | Wait an hour; vary test parameters to avoid the "10 identical wrong" sub-limit |
| Test returns `ACCESS_DENIED_FROM_IP` even with whitelist correct + correct creds | Hit the provider's "10 identical wrong requests" sub-limit (separate per-user counter) | **Only the provider's support can reset this.** Operator must contact the provider's support |
| Save creds returns `db.ErrSecretKeyUnset` | `SKYGATE_SECRET_KEY` not in `.env` on the node rendering the page | Add it; restart skygate |

## 6. B150 — /admin/deploy page + skygate deploy CLI

### 6.1 CLI subcommands

The package implements two top-level subcommands wired from
`cmd/skygate/main.go`:

```
skygate deploy {push,pull,sync,status}
skygate ha    {promote,demote,reclaim}
```

| Subcommand | Required args | Effect |
|---|---|---|
| `deploy push` | `[--target=X]` | Build the local binary, upload to `s3://<SKYGATE_HA_DEPLOY_S3_BUCKET>/deploy/<target>/` |
| `deploy pull` | `[--target=X]` | Pull the latest deployed binary from S3, write to `/usr/local/bin/skygate`, trigger a graceful restart |
| `deploy sync` | (no args) | Atomic push + wait + pull (used by `scripts/rolling_deploy.sh`) |
| `deploy status` | (no args) | Print local + remote build version, timestamps, S3 object metadata |
| `ha promote` | `<hostname>` | Set `ha_apply_active_role=<host>`, elector picks it up on the next 5s tick |
| `ha demote` | `<hostname>` | Set + clear `ha_apply_active_role=<host>` (revoke auto-promote intent) |
| `ha reclaim` | (no args) | Set `ha_apply_active_role=""`, elector re-picks (P1 wins if alive) |
| `help` | (no args) | Print help |

### 6.2 /admin/deploy page surface (4 sections)

1. **Cluster topology** — read-only chain table (same data as
   /admin/ha section 1)
2. **Deploy controls** — Push / Pull / Test-failover buttons
   (per-target dropdown)
3. **HA actions** — promote / demote / reclaim (same as /admin/ha
   section 5)
4. **Audit log** — read-only last N deploy + HA events

The 3 POST handlers mirror the CLI verbs so an operator who
can't SSH to the box (or is on a phone, or wants a
CSRF-protected form submission) can drive the same actions from
the web.

The **"Test failover"** button is a dry-run: it computes what
the elector WOULD do if the active node went down right now
(read the chain + `ha_apply_active_role`, render the "next
active" prediction) WITHOUT touching the chain or the audit log.
This is the operator's "show me what would happen if I pulled
the power on P1" tool.

### 6.3 Rolling deploy flow

The recommended flow for a new release:

```bash
# 1. Build + push from the workstation
cd /path/to/skygate
git pull
make build
./skygate deploy push --target=skygate
./skygate deploy push --target=skygate-standby

# 2. Verify S3 has the new binaries
./skygate deploy status

# 3. Pull on each node (one at a time, with a smoke test
#    between them)
ssh <skygate>  "skygate deploy pull && sleep 30 && curl -fsS http://localhost:8080/healthz"
ssh <skygate-standby> "skygate deploy pull && sleep 30 && curl -fsS http://localhost:8080/healthz"

# 4. (Optional) Reclaim primary if the new build is preferred
ssh <skygate> "skygate ha reclaim"
```

The /admin/deploy "Sync" button does steps 1+3 atomically. The
"Push" / "Pull" buttons are the granular versions.

### 6.4 Configuration

```
SKYGATE_HA_DEPLOY_S3_BUCKET=skygate-backups   # required for any deploy/* subcommand
SKYGATE_HA_SELF_HOSTNAME=skygate              # optional override; default os.Hostname()
```

`SKYGATE_HA_DEPLOY_S3_BUCKET` is the S3 bucket that holds the
`deploy/<target>/` layout. It defaults to nothing — the deploy
subcommands return `ErrNoS3Config` if unset.

### 6.5 Common pitfalls

| Pitfall | What happens | Fix |
|---|---|---|
| `deploy push` returns `ErrNoS3Config` | `SKYGATE_HA_DEPLOY_S3_BUCKET` not set | Set it in `.env` on the workstation running `skygate deploy push` |
| `deploy pull` runs but Caddy is broken | The new binary has a regression; rollback is via `git checkout <last-known-good-tag> && make build && deploy push` | Roll back; check `git log` for the suspect commit |
| `ha promote` returns "not a member of the chain" | Typo in the hostname | Re-run with the correct hostname from the chain table |
| `ha promote` succeeds but the elector doesn't pick it up | `SKYGATE_HA_ENABLED=false` on the target node | Set to `true` on every node; restart skygate |
| "Test failover" shows the wrong prediction | The prediction is based on `ha_apply_active_role` + chain; if you've recently promoted, the prediction reflects the override, not the chain's natural priority | This is correct behavior; click "Reclaim primary" if you want the chain's natural priority to win |
| `deploy status` shows different version on the active vs standby | Normal during a rolling deploy; resolves once the second node is pulled | Wait for the rolling deploy to complete |

curl -fsS http://localhost:8080/healthz

curl -fsS http://localhost:8080/readyz
# Expected: 200, all dependencies green (db/headscale/headplane/tailscale)

If these are not green, **fix that first**. v1.5.0 builds on a

### 7.2 Inspect the chain from the DB

```bash
# Read the current chain JSON
psql ... -c "SELECT value FROM global_settings WHERE key = 'ha_chain';"

# Read the elector's "force target" (empty = elector decides)
psql ... -c "SELECT value FROM global_settings WHERE key = 'ha_apply_active_role';"

# Read the DNS provider creds metadata (NOT the secret itself)
psql ... -c "SELECT value FROM global_settings WHERE key LIKE 'ha.dns.%';"
```

The actual cert + password are encrypted — the DB dump shows
ciphertext only, which is the right behavior.

### 7.3 Recent HA + certsync events

```bash
# Last 20 HA events
psql ... -c "SELECT created_at, actor, action, target, reason FROM audit_log WHERE action LIKE 'ha.%' ORDER BY id DESC LIMIT 20;"

# Last 10 certsync events
psql ... -c "SELECT created_at, actor, action, target, reason FROM audit_log WHERE action LIKE 'certsync.%' ORDER BY id DESC LIMIT 10;"

# Last 10 deploy events
psql ... -c "SELECT created_at, actor, action, target, reason FROM audit_log WHERE action LIKE 'deploy.%' ORDER BY id DESC LIMIT 10;"
```

### 7.4 Verify the certsync is alive

```bash
# On each node, check the local .version cache
cat /var/lib/skygate/certs/.version
# Should be a JSON object with version, sha256, uploaded_at
# matching what's in s3://<bucket>/ha/certs/.version

# Check the cert SHA-256 matches
sha256sum /var/lib/skygate/certs/cert.pem
# Compare with the .version file's sha256
```

If the local SHA doesn't match the .version, certsync will pull
on the next tick (30s). If the local cert is fine but the
version is stale, the operator's upload didn't actually bump
the version — re-upload via /admin/certificates.

### 7.5 Verify the elector is alive

```bash
# Check the audit log for ha.heartbeat rows (one per minute
# per node, with summary of who's alive)
psql ... -c "SELECT created_at, actor, action, target, reason FROM audit_log WHERE action = 'ha.heartbeat' ORDER BY id DESC LIMIT 10;"

# Check the live chain for last_seen_unix — should be within
# 30s of "now" if the elector is healthy
psql ... -c "SELECT value->'members' FROM global_settings WHERE key = 'ha_chain';"
```

If `last_seen_unix` is older than 60s, the elector on that node
is stalled. Check `journalctl -u skygate` for panics; check
`/readyz` for the underlying dependency.

## 8. Common failure modes (cross-cutting)

### 8.1 Heartbeat miss → false failover

**Symptom**: the active node is healthy, but the chain flips to
the standby (or vice versa).

**Likely cause**: Tailscale connectivity between the two nodes
blipped for 15s (3 missed heartbeats at the 5s default).

**Fix**: check `tailscale status` on both nodes; resolve the
network issue; run `skygate ha reclaim` on the higher-priority
node once connectivity is restored.

**Anti-flap rule**: the system does NOT auto-flip back when the
P1 node recovers; the operator explicitly reclaims. This is
intentional (see §2.5).

### 8.2 Certsync stuck

**Symptom**: new certs uploaded via /admin/certificates, but
the standby is still serving the old cert after 30s+.

**Likely causes (in order of probability)**:
1. Standby's `SKYGATE_CERTSYNC_ENABLED=false`
2. Standby's S3 client can't reach the bucket (network blip)
3. Standby's local `.version` cache is corrupt (e.g. operator
   manually edited it)
4. Caddy reload callback on the standby is broken

**Fix**: check the standby's audit log for `certsync.pull` rows
in the last minute; check `journalctl -u skygate` on the standby
for certsync errors; verify the S3 bucket is reachable from the
standby (`aws s3 ls s3://<bucket>/ha/certs/`).

### 8.3 S3 unreachable

**Symptom**: certsync ticks are no-ops, deploy push/pull fails
with "S3 unreachable", the backup scheduler starts failing.

**Fix**: this is a single point of failure for v1.5.0 (the S3
bucket is the source of truth for certsync + the deploy
pipeline). The pre-v1.5.0 backup pipeline already had this
property; the v1.5.0 features reuse the same bucket. Recovery:
restore the S3 bucket (see `docs/backup-restore-and-migration.md`).

### 8.4 DNS provider auth failure

**Symptom**: HA failover is stuck — the new active node
successfully takes over the chain, but the external DNS still
points at the old IP.

**Likely cause**: the DNS provider creds in /admin/ha §4 are stale
(either the cert expired, the password was rotated, or the
whitelist was changed).

**Fix**: open /admin/ha §4, click **Test**. If it returns
`auth_error`, re-paste the correct creds. If it returns
`ACCESS_DENIED_FROM_IP`, check the whitelist in the provider's's
"Настройки API". If it returns `IP_EXCEEDED_ALLOWED_CONNECTION_RATE`,
wait an hour.

### 8.5 Elector writes the chain but the UI shows stale data

**Symptom**: you ran `skygate ha promote skygate-standby` on
the CLI; the audit log shows the `ha.promote` row; but
/admin/ha still shows `skygate` as active.

**Likely cause**: the /admin/ha page re-loads the chain from
DB on every render; if you're seeing stale data, the chain on
disk is actually what the page shows, not what the CLI
requested. The CLI wrote `ha_apply_active_role=skygate-standby`
but Patroni may not have agreed (so the elector didn't promote).

**Fix**: check the `ha.role_change` audit rows for the reason
Patroni disagreed. Common reason: `skygate-standby` is not the
Patroni primary. Resolve Patroni first, then re-promote.

## 9. Migration from v1.4.x → v1.5.0-alpha1

The v1.5.0 surface is **purely additive**. v1.4.x behaviour is
preserved unless you enable the new env vars. The migration is:

### 9.1 Code side

```bash
# 1. Pull the v1.5.0-alpha1 tag
cd /opt/skygate
git fetch --tags
git checkout v1.5.0-alpha1

# 2. Rebuild
docker compose build

# 3. Restart (no --force-recreate needed for additive changes)
docker compose up -d --no-deps skygate

# 4. Verify
curl -fsS http://localhost:8080/readyz
# Expected: 200, all dependencies green
```

### 9.2 .env additions (opt-in)

```
# --- B145 (HA chain + elector) — opt-in ---
SKYGATE_HA_ENABLED=true
SKYGATE_HA_HEARTBEAT_INTERVAL=5s
SKYGATE_HA_MISSED_THRESHOLD=3
# SKYGATE_HA_ROLE=auto         # default; "active" or "standby" also valid
# SKYGATE_HA_SELF_HOSTNAME=skygate  # default os.Hostname()

# --- B147 (certsync) — opt-in but on by default ---
SKYGATE_CERTSYNC_ENABLED=true
SKYGATE_CERTSYNC_S3_BUCKET=skygate-backups
SKYGATE_CERTSYNC_LOCAL_DIR=/var/lib/skygate/certs
SKYGATE_CERTSYNC_INTERVAL=30s

# --- B150 (deploy) — opt-in ---
SKYGATE_HA_DEPLOY_S3_BUCKET=skygate-backups

# --- external DNS provider (B145) — opt-in ---
SKYGATE_DNS_PROVIDER=external
# Creds live in /admin/ha §4 (encrypted via SKYGATE_SECRET_KEY)

# --- Master key for B145 DNS provider creds encryption ---
SKYGATE_SECRET_KEY=<your-32-byte-base64-key>  # generate with: openssl rand -base64 32
```

### 9.3 No data migration needed

- The HA chain (B145) is stored under `global_settings.ha_chain`.
  Fresh deploys have an empty chain; existing deploys are
  unaffected.
- The certsync state (B147) is computed on the first tick from
  the existing S3 layout. If the bucket is empty (no certs
  uploaded yet), the tick is a no-op.
- /admin/certificates (B148), /admin/ha (B149), and /admin/deploy
  (B150) are new routes; they don't touch any existing data.

### 9.4 Backout

The additive nature means you can back out by:

```bash
cd /opt/skygate
git checkout v1.4.4   # or whatever the previous tag was
docker compose build
docker compose up -d --force-recreate --no-deps skygate
```

The new `global_settings` rows (ha_chain, ha_apply_active_role,
ha.dns.*) will be left in the DB but ignored by v1.4.x. They
do NOT affect v1.4.x behaviour.
